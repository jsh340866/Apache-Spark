## 1. 한 줄 소개 (엘리베이터 피치)

> "기존에 Spring Boot로 만들어둔 가치투자 종목 추천 서비스(ValuePick)가 있는데, 여기서 계산하는 재무지표를
> Spark로 재현하고, 나아가 'PER 몇 이하, PBR 몇 이하인 종목을 매달 담아 투자했다면 실제로 얼마를 벌었을까'를
> 검증하는 백테스팅 파이프라인을 별도로 만들었습니다. 핵심은 원본 데이터 자체는 작지만, 전략 조합을 수백~수천 개
> 곱해서 돌리는 지점에서 Spark 분산 처리가 실질적으로 필요해진다는 걸 실측으로 증명하는 것이었습니다."

---

## 2. 예상 질문과 답변

### Q1. 이 프로젝트를 왜 만들었나요?

기존 ValuePick은 Spring Boot + MySQL 기반으로 실시간 API 호출 위주였습니다. 그런데 "이 전략이 과거에
얼마나 좋았는지"를 검증하려면 대량의 과거 데이터를 여러 조건으로 반복 계산해야 하는데, 이건 실시간 서비스
구조와 맞지 않는 별개의 배치/분석 워크로드입니다. 그래서 기존 서비스를 건드리지 않고 별도 리포로
Spark 기반 배치 파이프라인을 새로 구성했습니다.

### Q2. 전체 파이프라인 구조를 설명해주세요.

01~05번 잡으로 나눴습니다.
- **01_ingest_raw**: DART/공공데이터포털에서 원본을 받아 Parquet로 저장 (MySQL 미경유)
- **02_clean_prices**: 결측 거래일 보간, 액면분할 의심 탐지
- **03_build_indicators**: EPS/BPS/PER/PBR/ROE/부채비율/배당수익률/ROA/모멘텀/F-Score/EPS성장률 계산
- **04_backtest_grid**: 전략 조합별 백테스트 (프로젝트 핵심)
- **05_export_to_mysql**: 결과를 서빙용 MySQL로 적재

각 단계 산출물은 전부 Parquet로 주고받고, MySQL은 최종 서빙 단계에서만 씁니다.

### Q3. 데이터 크기가 얼마 안 되는데 왜 Spark를 썼나요? (가장 중요한 질문)

이 질문에 대한 답이 이 프로젝트의 핵심 논지입니다.

원본 데이터(전 종목 약 2,500개 × 10년 일봉 + 재무제표)는 사실 단일 프로세스로도 처리 가능한 크기입니다.
하지만 04번 백테스트 단계에서 "원본 데이터 × 전략 파라미터 조합 수(500~2,000개) × 리밸런싱 시점 수"를
곱하면 연산량이 수억~수십억 행 단위로 폭증합니다. 이 조합들은 서로 완전히 독립적이라 병렬화 효율이 높고,
워커를 1대에서 2대로 늘렸을 때 처리 시간이 얼마나 줄어드는지 실측 가능합니다.

**"데이터가 작아서 Spark가 불필요하다"는 지적에, "원본은 작지만 전략 그리드를 곱하는 순간 연산량이
폭증해서 분산 처리가 필요해진다"는 걸 실측 수치(튜닝 전/후 처리시간, 워커 스케일링 효과)로
증명하는 것이 이 프로젝트의 핵심 산출물입니다.**

### Q4. 기존 Java 서비스 계산 로직과 어떻게 정합성을 맞췄나요?

`03_build_indicators.py`는 새 계산 로직을 만든 게 아니라, 기존 Spring Boot의
`FinancialIndicatorService`, `DartFinancialCollector`의 계산/매핑 로직을 Spark로 그대로 재현하는 게
목표였습니다. 그리고 이걸 "말로만" 재현했다고 하지 않고, 실제로 검증했습니다.

로컬에 ValuePick을 별도로 기동시키고, 01번이 받은 원본 Parquet을 그대로 MySQL 스키마에 역주입한 뒤,
Java 서버의 지표 계산 API를 실제로 호출해서 나온 값과 Spark로 계산한 값을 종목별로 diff 비교했습니다.
결과는 대조 대상 79종목 중 78종목이 8개 지표(EPS/BPS/PER/PBR/ROE/부채비율/배당수익률/ROA) 완전 일치,
1종목만 반올림 순서 차이로 0.08 오차였습니다.

### Q5. 검증 중에 실제로 버그를 발견한 적 있나요?

네, 있습니다. DART 재무제표 응답에서 `ifrs-full_Equity`(자본총계) 계정이 재무상태표(BS)뿐 아니라
자본변동표(SCE)에도 지분 항목별로 수백 건 중복 등장한다는 걸 발견했습니다.

Java는 API 응답을 순서대로 받아서 HashMap에 "처음 만난 값"을 채택하는 방식이라 우연히 BS 값을
먼저 잡아서 정상 동작했지만, Spark는 분산 처리 특성상 `F.first()`의 순서가 보장되지 않아서
자본변동표의 엉뚱한 하위 항목을 자본총계로 잘못 채택하는 사례가 실제로 발생했습니다.

해결책으로는 DART 응답에 있는 `sj_div`(재무제표 구분: BS/CIS/IS/CF/SCE) 필드로 허용 범위를
명시적으로 필터링했습니다. 이 필드는 Java의 `DartItem.java`에는 아예 없는 필드라, 오히려
"Java보다 더 견고한 방식"으로 개선한 셈입니다. 이 경험에서 배운 건, 분산 처리 환경으로 옮길 때
"어차피 하나만 있겠지"라는 원본 시스템의 암묵적 가정이 깨질 수 있다는 점을 반드시 점검해야 한다는 겁니다.

### Q6. 백테스트에서 자주 나오는 함정이 있는데, 어떻게 대비했나요? (룩어헤드 바이어스)

재무제표는 회계연도와 실제 공시일이 다릅니다. 예를 들어 2023년 사업연도 재무제표는 실제로는
2024년 3~4월에 공시됩니다. 만약 2024년 1월 리밸런싱 시점에 2023년 재무제표를 그대로 써버리면,
그 시점엔 아직 세상에 없던 정보로 투자 판단을 한 셈이 되어 버립니다. 이게 룩어헤드 바이어스입니다.

이를 막기 위해, DART 응답에 들어있는 `rcept_no`(접수번호) 필드를 지표 계산 단계에 추가로
흘려보내도록 만들었습니다. 접수번호 앞 8자리가 실제 공시 접수일(YYYYMMDD)이라는 걸 실제 데이터로
확인했고, 백테스트 조인 조건에 "그 리밸런싱 시점 이전에 실제로 공시된 재무제표만 사용한다"는 조건
(`rcept_no <= rebalance_date`)을 명시적으로 걸 수 있게 만들었습니다.

추가로, 같은 회계연도 데이터가 "당해 사업보고서 자체"와 "다음해 사업보고서의 전기 데이터" 양쪽에서
중복으로 나올 수 있다는 것도 확인해서, 이 경우 더 일찍 공시된(보수적인) 접수번호를 채택하도록 처리했습니다.

### Q6-1. 룩어헤드 바이어스 방지 로직이 실제로 뭔가를 걸러낸 적이 있나요? (실전 검증 사례)

네, 있습니다. 이게 이 프로젝트에서 가장 실감 나는 경험이었습니다.

재무제표 API 응답 한 건에는 당기(thstrm)/전기(frmtrm)/전전기(bfefrmtrm) 3개년 수치가 같이 들어있어서,
2023년 사업보고서 하나만 받아도 2021/2022/2023 3개년 재무 수치를 얻을 수 있습니다. 그래서 처음엔
"이걸로 2021/2022년 지표도 계산해서 3개년 리밸런싱 백테스트를 검증하면 되겠다"고 생각했습니다.

그런데 04번을 처음 돌렸을 때 1,000개 전략 결과가 전부 0건으로 나왔습니다. 원인을 추적해보니, 이 3개년
수치가 전부 **같은 접수번호(2023년 사업보고서가 접수된 2024년 3월)**를 공유하고 있었습니다. 즉
"2021년 자산총계"라는 숫자 자체는 회계적으로 맞지만, 우리 시스템 관점에서는 이 숫자를 2024년 3월에야
알게 된 것으로 기록되어 있는 겁니다. 2021년 말 리밸런싱 시점에 이 수치로 스크리닝하면, 미래(2024년)에
공시될 정보로 과거 투자 판단을 하는 전형적인 룩어헤드 바이어스가 됩니다.

`rcept_no <= rebalance_date` 조건이 이걸 정확히 걸러내서, 2021/2022년 시점 스크리닝 결과가 0건으로
나온 겁니다. 처음엔 "버그인가?" 하고 당황했는데, 실제로는 안전장치가 의도대로 작동한 거였습니다.
이 경험으로 "그 연도의 재무 수치가 존재한다"는 것과 "그 시점에 실제로 공시되어 있었다"는 건 별개의
문제라는 걸 코드가 아니라 실제 데이터로 체감했습니다. 결론적으로 2021/2022년을 백테스트에 실제로 쓰려면
그 해 자체의 사업보고서를 DART에서 따로 수집해야 한다는 걸로 정리했습니다.

### Q7. 전략 조합 1,000개는 어떻게 만들었고, 뭘 의미하나요?

PER 상한(5개), PBR 상한(5개), 배당수익률 하한(4개), 리밸런싱 주기(월간/분기 2개), 보유 종목 수(5개)를
곱해서 1,000개 조합을 파이썬 스크립트로 자동 생성했습니다. 각 조합이 "이 조건대로 투자했으면 어땠을까"를
검증할 하나의 가치투자 전략입니다.

다만 여기서 중요한 건, "1,000개 중 1등 전략이 최적의 정답이다"라고 결론 내리지는 않는다는 점입니다.
같은 과거 데이터 구간에서만 성과가 좋았을 뿐, 그 조건이 미래에도 계속 통한다는 보장이 없기 때문에
과최적화(overfitting) 위험이 있습니다. 이 프로젝트의 산출물은 "최적 전략 발견"이 아니라, 조건별 성과
비교표와 그 대량 계산을 분산 처리로 얼마나 빠르게 처리할 수 있었는지에 대한 성능 실측치입니다.

### Q8. 성능 튜닝은 어떤 순서로 진행했나요? (또는 진행할 계획인가요?)

원칙은 "튜닝 전 수치를 반드시 먼저 실측하고, 그 다음에 튜닝을 적용해서 전/후를 비교한다"입니다.
튜닝을 먼저 적용하고 나중에 "이전엔 이랬을 것이다"라고 추정하는 건 하지 않습니다.

구체적으로는:
1. 튜닝 없는 최초 버전으로 1,000개 전략 백테스트 실행시간을 측정
2. 종목 마스터(작은 테이블)와 대형 시계열 조인 시 셔플이 과도하게 발생하는 지점에 `broadcast()` 힌트 적용
3. 워커의 총 코어 수 기준으로 파티션 수를 `repartition()`으로 재조정
4. 여러 전략에서 반복 참조되는 지표 데이터프레임을 `.cache()`/`.persist()`로 캐싱
5. 각 튜닝 단계마다 실행시간을 다시 측정해서 `docs/PERFORMANCE.md`에 기록

워커를 1대에서 2대로 늘렸을 때 처리 시간이 어떻게 줄어드는지(스케일링 효율)도 같이 실측합니다.

### Q9. 이 프로젝트에서 데이터를 다루면서 조심한 원칙이 있나요?

몇 가지가 있습니다.
- **불확실한 걸 사실처럼 말하지 않는다**: DART/공공데이터 API의 응답 필드나 동작 방식은 실제로 호출하거나
  코드를 읽어서 확인한 뒤에만 언급했습니다. 예를 들어 "재무제표 공시일 필드가 있는지"도 학습 지식으로
  추측하지 않고, 실제 수집된 Parquet 스키마를 Spark로 직접 조회해서 `rcept_no` 필드 존재를 확인한 뒤
  작업했습니다.
- **기존 시스템을 건드리지 않는다**: ValuePick의 MySQL, Entity, 스케줄러는 절대 직접 수정하지 않고,
  API 호출 로직(엔드포인트/인증/파싱)만 참고해서 재사용했습니다.
- **MySQL을 중간 데이터 전달용으로 쓰지 않는다**: Spark 잡 간 데이터 전달은 전부 Parquet로 하고,
  MySQL은 최종 서빙 단계에서만 사용합니다.
- **API 실패를 성급하게 일반화하지 않는다**: 2022년 재무제표를 전체 종목으로 재수집할 때 "재무데이터
  없음" 로그가 많이 떠서 API 문제인가 의심했는데, 바로 원인 조사부터 했습니다. 실제로 특정 종목 몇 개를
  DART API에 직접 재요청해본 결과, LG전자/SK하이닉스/현대차 같은 대형 우량주는 2021~2023 전부 정상
  조회되고, 실패하는 건 애초에 사업보고서가 없는 소형주이거나 삼성화재 같은 금융업 특이 케이스뿐이라는
  걸 확인했습니다. "로그가 많이 뜬다"는 인상만으로 문제를 단정하지 않고 실측으로 검증한 사례입니다.

### Q10. 진행하면서 겪은 시행착오가 있다면?

두 가지가 기억에 남습니다.

첫째, 작업 중간에 Docker Desktop이 재시작되면서 컨테이너들이 한꺼번에 죽었던 적이 있고, 이후 실수로
컨테이너가 실제로 마운트하고 있던 데이터 폴더를 "안 쓰는 사본"으로 착각해서 삭제한 적이 있습니다.
`docker inspect`로 실제 마운트 소스를 먼저 확인하지 않고 파일 수정 시각만 보고 판단한 게 원인이었습니다.
다행히 다른 위치에 복구 가능한 스냅샷이 남아있어서 큰 손실 없이 복구했지만, 이후로는 컨테이너 상태를
바꾸기 전에 반드시 `docker inspect`로 실제 마운트 경로부터 확인하는 습관을 들였습니다.

둘째, DART API 일일 호출 한도 계산을 제 임의로 보수적으로 잡아서 진행을 여러 번 멈춘 적이 있습니다.
실제로는 API 키의 일일 허용 건수를 개발자센터에서 4만 건으로 상향해둔 상태였는데, 그걸 확인하지 않고
기본값(1만 건) 기준으로만 계산해서 "이러다 콜 제한 넘겠다"고 판단해 작업을 보류시켰습니다. 나중에
실제 이용현황(허용 40,000건, 당시 사용 11,968건)을 스크린샷으로 확인하고서야 여유가 충분하다는 걸
알았습니다. 외부 API의 제약 조건은 코드나 기본값으로 추측하지 말고, 실제 계정 설정을 확인해야 한다는
걸 다시 느꼈습니다.

### Q11. 03번에서 발견한 심각한 버그가 있었다고요?

네, 이게 가장 아찔했던 버그입니다. 2021/2022년 재무제표를 실제로 재수집하고 03번을 재실행한 뒤 04번을
돌렸는데도 이상 동작이 계속돼서 파봤더니, **03번 지표 결과가 종목당 1행이 아니라 최대 50행까지
중복**되어 있었습니다.

원인은 `join_momentum`이 `stock_code`만으로 조인하는 구조인데, `01_ingest_raw.py`를 여러 날에 걸쳐
반복 실행하면서 "1개월전/12개월전" 가격 스냅샷이 종목당 여러 날짜로 계속 쌓인 겁니다. 예를 들어
1개월전 스냅샷이 5개, 12개월전 스냅샷이 5개 쌓여 있으면 조인 시 5×5=25배로 뻥튀기됩니다. 각 중복 행은
momentum 값만 다르고 PER/PBR 등 나머지 지표는 똑같았어서, 겉보기엔 멀쩡해 보였습니다.

종목별로 가장 최근 스냅샷 1건만 쓰도록 고치고 나서야 종목당 정확히 1행으로 정상화됐습니다. 이 버그는
79종목으로 검증했던 초기 시점(01번이 딱 한 번만 실행된 상태)에는 드러나지 않았을 겁니다 — **배치를
여러 번 재실행하는 실제 운영 환경에서만 나타나는 버그**였다는 게 중요한 교훈입니다. 배당 데이터 쪽도
같은 유형(원본에 값 있는 행과 공백 행이 동시에 존재)의 문제가 있어서 함께 고쳤습니다.

### Q12. 월간/분기 리밸런싱을 실제로 구현했나요?

네, 처음엔 연 단위로 간소화했다가 이후에 실제로 구현했습니다. 재무제표(사업보고서)는 연 1회만 있어서
스크리닝 기준 자체를 매달 갱신할 수는 없습니다. 그래서 "재무 기준은 그 시점 이전 가장 최근 공시된
사업보고서를 계속 사용하되, 가격 재평가와 포트폴리오 재구성만 매월/매분기 한다"는 방식으로 구현했습니다.
예를 들어 2022년 내내는 2021년 사업보고서를 쓰다가, 2023년 3월 이후부터 자동으로 2022년 사업보고서로
전환되는 식입니다.

이 과정에서 대량의 시점(월간 36개, 분기 12개)을 반복문으로 union하다가 드라이버 OutOfMemoryError를
겪었는데, 원인은 DataFrame의 실행계획(lineage)이 시점 수만큼 계속 이어붙는 구조였습니다. 중간 결과를
`.cache()` 하고 바로 `.count()`로 실체화해서 lineage를 끊어 해결했습니다. 결과적으로 같은 PER/PBR
조건이라도 monthly와 quarterly가 실제로 다른 성과(구간 수, 누적수익률, MDD가 전부 다름)를 내는 걸
확인했습니다.

### Q13. 백테스트 결과 1,000개 전략이 전부 마이너스로 나왔는데, 버그 아닌가요?

이것도 실제로 의심하고 검증했던 부분입니다. 결과만 보면 "다 마이너스면 계산이 잘못된 거 아닌가"
싶었는데, 전체 종목의 실제 가격 데이터를 기준선으로 비교해봤습니다. 2021년 초부터 2023년 말까지
전체 종목의 평균 수익률은 +0.6%였는데 중앙값은 -21.8%였습니다. 즉 극소수 종목(최대 +1690%)이 평균을
끌어올렸을 뿐, 실제로는 절반 이상의 종목이 이 기간에 손실을 봤다는 뜻입니다. 2021~2023년이 실제로
한국 중소형주에게 어려운 시기였다는 게 데이터로 확인된 거고, 저PER/저PBR 스크리닝이 고르는 종목군이
이 하락장에서 특히 부진했을 가능성(밸류 트랩)까지 감안하면 결과 자체는 버그가 아니라 실제 시장을
반영한 것으로 판단했습니다. 표본으로 뽑은 종목 가격도 보간이나 액면분할 의심 플래그 없이 정상
데이터였다는 것까지 확인했습니다.

다만 2021년 초중반 표본이 2~9종목으로 매우 작다는 한계도 같이 발견했습니다. 원인은 12월 결산 회사의
"2021년 사업연도" 보고서가 2022년 3월에야 공시되는데, 저희는 2020년 사업보고서(FY2020)를 아예
수집하지 않아서 2021년 초중반엔 결산월이 다른 소수 회사(예: 2월 결산 회사)만 스크리닝 대상이 될 수
있었다는 걸 확인했습니다. 이건 앞으로 FY2020 이전 사업보고서를 추가 수집해야 해결되는 명확한 개선
과제로 남겨뒀습니다.

## 3. 말하면 좋은 포인트 (강조 포인트)

1. **"검증까지 했다"는 것을 반드시 강조**: 단순히 "Java 로직을 Spark로 옮겼다"가 아니라,
   실제로 로컬 DB에 데이터를 역주입하고 Java API를 호출해서 나온 값과 diff 비교까지 했다는 게
   신뢰도를 크게 높이는 지점입니다.
2. **버그를 발견하고 고친 경험은 구체적인 예시로 설명**: "분산 처리라 순서가 달라질 수 있다"는
   추상적인 말보다, `ifrs-full_Equity`가 BS/SCE에 중복 등장하는 구체적 사례와 `sj_div` 필터링으로
   해결한 과정을 그대로 설명하는 게 훨씬 설득력 있습니다.
3. **"왜 Spark인가"에 대한 답을 숫자로 준비**: "전략 500~2,000개 × 종목 2,500개 × 리밸런싱 시점"
   같은 곱셈 구조를 명확히 설명하고, 04번 완료 후 실제 워커 1대 vs 2대 처리시간 실측치를 준비해두면
   가장 강력한 답변이 됩니다.
4. **한계도 숨기지 않고 설명**: 환율 실시간 조회로 인한 계산 시점 의존성, 금융업 F-Score 미스킵,
   모멘텀 단일 기준일 등 알려진 한계를 스스로 문서화해뒀다는 것 자체가 엔지니어링 성숙도를 보여줍니다.
5. **원칙을 지킨 것도 성과로 포함**: 룩어헤드 바이어스 방지, 튜닝 전 실측 우선 원칙, 기존 프로덕션
   미변경 원칙처럼 "지키기 귀찮지만 중요한 원칙"을 실제로 지켰다는 것도 실무 역량으로 어필 가능합니다.
6. **룩어헤드 바이어스 실전 검증 사례가 가장 강력한 카드**: "방지 로직을 넣었다"는 말보다,
   실제로 그 로직이 2021/2022년의 오염된 재계산값(같은 rcept_no를 공유하는 3개년 비교치)을
   정확히 걸러낸 경험(Q6-1)이 훨씬 설득력 있습니다. "버그인 줄 알았는데 안전장치가 작동한 거였다"는
   서사는 이해도를 직접 보여주는 지점입니다.
7. **결과가 이상해 보일 때 바로 버그로 단정하지 않고 기준선(baseline)과 비교한 경험**: 1,000개
   전략이 전부 마이너스로 나왔을 때, 전체 종목의 실제 가격 데이터를 기준선으로 삼아 "이게 계산
   오류인지 실제 시장 현상인지"를 구분한 것(Q13)은 데이터 분석 역량을 보여주는 좋은 사례입니다.
8. **여러 번 재실행해야만 드러나는 버그를 잡은 경험**: 모멘텀 fan-out 버그(Q11)는 처음 79종목
   검증 때는 드러나지 않다가, 배치를 여러 날에 걸쳐 반복 실행하는 실제 운영 상황에서만 나타났습니다.
   "한 번 검증했다고 끝이 아니다"라는 인식을 보여주는 지점입니다.
