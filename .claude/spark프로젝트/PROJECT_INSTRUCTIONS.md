# valuepick-batch: Spark 기반 가치투자 백테스팅 파이프라인

## 0. 이 문서의 목적

이 프로젝트를 구현할 때 지켜야 할 **구조, 각 컴포넌트의 역할, Spark를 쓰는 이유**를 정의한다.
코드를 짜기 전에 이 문서 전체를 먼저 읽고, 각 잡(job)을 만들 때마다 해당 섹션의 "역할"과 "왜 Spark인가"를 코드 주석/커밋 메시지에 반영할 것.

**절대 원칙**: 이 프로젝트는 기존 `ValuePick`(Spring Boot 서비스, MySQL)의 프로덕션 코드·스케줄러·DB를 건드리지 않는다. API 호출 로직(엔드포인트, 인증, 파싱)만 참고/재사용하고, 저장 대상과 실행 파이프라인은 완전히 분리된 새 리포로 구성한다.

---

## 1. 프로젝트가 존재하는 이유 (배경)

- 원본 데이터: 전 종목(약 2,500개) × 10년 일봉(약 620만 행) + 재무제표. 이 크기 자체는 Spark 없이도 처리 가능한 수준이다.
- 이 프로젝트에서 Spark를 쓰는 진짜 이유는 **원본 데이터 크기가 아니라 "전략 파라미터 조합 × 전체 데이터"의 연산량**이다.
- 전략 조합(PER 상한 × PBR 상한 × 배당수익률 하한 × 리밸런싱 주기 × 보유 종목 수)을 500~2,000개 만들고, 각 조합마다 전체 종목 × 전체 기간에 대해 "이 규칙대로 투자했으면 수익률이 얼마였는가"를 재현(백테스트)한다.
- 결과적으로 원본 행 수(620만) × 조합 수(최소 500) = 수십억 단위 연산이 발생하며, 이 지점에서 단일 프로세스는 비효율적이고 분산 처리가 실익을 가진다.
- **면접 방어 논리**: "데이터가 작아서 Spark가 불필요하다"는 지적에 대해 "원본은 작지만 전략 그리드를 곱하는 순간 연산량이 폭증해서 분산 처리가 필요했다"는 것을 실측 수치(튜닝 전/후 처리시간)로 증명하는 것이 이 프로젝트의 핵심 산출물이다.

## 3. 인프라 구성

### 3.1 Docker Compose 구성 요소

| 컨테이너 | 역할 |
|---|---|
| `spark-master` | 클러스터 마스터 — 잡 스케줄링, 워커에게 태스크 분배 |
| `spark-worker-1`, `spark-worker-2` | 실제 연산 수행 노드 — 병렬 처리의 주체 |
| `jupyter` | 개발·검증용 대화형 환경 (PySpark 커널) |
| `mysql` | 최종 결과 서빙 전용 (원천 데이터 저장소 아님) |

**왜 워커 2대로 구성하는가**: 단일 워커 대비 워커 수를 늘렸을 때 백테스트 그리드 처리 시간이 어떻게 줄어드는지(스케일링 효율)를 실측하기 위함. 이 수치가 `PERFORMANCE.md`의 핵심 근거 자료가 된다.

### 3.2 저장 포맷 원칙

- 원천~중간 데이터: **Parquet**, `year=YYYY/month=MM` 파티셔닝
  - 이유: 컬럼형 저장이라 백테스트 시 필요한 컬럼(종가, PER 등)만 선택적으로 읽어 I/O를 줄일 수 있음. CSV 대비 압축률과 스캔 속도에서 우위.
- 최종 결과: MySQL (Spring Boot가 그대로 서빙할 수 있는 형태)
- **MySQL은 절대 중간 처리 데이터의 저장소로 쓰지 않는다.** Spark 잡 간 데이터 전달은 전부 Parquet로 한다.

## 4. 각 Job의 상세 역할 및 Spark 사용 이유

### 4.1 `01_ingest_raw.py` — 데이터 레이크 구축

**역할**: DART/KRX API 응답(JSON/CSV)을 원본 그대로 받아 Parquet로 변환하고 종목/연도 기준으로 파티셔닝한다.

**왜 Spark인가**: 이 단계 자체는 Spark가 필수는 아니다(단순 변환). 다만 이후 단계에서 파티션 단위로 효율적으로 읽으려면 이 단계에서부터 Spark DataFrame으로 다뤄 파티션 전략을 일관되게 가져가는 것이 유리하다.

**입력**: 기존 `DartCompanyCollector`, `StockPriceCollector`의 API 호출 로직을 그대로 가져오되, 응답을 MySQL upsert 대신 로컬 파일로 저장.

**출력**: `data/raw/prices/year=2016/`, `data/raw/financials/year=2016/` 등.

**리스크 및 대응**: DART API 일일 10,000콜 제한 → 최초 1회 backfill 후 재수집하지 않도록 스크립트에 "이미 받은 종목/기간 스킵" 로직 필수 포함.

---

### 4.2 `02_clean_prices.py` — 정제

**역할**: 결측치 보간, 액면분할 반영, 거래정지 구간 처리.

**왜 Spark인가**: 종목별로 독립적인 정제 작업이 2,500개 종목에 걸쳐 반복된다. `groupBy("stock_code")` 기반 처리로 종목 단위 병렬화가 자연스럽게 이루어짐.

**출력**: `data/cleaned/prices/`

---

### 4.3 `03_build_indicators.py` — 지표 계산

**역할**: PER, PBR, ROE, 배당수익률 등을 계산. `Window.partitionBy("stock_code").orderBy("date")`로 이동평균·전분기 대비 증감 계산.

**왜 Spark인가**: Window 함수 기반 시계열 연산은 Spark가 강점을 가지는 영역. 종목별 파티션 내에서 정렬·누적 계산이 병렬로 이루어짐.

**검증 필수 사항**: 기존 Spring Boot `FinancialIndicatorService`의 계산 로직과 **동일한 종목·동일한 시점**에 대해 결과값이 일치하는지 별도 검증 노트북(`notebooks/verify_indicators.ipynb`)으로 대조할 것. 불일치 시 신뢰도 문제이므로 반드시 원인 규명 후 진행.

**출력**: `data/indicators/`

---

### 4.4 `04_backtest_grid.py` — 백테스트 그리드 (프로젝트의 핵심)

**역할**: `conf/strategies.yaml`에 정의된 전략 파라미터 조합 각각에 대해, 전체 종목 × 전체 기간 데이터로 시뮬레이션을 수행하고 최종 수익률·MDD·샤프비율 등을 산출한다.

**전략 파라미터 예시 구조**:
```yaml
strategies:
  - name: "conservative_quarterly"
    per_max: 10
    pbr_max: 1.0
    dividend_yield_min: null
    rebalance: "quarterly"
    portfolio_size: 20
  - name: "dividend_focused_monthly"
    per_max: 15
    pbr_max: 1.2
    dividend_yield_min: 3.0
    rebalance: "monthly"
    portfolio_size: 30
  # ... 최소 500개 조합이 나오도록 파라미터 격자 생성
```

**핵심 처리 흐름**:
1. 전략 조합 리스트를 Spark DataFrame으로 변환 (`strategies_df`)
2. 종목/지표 DataFrame과 **crossJoin** (조합 × 종목 × 시점 전체 조합 생성)
3. 각 리밸런싱 시점마다 조건에 맞는 종목 필터링 → 포트폴리오 구성
4. 포트폴리오 수익률 계산 (다음 리밸런싱 시점까지 보유)
5. 전략별 누적 수익률, MDD, 샤프비율 집계

**왜 Spark인가 (이 프로젝트 전체에서 가장 중요한 설명)**:
- 원본 데이터(620만 행) 자체는 단일 노드로 처리 가능한 규모다.
- 하지만 이 단계에서는 **원본 데이터 × 전략 조합 수**가 곱해진다. 조합 500~2,000개 × 종목 2,500개 × 리밸런싱 시점(월간 기준 10년 = 120회)을 곱하면 수억~수십억 행 규모의 연산이 발생한다.
- 이 연산은 **조합 간에 서로 독립적**이므로 병렬화 효율이 매우 높다. 워커를 늘리면 처리 시간이 거의 선형으로 줄어드는 것을 기대할 수 있고, 이걸 실측하는 것이 이 프로젝트의 증명 대상이다.
- **룩어헤드 바이어스(look-ahead bias) 방지**: 리밸런싱 시점 t에서 사용하는 재무 지표는 반드시 **t 시점 이전에 실제로 공시된 값**이어야 한다. 재무제표 공시일(`report_date`)과 리밸런싱 시점을 비교해 조인 조건에 `report_date <= rebalance_date` 를 명시적으로 걸 것. 이 로직이 빠지면 미래 정보를 사용한 가짜 고수익이 나오므로, 백테스트 신뢰도의 핵심 검증 포인트로 취급한다.

**튜닝 대상 및 기록 방법**:
| 튜닝 항목 | 문제 상황 | 조치 |
|---|---|---|
| 브로드캐스트 조인 | 종목 마스터(2,500행)와 대형 시계열 조인 시 셔플 과다 발생 | `broadcast()` 힌트 적용 |
| 파티션 수 | 기본 파티션 수가 워커 코어 수와 불일치해 비효율 | 워커 총 코어 수 기준으로 `repartition()` |
| 캐싱 | 정제된 지표 DataFrame이 여러 전략에서 반복 참조됨 | `.cache()` 또는 `.persist()` 적용 |

**필수 작업**: 튜닝 적용 **전**의 최초 실행 시간을 반드시 먼저 측정하고 기록한 뒤 튜닝을 적용할 것. 전/후 비교 없이 튜닝만 하면 산출물로서 의미가 없다.

**출력**: `data/backtest_results/` (전략별 수익률 시계열 + 최종 성과 지표 요약)

---

### 4.5 `05_export_to_mysql.py` — 서빙

**역할**: 백테스트 결과 Parquet를 MySQL 서빙 테이블로 upsert.

**왜 Spark인가**: 이 단계는 Spark의 분산처리가 필수는 아니다. 다만 파이프라인 일관성을 위해 Spark JDBC writer로 처리한다.

**출력 대상**: Spring Boot가 그대로 읽을 수 있는 `backtest_results`, `strategy_performance` 테이블.

## 6. 구현 순서 (Claude Code 작업 시 이 순서를 따를 것)

1. `docker/docker-compose.yml` — Spark 클러스터(master + worker 2) + Jupyter + MySQL 구성
2. `jobs/01_ingest_raw.py` — 기존 ValuePick 수집 로직을 참고해 Parquet 저장 스크립트로 재작성 (MySQL 미경유)
3. `jobs/02_clean_prices.py`, `jobs/03_build_indicators.py`

6. `jobs/04_backtest_grid.py` — 튜닝 없는 최초 버전부터 작성 → 실행시간 기록 → 튜닝 적용 → 재기록
7. `jobs/05_export_to_mysql.py`
8. `docs/` 3종 문서 작성 (진행하면서 계속 갱신, 마지막에 몰아서 쓰지 않음)

## 7. 하지 말아야 할 것

- 기존 ValuePick의 Entity/DTO/스케줄러를 직접 수정하지 않는다.
- MySQL을 Spark 잡 간 중간 데이터 전달 용도로 쓰지 않는다.
- 백테스트에서 리밸런싱 시점 이후 공시된 재무 데이터를 사용하지 않는다 (룩어헤드 바이어스).
- 튜닝을 먼저 적용하고 "전" 수치를 나중에 추정해서 기록하지 않는다 — 반드시 실측 순서를 지킨다.
