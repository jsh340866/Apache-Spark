# valuepick-batch 04단계 구현 및 이상치 조사 (2026-07-30)

## 개요

`04_backtest_grid.py`(전략 그리드 백테스트, 프로젝트 핵심)를 실제로 구현하고 검증하는 과정에서
데이터 확장, 03번 심각한 버그 발견/수정, 실제 시장 데이터 기반 결과 해석, 인프라 안정화 작업을 진행했다.

## 1. 03_build_indicators.py 개선

### rcept_no 컬럼 추가
DART 접수번호(`rcept_no`, 앞 8자리가 실제 공시일 YYYYMMDD)를 03번 최종 출력에 포함.
04번 백테스트에서 룩어헤드 바이어스 방지(`rcept_no <= rebalance_date`)에 반드시 필요한 필드.
같은 연도가 여러 rcept_no에서 유래할 경우(당해 보고서 vs 다음해 보고서 전기 비교치) `F.min()`으로
가장 이른(보수적) 값을 채택.

### 심각한 fan-out 버그 발견 및 수정 (핵심 교훈)
04번을 처음 돌렸을 때 이상 동작이 발견되어 조사한 결과, 03번 지표 결과가 종목당 1행이 아니라
**최대 50행까지 중복**되어 있었음(2021년 기준 55,182행 vs 실제 종목수 2,368).

- **원인**: `join_momentum`이 `stock_code`만으로 조인하는데, `01_ingest_raw.py`를 여러 날에 걸쳐
  반복 실행하면서 `1m_ago`/`12m_ago` 가격 스냅샷이 종목당 여러 `bas_dt`로 계속 append됨
  (예: 1m_ago 5개 x 12m_ago 5개 = 25배 중복). 각 중복 행은 momentum 값만 다르고 나머지 지표는 동일.
- **해결**: `_latest_snapshot()` 헬퍼로 종목별 `bas_dt` 최신 1건만 사용.
- 배당 조인(`join_dividend_yield`)도 원본 DART 배당 API 응답 자체의 중복 행(값 있는 행과 공백 행이
  동시 존재) 문제가 있어 `F.first(ignorenulls=True)`로 값이 있는 행만 채택하도록 함께 수정.
- **교훈**: 79종목 초기 검증(2026-07-29) 당시엔 01번이 한 번만 실행된 상태라 이 문제가 드러나지
  않았다. **배치를 여러 번 재실행하는 실제 운영 환경에서만 나타나는 버그**였다는 점이 중요.

## 2. 데이터 범위 확장

- companies/prices: 2,555종목(KOSPI+KOSDAQ) 전체 확보
- financials/dividends: `--dart-limit` 없이 전체 2,555종목으로 재수집, **2020~2023 4개년** 각 연도
  자체의 실제 사업보고서를 개별 수집(연도별 `--year` 재실행)
- DART API 키 일일 호출 한도를 개발자센터에서 40,000건으로 상향 확인 후 진행
- 일별 시세: 2021(247거래일)/2022(245거래일)/2023(245거래일) 3개년 전체 확보

### 룩어헤드 바이어스 재확인: 재계산값은 백테스트에 쓸 수 없음
재무제표 API 응답 한 건에는 당기/전기/전전기 3개년 수치가 함께 들어있지만, 이 비교치들은 전부
**당해 보고서 하나의 rcept_no**를 공유한다. 즉 "2021년 자산총계"라는 숫자가 있어도, 그 값을
2023년 사업보고서에서 뽑아낸 것이라면 실제로는 2024년 3월에야 알 수 있었던 정보로 기록된다.
`rcept_no <= rebalance_date` 조건이 이 오염 사용을 정확히 차단했다(2021/2022 시점 스크리닝
결과가 0건으로 나온 게 버그가 아니라 안전장치가 정상 작동한 것). **해결책은 그 해 자체의
사업보고서를 실제로 재수집하는 것뿐**이며, 이번에 2020~2022년치를 각각 재수집해서 반영했다.

### FY2020 데이터 보강으로 2021년 초중반 표본 부족 문제 해결
12월 결산 회사는 "2021년 사업연도" 보고서를 2022년 3월에야 공시하므로, 2021년 초중반
리밸런싱 시점엔 FY2020(2020년 사업연도) 보고서가 있어야 스크리닝이 가능하다. FY2020을
추가 수집한 결과, 2021-01/02월 표본 25~33종목 → 2021-03월 이후 1,533~1,760종목으로
극적으로 개선됨을 실측 확인.

### DART API 특이 케이스 (실측 확인)
- 소형주/신규상장 종목: 여러 연도 전부 조회 실패 — 애초에 사업보고서가 없는 정상 케이스
- 금융업(예: 삼성화재): 특정 연도만 정상 응답, 나머지는 CFS/OFS 모두 데이터 없음 — 원인 미확정
- 대형 우량주(LG전자/SK하이닉스/현대차 등): 전 연도 정상 조회
- 일부 종목(예: 지누스)은 DART가 최신 **정정보고서**의 rcept_no를 반환 — 종목 부당 탈락 가능성은
  있으나 미래정보 누출보다는 안전한 방향

### 공공데이터포털 502/503 대응
429뿐 아니라 502/503(일시적 게이트웨이 장애)도 재시도하도록 `request_json_with_retry` 보강.
직후 재요청 시 정상 응답을 받아 횟수 제한이 아님을 확인.

## 3. 04_backtest_grid.py 구현

### 핵심 로직
- 재무제표는 연 1회만 확보되므로, "재무 기준은 그 시점 이전 가장 최근 공시된 사업보고서를 계속
  사용하되, 가격은 매월/매분기 재평가해서 포트폴리오를 재구성"하는 방식으로 monthly(36시점)/
  quarterly(12시점) 리밸런싱 주기를 실제로 구분 구현 (`latest_valid_indicators`가 시점마다
  종목별 최신 유효 rcept_no를 자동 판단)
- `--market KOSPI/KOSDAQ/ALL` 필터 옵션 추가 (`companies.corp_cls` 기준)
- 종목 선정: 조건(PER/PBR/배당수익률하한) 만족 종목 중 PER 낮은 순 상위 N종목, 동일비중 가정

### OutOfMemoryError 및 성능 이슈 해결
- for루프로 `unionByName`을 반복 호출하는 구조가 DataFrame 실행계획(lineage)을 시점 수(48개)만큼
  계속 이어붙여 드라이버 OOM 발생 → `.cache()` + `.count()`로 각 단계마다 즉시 실체화해 해결
- `--conf spark.driver.memory`는 클라이언트 모드에서 이미 시작된 SparkContext에 적용 안 됨을
  확인 — `spark-submit --driver-memory 3g`(CLI 전용 플래그)로 지정해야 실제 반영됨
- Spark는 모든 애플리케이션의 소요시간(`Duration`)을 마스터 UI(`localhost:8088`)에 자동 기록하므로,
  `time` 명령으로 별도 측정할 필요가 없음을 확인 (REST API `/api/v1/applications`로도 조회 가능)

### 워커 4대 스케일링 벤치마크 (미완료)
워커 3/4(각 1G)를 추가해 워커 2대 vs 4대 비교를 시도했으나:
- 호스트 메모리(7.7GB) 대비 워커 6GB + 드라이버 3GB 등 과다 할당으로 Docker Desktop/WSL2가
  응답 불가 상태에 빠짐 (2회 발생, Docker Desktop 재시작으로 복구)
- 정식 비교값 없이 작업 중단, 워커 3/4는 컨테이너 및 `docker-compose.yml` 정의 모두 제거,
  평소 체제(워커 1/2, 각 2코어/2GB)로 복귀
- **다음에 재시도할 때는 워커 메모리 총합 + 드라이버 메모리가 호스트 총 메모리를 넘지 않도록
  사전에 계산할 것**

## 4. 백테스트 결과 해석: 실제 시장 데이터 검증

### 1,000개 전략 전부 마이너스 — 버그 아닌 실제 시장 데이터
초기 결과(전체 시장, FY2020 보강 전)가 1,000개 전략 전부 음수(평균 -48%)로 나와 버그 의심 →
전체 종목 실제 가격 기준선과 대조. 2021~2023 전체 종목 평균 수익률 +0.6%, **중앙값 -21.8%**
(소수 극단적 급등주가 평균을 끌어올릴 뿐, 실제로는 절반 이상 종목이 손실). 저PER/저PBR
스크리닝이 고르는 소형·저유동성 종목군이 이 하락장에서 특히 부진했을 가능성(밸류 트랩).

KOSPI 필터 + FY2020 보강 버전에서는 최고 성과 전략이 **+72.6%**까지 나와, 시장/데이터 범위에
따라 결과가 크게 달라짐을 확인.

### 종목 101140 급등 이상치 발견
`per8_pbr1.2_dynone_monthly_n10` 전략의 2023-09-30~10-31 구간 누적수익률이 갑자기 +179%로
튄 원인을 추적한 결과, 종목 `101140`이 그 구간에 **467원 → 9,340원(+1,900%, 약 20배)** 급등한
것이 원인. 10종목 동일비중 포트폴리오에서 종목 하나가 10% 비중을 차지하므로,
`1900%/10 = +190%p`가 나머지 9종목의 손실(`-109.8%/10 = -10.98%p`)을 뒤엎어버림 — 계산 자체는
정확했음(179.02% ≈ 실측 179.03%). 다만 이 종목의 `split_suspected` 플래그가 매수/매도 시점
자체엔 `False`로 찍혀 있어, 액면분할/병합 의심 탐지가 이 케이스를 놓쳤을 가능성이 있음
(정확한 발생 일자는 조사 중 인프라 이슈로 중단, 다음 세션에서 이어갈 것).

## 6. 인프라 이슈 및 대응

- Docker Desktop이 리소스 압박(메모리 부족)으로 2회 응답 불가 상태에 빠짐 → 프로세스 재시작으로 복구
- 재시작 후 컨테이너는 정지 상태로 남아있을 뿐 삭제되지 않음(`docker stop` ≠ `docker rm`) — 정상
- 컨테이너 상태를 바꾸기 전에는 반드시 `docker inspect <container> --format '{{json .Mounts}}'`로
  실제 마운트 경로가 `Apache-Spark\valuepick-batch`인지 재확인하는 습관을 유지 중 (이전 세션의
  마운트 혼동 사고 재발 방지)
- Jupyter 컨테이너에서 `pyspark`를 쓰려면 `PYTHONPATH=/usr/local/spark/python/lib/py4j-*.zip:/usr/local/spark/python`
  환경변수가 필요함을 확인. 이 값은 Jupyter 서버가 커널을 띄울 때만 주입되고, `docker exec`로
  새 프로세스를 띄우면 안 잡혀 있어 별도로 `-e PYTHONPATH=...`를 지정해야 함
  (`docker exec ... jupyter nbconvert`로 노트북을 헤드리스 실행/디버깅할 때 필요)
