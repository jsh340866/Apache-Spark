## 1. 에이전트 팀이란?

**여러 Claude Code 인스턴스가 함께 협력하는 시스템.**

- 메인 세션이 **팀 리더**가 되어 작업을 조율하고 팀원들을 관리
- 각 팀원은 **독립적인 Claude Code 세션**으로 자신의 컨텍스트 윈도우에서 실행
- 팀원들이 **리더를 거치지 않고 서로 직접 메시지** 전송 가능
- 공유 작업 목록(Task List)을 통해 자율적으로 작업 조율

> **핵심 차이**: Subagents는 메인 에이전트에게만 보고하지만,  
> 에이전트 팀은 팀원들이 서로 직접 소통하며 독립적으로 작동한다.

## 2. 언제 사용해야 하나?

### 적합한 경우 ✅

| 상황 | 예시 |
|------|------|
| **병렬 연구/검토** | 보안·성능·테스트 커버리지를 각각 다른 팀원이 동시에 검토 |
| **새로운 모듈/기능 개발** | 프론트엔드·백엔드·테스트를 팀원들이 각각 소유 |
| **디버깅 (경쟁 가설)** | 여러 이론을 병렬로 테스트해서 빠르게 근본 원인 수렴 |
| **교차 계층 조율** | 여러 레이어에 걸친 변경사항을 각 팀원이 담당 |

### 적합하지 않은 경우 ❌

- **순차적 작업**: 단계가 서로 의존하는 경우
- **동일 파일 편집**: 여러 팀원이 같은 파일을 수정하면 덮어쓰기 발생
- **종속성 많은 작업**: 단일 세션이나 Subagents가 더 효율적
- **단순 일상 작업**: 조율 오버헤드와 토큰 비용이 이점을 초과

## 3. Subagents와 차이점

```
Subagents:
  메인 에이전트 → Worker1 (결과 반환)
               → Worker2 (결과 반환)
               → Worker3 (결과 반환)

에이전트 팀:
  리더 ↔ 팀원1 ↔ 팀원2 ↔ 팀원3
       (공유 작업 목록으로 자율 조율)
```

| 항목 | Subagents | 에이전트 팀 |
|------|-----------|------------|
| **컨텍스트** | 결과만 호출자에게 반환 | 완전히 독립적 |
| **통신** | 메인 에이전트에게만 보고 | 팀원끼리 직접 메시지 |
| **조율** | 메인 에이전트가 모든 작업 관리 | 공유 작업 목록으로 자체 조율 |
| **최적 용도** | 결과만 중요한 집중된 작업 | 논의와 협업이 필요한 복잡한 작업 |
| **토큰 비용** | 낮음 | 높음 (각 팀원 = 별도 Claude 인스턴스) |

**선택 기준**: 팀원들이 서로 소통하며 협업해야 하면 → 에이전트 팀  
발견 사항만 리더에게 보고하면 충분하면 → Subagents

## 4. 활성화 방법

에이전트 팀은 기본적으로 **비활성화** 상태다.

### 방법 1: settings.json (프로젝트 수준 권장)

`.claude/settings.json` 파일에 추가:

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

### 방법 2: 글로벌 설정

`~/.claude/settings.json`에 동일하게 추가.

### 방법 3: 셸 환경변수

```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
```

> 이 프로젝트는 이미 `.claude/settings.json`에 활성화 설정이 되어 있음.

## 5. 첫 번째 에이전트 팀 시작하기

활성화 후, 자연어로 원하는 작업과 팀원 역할을 설명한다.

### 기본 예시

```text
CLI 도구를 설계하는데 세 명의 팀원을 배치해줘:
- UX 관점으로 분석하는 팀원
- 기술 아키텍처 관점으로 분석하는 팀원
- 반론을 제시하는 악마의 변호사 역할 팀원
```

Claude가 자동으로:
1. 공유 작업 목록(Task List) 생성
2. 각 팀원 인스턴스 생성
3. 작업 배분 및 조율
4. 결과 종합

### 팀원 패널 조작 (In-process 모드)

| 키 | 동작 |
|----|------|
| `↑` `↓` | 팀원 선택 |
| `Enter` | 선택된 팀원의 대화 열고 직접 메시지 전송 |
| `Escape` | 선택된 팀원의 현재 턴 중단 |
| `x` | 팀원 중지 |
| `Ctrl+T` | 작업 목록 토글 |

## 6. 팀 제어 방법

### 6-1. 표시 모드 선택

| 모드 | 설명 | 요구사항 |
|------|------|----------|
| `in-process` (기본값) | 메인 터미널 내 에이전트 패널 | 없음 |
| `auto` | tmux/iTerm2 있으면 분할 창, 없으면 in-process | tmux 또는 iTerm2 |
| `tmux` | 분할 창 (자동 감지) | tmux 또는 iTerm2 |
| `iterm2` | iTerm2 네이티브 분할 창 | `it2` CLI + Python API 활성화 |

`~/.claude/settings.json`에서 기본값 설정:

```json
{
  "teammateMode": "auto"
}
```

단일 세션에만 적용:

```bash
claude --teammate-mode auto
```

### 6-2. 팀원 수와 모델 지정

```text
4명의 팀원을 배치하여 이 모듈들을 병렬로 리팩토링해줘.
각 팀원은 Sonnet을 사용하도록 해줘.
```

- 팀원들은 기본적으로 리더의 모델을 상속하지 않음
- `/config`에서 **기본 팀원 모델** 설정 가능
- 팀원들은 리더의 **노력 수준(effort level)** 을 상속함 (v2.1.186+)

### 6-3. 계획 승인 요구

위험한 작업에서 팀원이 구현 전에 계획을 제출하도록 강제:

```text
인증 모듈을 리팩토링할 아키텍트 팀원을 배치해줘.
변경사항을 만들기 전에 반드시 계획 승인을 받도록 해줘.
```

흐름:
1. 팀원이 읽기 전용 계획 모드에서 계획 작성
2. 리더에게 승인 요청 전송
3. 리더가 승인 또는 피드백과 함께 거부
4. 승인 후 팀원이 구현 시작

### 6-4. 팀원에게 직접 메시지 보내기

- **In-process 모드**: 에이전트 패널 → 팀원 선택 → `Enter` → 메시지 입력
- **분할 창 모드**: 팀원의 창을 클릭 후 직접 입력

### 6-5. 팀원 종료

```text
researcher 팀원에게 종료하도록 요청해줘
```

팀원이 우아하게 종료하거나 이유와 함께 거부 가능.  
세션 종료 시 팀 공유 디렉토리는 **자동 정리**됨.

### 6-6. Hooks로 품질 게이트 설정

| Hook | 트리거 시점 | 활용 |
|------|------------|------|
| `TeammateIdle` | 팀원이 유휴 상태가 될 때 | 종료 코드 2로 피드백 보내 계속 작동 |
| `TaskCreated` | 작업이 생성될 때 | 종료 코드 2로 생성 방지 |
| `TaskCompleted` | 작업이 완료될 때 | 종료 코드 2로 완료 방지 |

## 7. 아키텍처 & 내부 동작

### 구성 요소

| 구성 요소 | 역할 |
|-----------|------|
| **팀 리더** | 팀원 생성 및 작업 조율하는 메인 세션 |
| **팀원들** | 각자 독립적으로 작동하는 Claude Code 인스턴스 |
| **작업 목록** | 팀원들이 요청하고 완료하는 공유 작업 항목 |
| **메일박스** | 에이전트 간 메시지 시스템 |

### 저장 위치

```
~/.claude/teams/{session-id의 앞 8자}/config.json   ← 팀 구성 (세션 종료 시 삭제)
~/.claude/tasks/{session-id의 앞 8자}/             ← 작업 목록 (재개 세션을 위해 유지)
```

- 팀 이름 형식: `session-` + 세션 ID 앞 8자
- 팀 구성 파일은 **수동 편집 금지** (런타임 상태 포함, 다음 업데이트 시 덮어씌워짐)
- 작업 목록은 로컬에만 유지되며 절대 업로드되지 않음

### 팀원이 생성되는 방법

1. **직접 요청**: "팀원을 배치해줘" 라고 명시적으로 요청
2. **Claude가 제안**: Claude가 병렬 작업이 유리하다고 판단 시 제안  
   → 항상 사용자 확인 후 생성 (자동으로 생성하지 않음)

### 작업(Task) 상태

```
대기 중 → 진행 중 → 완료됨
```

- 미해결 종속성이 있는 대기 중 작업은 종속성 완료 전까지 요청 불가
- 파일 잠금으로 경합 조건 방지

### 컨텍스트 공유 방식

팀원들은 다음을 자동으로 로드:
- CLAUDE.md
- MCP servers
- Skills
- 리더의 생성 프롬프트

팀원들이 받지 않는 것:
- 리더의 **대화 기록**

정보 공유 메커니즘:
- **자동 메시지 전달**: 보낸 메시지가 수신자에게 자동 전달
- **유휴 알림**: 팀원 완료 시 리더에게 자동 통보
- **공유 작업 목록**: 모든 에이전트가 작업 상태 확인 및 요청 가능
- **팀원 메시징**: 이름으로 특정 팀원에게 직접 메시지

### 권한

- 팀원은 **리더의 권한 설정**으로 시작
- 리더가 `--dangerously-skip-permissions`로 실행 시 모든 팀원도 동일
- 생성 후 개별 팀원 모드 변경 가능 (생성 시에는 팀원별 모드 설정 불가)

## 8. 실전 사용 예시

### 예시 1: 병렬 코드 검토

```text
PR #142를 검토하기 위해 세 명의 팀원을 배치합니다:
- 보안 영향에 중점을 두는 팀원
- 성능 영향을 확인하는 팀원
- 테스트 커버리지를 검증하는 팀원
각각 검토하고 발견 사항을 보고하도록 합니다.
```

### 예시 2: 경쟁 가설로 버그 조사

```text
사용자들이 앱이 연결 상태를 유지하는 대신 한 메시지 후에 종료된다고 보고합니다.
5명의 에이전트 팀원을 배치하여 다양한 가설을 조사하도록 합니다.
서로 대화하여 서로의 이론을 반박하도록 합니다.
발견 사항 문서를 합의 내용으로 업데이트합니다.
```

### 예시 3: 모듈 병렬 개발 (이 프로젝트 적용 예시)

```text
valuepick 프로젝트에서 새로운 기능을 개발하기 위해 팀원을 배치해줘:
- 백엔드 API 담당 팀원: DartFinancialCollector 수정
- 스케줄러 담당 팀원: FinancialScheduler 업데이트
- 테스트 담당 팀원: CollectorTest 작성
각 팀원이 서로 다른 파일을 담당하도록 해줘.
```

### 예시 4: 팀원에게 충분한 컨텍스트 제공

```text
src/auth/ 인증 모듈을 보안 취약점 관점에서 검토할 팀원을 배치해줘.
프롬프트: "src/auth/ 디렉토리의 인증 모듈을 보안 취약점 관점에서 검토하세요.
토큰 처리, 세션 관리, 입력 유효성 검사에 집중하세요.
앱은 httpOnly 쿠키에 저장된 JWT 토큰을 사용합니다.
심각도 등급과 함께 문제를 보고하세요."
```

## 9. 모범 사례

### 팀 크기

- 대부분의 워크플로우: **3~5명** 시작 권장
- 팀원당 **5~6개 작업** 유지 (과도한 컨텍스트 전환 방지)
- 15개 독립 작업 → 팀원 3명이 적당

### 작업 크기

| 크기 | 문제 |
|------|------|
| 너무 작음 | 조율 오버헤드 > 이점 |
| 너무 큼 | 낭비된 노력 위험 증가 |
| 적당함 | 함수, 테스트 파일, 검토 단위의 자체 포함 작업 |

### 파일 충돌 방지

**두 팀원이 같은 파일을 편집하면 덮어쓰기 발생!**  
각 팀원이 서로 다른 파일 집합을 소유하도록 작업을 분할할 것.

### 팀원들이 완료될 때까지 기다리기

```text
팀원들이 작업을 완료할 때까지 기다린 후 진행해줘
```

리더가 팀원들을 기다리지 않고 혼자 작업하기 시작하면 이 명령을 사용.

### 처음에는 연구·검토 작업으로 시작

코드 작성이 필요 없는 작업(PR 검토, 라이브러리 조사, 버그 조사)으로 먼저 에이전트 팀을 경험하면 조율 문제 없이 병렬 탐색의 가치를 확인할 수 있음.

### 모니터링 필수

팀을 너무 오래 무인으로 실행하면 낭비된 노력 위험 증가.  
진행 상황을 확인하고, 막힌 부분을 재지정하고, 발견을 종합할 것.

### 재사용 가능한 팀원 역할 정의

`.claude/agents/` 폴더에 Subagent 정의 파일을 만들어두면,  
에이전트 팀원으로도 재사용 가능:

```text
security-reviewer 에이전트 타입을 사용하는 팀원을 배치하여 auth 모듈을 감사해줘.
```

> **주의**: Subagent 정의의 `skills`와 `mcpServers` frontmatter는  
> 팀원으로 실행될 때 적용되지 않음.

## 10. 문제 해결

### 팀원이 나타나지 않음

1. 에이전트 패널 확인 (↑↓ 키로 선택, Enter 입력)
2. 숨겨진 팀원 확인: 유휴 행은 30초 후 숨겨짐 → 이름으로 메시지 보내면 재표시
3. 작업이 팀이 필요할 만큼 복잡한지 확인
4. 분할 창 요청 시 tmux 설치 여부 확인: `which tmux`

### 권한 프롬프트가 너무 많음

팀원 생성 전 [권한 설정]에서 일반적인 작업을 사전 승인하여 중단 줄이기.

### 팀원이 오류 후 중지됨

In-process 모드: 에이전트 패널 → 팀원 선택 → `Enter` → 출력 확인  
→ 직접 추가 지시 제공 또는 대체 팀원 생성

### 리더가 작업 완료 전에 종료됨

```text
계속해줘 / 팀원들이 완료될 때까지 기다린 후 진행해줘
```

### 고아 tmux 세션 정리

```bash
tmux ls
tmux kill-session -t <session-name>
```

## 11. 제한 사항

| 제한 | 내용 |
|------|------|
| **세션 재개 불가** | `/resume`과 `/rewind`는 in-process 팀원을 복원하지 않음 |
| **작업 상태 지연** | 팀원이 작업을 완료로 표시하지 못해 종속 작업 차단 가능 |
| **종료 지연** | 현재 요청/도구 호출 완료 후 종료되어 시간 걸릴 수 있음 |
| **세션당 한 팀** | 추가 팀 생성 또는 세션 간 팀 공유 불가 |
| **중첩된 팀 없음** | 팀원은 자신의 팀원을 생성할 수 없음 |
| **리더 고정** | 팀원을 리더로 승격하거나 리더십 이전 불가 |
| **생성 시 권한 고정** | 생성 시 팀원별 개별 권한 모드 설정 불가 |
| **분할 창 제한** | VS Code 통합 터미널, Windows Terminal, Ghostty에서 분할 창 미지원 |
