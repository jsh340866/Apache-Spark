# ValuePick 프로젝트 면접 설명

---

## 프로젝트 한 줄 소개

국내 상장 주식 중 저평가 우량주를 자동으로 선별해주는 투자 보조 서비스입니다.
KRX와 DART의 공공 API를 연동해 재무 데이터를 수집하고, 지표를 계산해 매일 TOP 100 종목을 제공합니다.

---

## 제가 구현한 핵심 작업

### 1. 외부 API 연동 — 데이터 수집 파이프라인 구축

**무엇을 했나:**
KRX 상장종목 API, DART 전자공시 API, 한국수출입은행 환율 API 세 가지를 연동해서 기업 정보 → 재무제표 → 환율 순서로 수집하는 파이프라인을 만들었습니다.

**기술적 선택:**
- KRX API로 현재 상장 종목 목록을 가져오고, DART `corpCode.xml`(ZIP 파일)에서 종목코드 → 법인코드 매핑을 추출합니다. 두 데이터를 조인해야 재무 데이터 조회가 가능한 구조입니다.
- DART API 응답이 XML ZIP 형태로 오기 때문에 `ZipInputStream`으로 압축을 풀고 DOM 파싱으로 처리했습니다.

---

### 2. 상장 종목 필터링 — 법적 명칭 규칙 활용

**문제:**
KOSPI/KOSDAQ에는 일반 기업 외에 스팩(SPAC), 리츠(REIT) 같은 투자 수단 종목이 섞여 있는데, 이런 종목은 PER/PBR 지표가 의미 없어서 분석 대상에서 제외해야 합니다.

KRX API에는 종목 유형을 구분하는 필드가 없어서 이름 기반 필터링이 불가피했습니다.

**초기 접근과 문제점:**
처음에는 `contains("리츠")`로 필터링했는데, "메리츠금융지주", "블리츠웨이엔터테인먼트" 같이 이름에 "리츠"가 우연히 포함된 일반 기업도 걸렸습니다. 이를 막기 위해 화이트리스트를 하드코딩으로 관리했는데, 신규 상장 기업이 생길 때마다 코드를 수정해야 하는 구조적 문제가 있었습니다.

**개선:**
금융 법령을 확인한 결과, 법적으로 명칭에 제약이 있다는 점을 발견했습니다.
- 부동산투자회사법: 리츠는 상호 **끝**에 "리츠" 표기 의무
- 자본시장법: 스팩은 상호에 "스팩" 또는 "기업인수목적" 포함 의무

따라서 리츠만 `contains` → `endsWith`로 바꾸면 화이트리스트 없이 정확하게 구분됩니다.

```java
private boolean isExcludedStock(String corpName) {
    return corpName.endsWith("리츠")
            || corpName.contains("스팩")
            || corpName.contains("기업인수목적");
}
```

"메리츠금융지주"는 끝이 "금융지주"이므로 통과, "NH프라임리츠"는 끝이 "리츠"이므로 제외됩니다.
화이트리스트와 EXCLUDE_KEYWORDS 상수를 모두 제거하고 로직 하나로 정리했습니다.

### 3. 상장폐지 종목 처리 — Cascade 삭제 설계

**문제:**
매일 스케줄러가 실행될 때 상장폐지된 종목을 DB에서 제거해야 하는데, Company 테이블에 연결된 자식 테이블(재무제표, 주가, 투자지표 등)이 6개입니다. 외래키 제약 조건 때문에 Company를 바로 삭제하면 에러가 납니다.

**접근 방식:**
JPA의 `CascadeType.ALL` + `orphanRemoval = true`를 Company 엔티티의 연관관계에 설정해서, `companyRepository.deleteAllById()`만 호출하면 6개 자식 테이블 데이터가 자동으로 함께 삭제되도록 했습니다.

삭제 대상 종목은 "DB에 있는 종목코드 전체 - KRX 현재 상장 목록 = 상장폐지 종목"으로 판단합니다. 엔티티 전체를 로딩하는 대신 `stockCode`만 조회하는 커스텀 쿼리(`findAllIds()`)를 사용해 메모리 효율을 높였습니다.

### 4. 재무제표 처리 — CFS/OFS 선택 로직

**배경:**
DART 재무제표는 연결재무제표(CFS)와 별도재무제표(OFS) 두 가지가 있습니다. 자회사가 있는 기업은 CFS를, 소규모 기업은 OFS만 제공합니다. 투자 분석에서는 CFS가 기업 전체 실적을 반영하므로 CFS 우선, 없으면 OFS를 사용합니다.

**구현 포인트:**
- DART API가 동일 계정명을 중복으로 보내는 경우가 있어서(정정 공시 포함), 먼저 나온 값을 우선하도록 `containsKey` 체크를 추가했습니다.
- CFS를 사용할지 OFS를 사용할지 결정된 후에, 결정된 쪽을 `primary`로 나머지를 `fallback`으로 두는 구조로 리팩토링했습니다. 기존 코드는 항상 CFS를 먼저 시도하도록 하드코딩되어 있어 OFS가 primary인 경우를 처리하지 못했습니다.

### 5. 다통화 환율 변환

**문제:**
DART 재무제표는 KRW 외에 USD, JPY, CNY 등으로 기재된 기업이 있습니다. PER/PBR 계산 시 주가(KRW)와 재무 수치의 단위를 맞춰야 합니다.

**구현:**
한국수출입은행 API에서 환율을 수집해두고, 재무 지표 계산 시 통화에 따라 KRW로 환산합니다. 주의한 점은 JPY와 IDR는 수출입은행이 100단위(`JPY(100)`)로 제공하기 때문에 1단위 환율로 변환하는 보정 로직을 추가했습니다.

환율 조회 실패 시에는 잘못된 값으로 계산하는 것보다 해당 기업을 스킵하는 게 낫다고 판단해서 예외를 던지고 상위에서 로그만 남기도록 했습니다.

### 6. TOP 100 스코어링 시스템 — 백분위 정규화

**방식:**
PER, PBR, ROE, 부채비율 4개 지표를 각각 **0~25점 백분위 정규화** 후 합산해서 100점 만점 점수를 산출합니다.

단순 수치를 비교하면 PER 10과 ROE 15%처럼 단위가 다른 지표를 더할 수 없습니다. 전체 종목 중 몇 번째 순위인지로 변환하면 모든 지표를 동일한 기준으로 합산할 수 있습니다.

```
점수 = (n - 1 - rank) / (n - 1) × 25
```
예: 1000개 종목 중 PER이 가장 낮은 종목 → rank=0 → 25점

완전자본잠식(자본 ≤ 0)이나 적자 기업은 지표 계산이 무의미하므로 `null`로 저장하고 스코어링 대상에서 제외합니다.

### 7. 비동기 처리 및 스케줄링

종목이 2,500개 이상이기 때문에 순차 처리 시 수집 시간이 과도하게 길어집니다. `@Async`와 커스텀 스레드풀(`dartExecutor`, `stockExecutor`)을 사용해 기업별 API 호출을 병렬로 처리했습니다.

스케줄러는 분기별(1분기/반기/3분기/연간) 재무 수집과 매일 주가 수집 + TOP 100 재계산으로 구성됩니다. 재무 수집(01:00) → 지표 계산(03:00) 순으로 2시간 간격을 두어 수집이 완료된 후 계산이 실행되도록 했습니다.

### 8. 주가 수집 API 호출 수 최적화 — 2,700번 → 1번

**문제:**
공공데이터포털 주가 API를 종목별로 개별 호출하는 구조였습니다. 국내 상장사가 약 2,700개이므로 하루 2,700번 API를 호출해야 했고, 일일 호출 한도를 초과해 `"API token quota exceeded"` 에러가 발생했습니다.

**원인 분석:**
처음에는 API 방식 자체가 틀렸다고 생각했지만, 공식 파라미터 문서를 다시 확인했더니 종목코드 필터(`likeSrtnCd`)가 선택 파라미터였습니다. 즉 날짜(`basDt`)만 넘기고 `numOfRows=4000`으로 설정하면 해당일 전 종목 데이터를 한 번에 받을 수 있는 구조였습니다.

**해결:**
- 종목별 루프를 제거하고 날짜당 1번 호출로 전면 전환
- XML 응답 → JSON 응답으로 교체 (`resultType=json`)
- XML 파싱 전용 클래스(`StockPriceXmlParser`) 삭제, 기존 프로젝트의 JSON 파싱 패턴 재사용

결과적으로 하루 API 호출 수가 **2,700번 → 1번**으로 줄었고, 파서 코드도 단순해졌습니다.

```java
// 변경 전: 종목당 1번 호출
for (Company company : companies) {
    requestApi(company.getStockCode(), date); // 2,700번 반복
}

// 변경 후: 날짜당 1번 호출
// numOfRows=4000, basDt=date, likeSrtnCd 제거 → 전 종목 한 번에 수신
requestAllByDate(date);
```

### 9. 재무제표 API 확장 — 계정명 대신 표준 코드로 매칭하도록 전환

**배경:**
멀티팩터 스코어링(F-Score, ROA, 모멘텀)을 추가하면서 영업활동현금흐름·유동자산·유동부채·매출총이익 데이터가 필요해졌는데, 기존에 쓰던 DART `fnlttMultiAcnt.json`(다중회사 계정과목) API는 비교 편의를 위해 표준화된 "주요계정" 14개만 요약해서 주는 API라 현금흐름표 항목 자체가 없었습니다.

**API 조사 및 검증:**
DART의 다른 엔드포인트 `fnlttSinglAcntAll.json`(단일회사 전체 재무제표)을 실제로 호출해서, 이 API가 재무상태표·손익계산서뿐 아니라 현금흐름표·자본변동표까지 포함한 전체 공시 내용을 준다는 걸 확인했습니다. 다만 이 API는 `fs_div`(연결/별도)를 요청 시점에 미리 지정해야 해서, 회사당 CFS로 먼저 호출 → 응답이 비어있으면(실제로 호출해서 `status="013"` 응답을 확인) OFS로 재호출하는 구조로 설계했습니다. 자회사가 있어 CFS를 내는 회사는 호출 1번으로 끝나고, 없는 회사만 2번 호출됩니다.

**버그 발견:**
API 전환 후 테스트 데이터를 DB로 확인했더니 영업이익·매출총이익·영업현금흐름 컬럼에 0값이 예상보다 훨씬 많이 나왔습니다. 원인을 파보니 DART의 `account_nm`(계정명)은 회사가 재무제표에 실제로 표기한 한글 텍스트 그대로라서, 같은 개념도 회사마다 표기가 달랐습니다.

- 영업이익: "영업이익" / "영업이익(손실)" (적자 기업은 계정명 자체에 손실 표기)
- 매출액: "매출액" / "영업수익" / "수익(매출액)"
- 영업현금흐름: "영업활동현금흐름" / "영업활동으로 인한 현금흐름"

코드가 특정 문자열(`"영업이익"` 등)만 정확히 매칭하도록 짜여 있어서, 표기가 다른 회사는 값을 못 찾고 0으로 기본 처리됐던 겁니다.

**해결:**
API 응답을 다시 뜯어보니 `account_id`라는 필드가 있었고, 이건 IFRS/DART가 정한 표준 계정 코드라서 회사가 뭐라고 표기하든 항상 동일했습니다 (예: "매출액"이든 "영업수익"이든 `account_id`는 항상 `ifrs-full_Revenue`). 매칭 기준을 자유 텍스트(`account_nm`)에서 표준 코드(`account_id`)로 바꾸는 것으로 근본 해결했습니다.

```java
// 변경 전: 계정명(자유 텍스트) 매칭 - 회사마다 표기가 달라 값을 놓침
if (!curr.containsKey(item.getAccountNm())) ...
operatingIncome(pick(map, "영업이익"))  // "영업이익(손실)"인 회사는 매칭 실패 → 0

// 변경 후: 표준 코드(account_id) 매칭 - 표기와 무관하게 항상 매칭
if (!curr.containsKey(item.getAccountId())) ...
operatingIncome(pick(map, "dart_OperatingIncomeLoss"))  // 표기와 무관하게 항상 매칭
```

**교훈:**
겉보기엔 "데이터가 이상하다"는 증상이었지만, 실제로 DART API를 직접 호출해서 응답 구조를 하나씩 비교해보지 않았다면 "그냥 재무제표가 없는 회사겠거니" 하고 넘어갔을 수 있는 문제였습니다. 외부 API 스펙은 문서나 추측이 아니라 실제 호출 결과로 검증해야 한다는 걸 다시 확인한 케이스입니다.
