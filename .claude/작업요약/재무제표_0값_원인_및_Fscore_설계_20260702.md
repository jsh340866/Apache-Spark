# 재무제표 0값 원인 분석 및 F-Score 설계 — 2026-07-02

---

## 1. financial_statement 0값 원인 분석

### 배경

2단계(ROA·모멘텀·F-Score) 작업 중 DART 재무제표 API를 `fnlttMultiAcnt.json`(다중회사 계정과목) → `fnlttSinglAcntAll.json`(단일회사 전체 재무제표)로 교체했다. 교체 직후 테스트 데이터에서 `operating_income`, `revenue`, `gross_profit` 등에 0값이 예상보다 많이 나와서 원인을 추적했다.

### 1차 원인 — 계정명(account_nm) 자유 표기

DART의 `account_nm`(계정명)은 회사가 재무제표에 실제로 표기한 한글 텍스트 그대로라서, 같은 개념도 회사마다 표기가 달랐다.

| 개념 | 표기 예시 |
|---|---|
| 매출액 | "매출액" / "영업수익" / "수익(매출액)" |
| 영업이익 | "영업이익" / "영업이익(손실)" |
| 영업현금흐름 | "영업활동현금흐름" / "영업활동으로 인한 현금흐름" |
| 매출총이익 | "매출총이익" / "매출총이익(손실)" |

코드가 특정 문자열만 정확히 매칭하도록 짜여 있어서, 표기가 다른 회사는 값을 못 찾고 0으로 기본 처리됐다.

### 2차 원인 — 업종에 따라 표준 코드 자체가 다름

DART API 응답에는 `account_id`(IFRS/DART 표준 계정 코드)가 있고, 이건 회사가 뭐라고 표기하든 항상 동일하다는 걸 확인했다. 계정명 텍스트 대신 이 표준 코드로 매칭하도록 바꿨다.

다만 매출액·영업이익은 업종에 따라 쓰는 **표준 코드 자체가 다름**을 추가로 확인했다.

| 개념 | 일반 제조업 | 증권·보험사 |
|---|---|---|
| 매출액 | `ifrs-full_Revenue` | `ifrs-full_InsuranceRevenue`(보험) 등 |
| 영업이익 | `dart_OperatingIncomeLoss` | `ifrs-full_ProfitLossFromOperatingActivities` |

→ 두 후보 코드를 모두 확인하도록 수정 (`ACC_REVENUE`, `ACC_OPERATING_INCOME`을 리스트로 변경).

### 3차 원인 — DART 태깅 자체가 누락된 케이스

일부 회사는 계정 자체에 표준 코드를 아예 안 써서 `account_id`에 `"-표준계정코드 미사용-"`이라는 문자열이 그대로 찍혀 있었다 (예: DH오토넥스(000300)의 "매출액" 계정 — 실제 매출 400억원대가 있는데도 태깅이 안 되어 있었음).

→ `account_id`를 1순위로, 매칭 실패 시 `account_nm` 텍스트 매칭(1차 원인에서 썼던 별칭 목록)을 2순위 안전망으로 두는 구조로 최종 변경. 새 API 호출 없이 이미 받은 응답 안에서 두 가지 방식으로 인덱싱만 추가하는 것이라 API 호출량 증가는 없음.

### 최종적으로 남은 0값 — 전부 정상값 (버그 아님)

DB에서 업종별로 재검증한 결과, 남은 0값은 아래 두 가지 구조적 이유뿐이었다.

**(A) 금융업(은행·보험·증권) — 유동자산/유동부채, 매출총이익, 매출액 일부**
- 금융업은 재무상태표를 유동성배열법으로 작성해서 유동/비유동 구분 자체를 안 함 → `current_assets`/`current_liabilities` 0
- 매출원가라는 개념 자체가 없음(사업모델이 "상품 판매"가 아니라 "자금 운용") → `gross_profit` 0
- 일부 증권사(현대차증권·유화증권 등)는 "매출액" 통합 계정 없이 이자수익·수수료수익 등 항목별로만 공시 → `revenue` 0 (다중회사 API로 되돌려도 동일하게 없음을 실제 호출로 확인함 — API 문제가 아니라 회사 공시 방식 자체의 한계)

**(B) 성격별 손익계산서를 쓰는 업종 — 매출총이익만**
K-IFRS는 손익계산서를 "기능별"(매출원가 별도 구분)과 "성격별"(재료비·인건비·감가상각비 등으로만 나열) 중 선택할 수 있다. 지주회사(자체 판매사업 없음)·연구개발업·출판업·엔지니어링·전기가스공급업 등은 성격별을 주로 써서 매출원가/매출총이익 항목이 아예 안 나온다.

**(C) 진짜 매출 0원 (정상)**
인벤테라 등 임상/연구 단계 바이오 기업은 `ifrs-full_Revenue` 태그는 있지만 값 자체가 "0" — 아직 제품 매출이 없는 게 맞음.

### 결론

지금 시점에서 남은 0값은 전부 (A)/(B)/(C) 중 하나에 해당하는 정상값이며, 별도 조치 없이 F-Score 계산 시 업종 처리 로직으로 흡수한다 (아래 2번 항목 참고).
- currentAssets/currentLiabilities → 261~263번째 줄, "재무건전성" 항목 중 유동비율 전년대비 증가 판단
- grossProfit → 271~273번째 줄, "운영효율성" 항목 중 매출총이익률 전년대비 증가 판단
- currGrossMargin = grossProfit / revenue 를 당기·전기 각각 계산해서 당기가 더 높으면 1점


F-Score 필터 먼저 적용 → fScore >= 6 이거나 fScore == null && 금융업 인 종목만 후보 pool로 추림
그 후보 pool 안에서만 PER/PBR/ROE/ROA/부채비율/EPS성장률/모멘텀 각각 percentile rank 계산 (지금 ascRank/descRank/percentileScore 로직 그대로 재사용)
가중합산 후 상위 100개 추출
이렇게 하면:

금융업 종목은 F-Score 때문에 탈락하지 않고 pool에 들어와서, 자기 PER/PBR/ROE 등 값으로 다른 종목들과 정상적으로 경쟁합니다 (md 79번째 줄에서 언급한 "하나금융지주 같은 금융주도 저평가 우량주에 포함될 수 있다"는 취지에 부합).
F-Score 미달(6점 미만) 종목은 애초에 pool에서 빠지니까, 얘내 때문에 나머지 종목들의 percentile 분모(n)가 왜곡되는 일도 없고요.

## 2. F-Score 설계 — 매출총이익률 항목을 유지하는 이유

### 논의된 문제

F-Score의 "매출총이익률 전년대비 증가" 항목은, 매출총이익 개념 자체가 없는 회사(위 1번의 (A), (B))는 항상 0%>0%(거짓)가 되어 이 항목을 절대 못 받는다. 실제 수익성이 나빠서가 아니라 업종 구조 때문에 불이익을 받는 셈이라 불공정 문제가 제기됐다.

### 검토한 대안과 결정

| 대안 | 채택 여부 |
|---|---|
| 금융업 종목은 F-Score 계산 자체를 스킵(null) | ✅ 채택 |
| 매출총이익률 항목을 전체 종목에서 삭제 | ❌ 기각 |
| 매출총이익률 항목은 유지, 계산 안 되면 자연스럽게 0점(현재 구조 그대로) | ✅ 채택 |

**금융업(induty_code 64/65/66) — F-Score 전체 스킵(null)으로 처리한다.**
- 이유: 금융업은 유동비율·매출총이익률·때로는 매출액 자체까지, 9개 항목 중 여러 개가 구조적으로 안 맞는다. Piotroski F-Score 원논문 자체도 은행·보험사를 표본에서 제외한다 (실제 웹 검색으로 확인 — 유동비율·자산회전율 테스트가 금융업에는 의미가 없고, 많은 은행이 유동자산/유동부채를 애초에 구분해서 보고한 적이 없다는 게 이유).
- F-Score는 4단계 가중합산 점수(PER 25%/PBR 15%/ROE 20%/ROA 10%/부채비율 15%/EPS성장률 5%/모멘텀 10%)에는 포함되지 않고 "기준 미달 필터링"(F-Score ≥ 6점 통과)에만 쓰이므로, null 처리 시 4단계 필터에서 "미달"이 아니라 "필터 예외(통과)"로 다뤄야 한다 — **4단계 `Top100Service` 구현 시 반영 필요.**
- 금융업이라고 PER/PBR/ROE/ROA/부채비율/모멘텀까지 배제하는 건 아니다. 이 지표들은 금융업에도 정상 계산되고, 실제로 국내 "저평가 우량주" 콘텐츠에도 은행지주 등 금융주가 포함되는 경우가 흔하다 (예: 하나금융지주). F-Score만 업종 특성과 안 맞아서 예외 처리하는 것.

**매출총이익 개념이 없는 비금융업(지주회사·연구개발업 등, ~21개사 수준) — 항목 삭제하지 않고 유지한다.**
- 이유: 매출총이익률 개선은 전체 종목의 대다수(제조업·유통업 등)에게는 실제로 유효한 수익성 개선 신호다. 소수 업종을 위해 전체 종목에서 이 항목을 삭제하면, 대다수 기업에 대해 정상 작동하던 유효한 판단 기준을 잃는다.
- 지금 구조(`ratio()`가 분모/값이 없으면 `null` 반환 → 해당 항목 점수 미부여)는 이미 안전하게 처리되고 있다 — 에러가 나거나 마이너스가 되는 게 아니라 그냥 1점을 못 받는(9점 만점이 사실상 8점 만점이 되는) 수준이다.
- F-Score는 정밀 랭킹이 아니라 "6점 이상 통과" 식 필터로만 쓰므로, 9개 중 1개 항목을 구조적으로 못 받는 정도는 필터링 결과에 미치는 영향이 미미하다.
- Piotroski 원논문도 모든 회사에 9개 항목이 똑같이 적용 가능한 게 아니라는 한계를 인정하고, 심하게 안 맞는 업종(금융업)만 통째로 제외하는 방식을 쓴다 — 지금 결정과 같은 방향.

### 남은 작업 (4단계 Top100Service 구현 시 반영)

- [ ] `Company.induty_code` 앞 2자리가 금융업 계열(64/65/66 등)이면 F-Score 계산 스킵 → `f_score = null`
- [ ] F-Score 필터링 로직에서 `f_score IS NULL`은 "미달"이 아니라 "필터 예외(통과)"로 처리
- [ ] F-Score 통과 기준: **6점 이상**
