## 2. `04_backtest_grid.py` 집계 버그 2건 수정

### 2-1. `final_cum_return` 비결정성 (심각도 높음)

```python
# 수정 전
summary = with_drawdown.groupBy("name").agg(
    F.last("cum_return").alias("final_cum_return"),   # 셔플 순서 의존
```

`groupBy().agg(F.last(...))`는 셔플 이후의 행 순서에 의존하는 **비결정적 함수**다. 앞에서 윈도우로 정렬했더라도 마지막 구간 값이 나온다는 보장이 없다.

**이건 03번에서 `F.first()` 순서 의존성으로 이미 두 번 겪은 것과 완전히 같은 패턴이다.** `03_build_indicators.py`의 `join_dividend_yield` 주석에 "Spark 분산 처리 특성상 정렬 후 groupBy도 순서 보장 안 됨"이라고 직접 적어놓았는데, 04번에는 그 교훈이 반영되지 않았다.

**수정**: orderBy와 프레임을 명시한 윈도우 위의 `F.last()`로 마지막 행 값을 그룹 전체에 채운 뒤 집계. 윈도우에 프레임이 명시되면 순서가 정의되어 있어 안전하다.

```python
w_full = w.rowsBetween(Window.unboundedPreceding, Window.unboundedFollowing)
with_final = with_drawdown.withColumn("final_cum_return", F.last("cum_return").over(w_full))
summary = with_final.groupBy("name").agg(F.max("final_cum_return").alias("final_cum_return"), ...)
```

처음에는 `F.max_by("cum_return", "period_start")` 한 줄로 쓰려 했으나, Docker가 꺼져 있어 런타임에 `F.max_by`가 존재하는지 확인할 수 없었다. 확인하지 못한 API를 남기지 않기 위해 **이 파일에 이미 쓰이던 함수만으로** 처리했다.

**영향**: 프로젝트 최종 산출 지표이므로, 기존에 기록된 성과 수치(KOSPI 최고 +72.6%, monthly -64.6% 등)는 **재실행 후 재확인이 필요하다.**

### 2-2. MDD가 첫 구간 하락을 누락

`running_peak`이 누적수익률의 최댓값이라 자산곡선 시작점(누적 0%)이 고점 후보에서 빠져 있었다. 첫 구간에 -20%가 나면 `running_peak = -0.2`, `drawdown = 0`이 되어 그 낙폭이 MDD에 잡히지 않는다.

**수정**: `F.greatest(F.max("cum_return").over(...), F.lit(0.0))`로 하한을 0에 걸었다.

**영향**: MDD가 **더 나빠지는 방향으로만** 바뀐다.

## 3. 룩어헤드 바이어스 수정 (핵심)

### 3-1. 문제

`03_build_indicators.py`의 `main()`이 `prices_current`를 **연도 필터 없이** `join_latest_price()`에 넘기는데, 이 함수는 `Window.partitionBy("stock_code").orderBy(F.desc("bas_dt"))` + `row_number()==1`로 **데이터셋 전체에서 가장 최근 bas_dt 한 건**을 고른다.

따라서 `--year 2021`로 실행해도 `per`/`pbr`/`dividend_yield`가 **2023-12 종가**로 계산되고, 04번은 이 값으로 2021년 리밸런싱 시점 스크리닝을 한다.

**`rcept_no <= rebalance_date` 조건이 재무제표 쪽 미래 정보는 막았지만, 비율의 분자인 가격은 안 막혀 있었다.**

오염 범위가 PER 하나가 아니었다.

| 대상 | 오염 경로 |
|---|---|
| `per`, `pbr` | 분자인 `close_price`가 전체 최신가 |
| `eps`, `bps` | 분모인 `share_count`도 `join_latest_price`가 같은 최신 스냅샷에서 함께 가져옴 |
| `dividend_yield` | `dividend_amount / close_price`의 분모가 같은 최신가 |

즉 `strategies.yaml`이 쓰는 **3개 조건(`per_max`/`pbr_max`/`dividend_yield_min`) 전부**가 이 문제를 공유했다.

### 3-2. 왜 지금까지 안 걸렸나

- **verify_indicators 검증에서 안 잡힌 이유**: Java `FinancialIndicatorService`도 최신가를 쓴다(실시간 서비스로는 맞는 동작). 이 노트북은 "03번이 Java의 실시간 계산 로직을 정확히 재현했는가"만 검증하며, "과거 시점 백테스트에 쓸 수 있는가"는 애초에 검증 범위 밖이었다.
- **의도된 설계가 아니라 버그**: 04번 docstring이 룩어헤드 방지를 설계 목표로 명시하고 있고, `prices_at_dates()`는 수익률 계산에 시점별 가격을 이미 제대로 쓰고 있다. 즉 "가격은 시점별로 재평가해야 한다"는 걸 알고 실천하고 있었는데, **스크리닝에 쓰는 PER/PBR만 03번에서 확정된 고정값을 그대로 받아 쓴** 03/04 경계의 구조적 결함이다.
- **fan-out 버그와 발생 조건이 동일**: 2023년 단일 연도만 있을 때는 정상이었다가 다년치로 확장하면서 드러났다.

### 3-3. 결과에 대한 가설 (미검증)

"PER 낮은 순 상위 N종목"이 실질적으로 **"2023년 12월 기준으로 싼 종목"**, 즉 3년간 많이 떨어질 종목을 2021년에 사는 셈이 된다. 1,000개 전략 평균 -48%가 전체 종목 중앙값 -21.8%보다 훨씬 나빴던 것과 방향이 맞는다.

**단 이 인과관계는 가설이며, 재실행 전에는 확정할 수 없다.**

### 3-4. 수정 내용

추가 API 수집은 필요 없었다. 필요한 데이터가 이미 전부 있었다.

- `01_ingest_raw.py`가 `lstgStCnt`(상장주식수)를 일자별로 수집
- `02_clean_prices.py`가 `listed_share_count`를 forward-fill 대상에 포함
- 03번 `df`에 `net_income_krw`/`equity_krw`/`dividend_amount`가 이미 계산돼 있으나 최종 `select`에서 빠져 있었을 뿐

**`03_build_indicators.py`** (1줄 추가)
- 최종 `result.select(...)`에 `net_income_krw`, `equity_krw`, `dividend_amount` 추가
- 기존 `per`/`pbr`/`dividend_yield` 컬럼은 **의도적으로 유지** — `verify_indicators.ipynb`가 이 컬럼명에 직접 의존하므로 제거하면 Java 대조 검증이 즉시 깨진다
- `join_latest_price`/`calculate_core_ratios`/`join_dividend_yield` 로직 자체는 무변경

**`04_backtest_grid.py`**
- `MAX_VALID_DIVIDEND_YIELD = 100.0` 상수 추가 (03번과 동일 값)
- `prices_at_dates()`: `listed_share_count`를 `share_count_t`로 함께 select
- `compute_point_in_time_ratios()` 신규 — 시점별 `eps_t`/`bps_t`/`per_t`/`pbr_t`/`dividend_yield_t` 계산
- `screen_portfolio()`: `crossJoin(strategies)` **이전에** 가격 조인 후 비율 재계산, `condition`과 정렬 기준을 `_t` 컬럼으로 교체
- `run_for_rebalance_group()`: 캐시된 `prices_by_date`의 시점별 슬라이스를 `screen_portfolio`에 전달

**03번 가드 5개를 04번에 복제** (누락 시 의미가 달라지는 부분)

| 가드 | 목적 |
|---|---|
| `eps_t > 0`일 때만 PER | 적자 기업 PER N/A |
| `equity_krw > 0` & `bps_t != 0`일 때만 PBR | 자본잠식 기업 제외 |
| `share_count_t != 0` | 0으로 나누기 방지 |
| `price != 0` & `dividend_amount` non-null | 배당수익률 계산 가능 조건 |
| `dividend_yield_t <= 100.0` | DART 공시 오류 이상치 제외 |

**조인 순서**: 가격 조인을 `crossJoin` 이전에 배치했다. 전략 1,000개를 곱해 행이 불어나기 전에 종목 수(수천 행) 규모에서 계산을 끝내기 위함이다.

**fan-out 없음 근거**: `latest_valid_indicators`는 `(stock_code)`당 1행, `prices_at_dates`의 시점 슬라이스도 `(stock_code)`당 1행이므로 1:1 조인이다. inner join이라 행이 줄 수는 있어도 늘 수 없다.

**미변경**: 모멘텀·F-Score·EPS성장률은 전략 조건에 쓰이지 않아 그대로 뒀다.

## 5. 발견했으나 수정하지 않은 것

### [중간] 04번이 02번의 플래그를 전혀 사용하지 않음

`is_interpolated` / `split_suspected`를 04번이 한 번도 읽지 않는다.

- 02번이 전 종목 × 전 거래일 격자를 forward-fill하므로 **상장폐지 종목도 마지막 가격이 끝까지 유지**된다. 04번은 그 가격으로 계속 보유한 것으로 계산해 **상폐 손실이 수익률 0%로 기록**된다.
- **종목 101140 건에 대한 새 가설**: 02번은 `lag` 기준 **일별** 판정이므로 급등일에는 `split_suspected`가 True로 찍혔을 가능성이 크다. 04번은 월말 시점만 보고 구간 사이 플래그를 확인하지 않는다. 즉 "02번 탐지가 놓쳤다"기보다 **"04번이 플래그를 안 읽는다"**가 원인일 수 있다. 코드만으로는 단정 불가, 실측 확인 필요.

### [낮음]
- `04:168` `F.log(period_return + 1.0)` — `period_return <= -1`이면 NaN이 되어 해당 전략 이후 누적이 전부 오염
- `01:287` `companies`만 `mode("overwrite")` + `partitionBy("bas_dt")`(static) — 다른 `--bas-dt`로 재실행하면 이전 파티션이 지워짐. prices/financials/dividends는 전부 `append`인데 여기만 다름
- `03:248` `bps`에 `share_count != 0` 체크 없음(`eps`에는 있음). Spark가 null을 반환해 크래시는 나지 않음. 04번 `bps_t`에는 이 체크를 넣어 원본보다 엄격하다.

### 문서 불일치
- `04_backtest_grid.py` docstring 25-27행이 "dividends 원본이 2023년치만 수집되어 있어 2021/2022 dividend_yield는 전부 null"이라고 서술하나, 실제로는 2020~2023 4개년 수집이 완료됐다. 갱신 필요.

### 인프라
- `.claude/agents/spark-batch-engineer.md`의 `model: claude-sonnet-5-0`이 **존재하지 않는 모델 ID**라 에이전트 호출이 실패한다. `claude-sonnet-5`로 수정 필요. (이번 세션에서는 호출 시 모델을 덮어써서 우회함)

## 7. 이번 세션의 교훈

- **같은 실수가 다른 파일에서 반복된다.** `F.first()` 순서 의존성을 03번에서 두 번 고치고 주석까지 남겼는데, 04번에 `F.last()`로 그대로 남아 있었다. 한 곳에서 버그를 고치면 **같은 패턴을 전체 코드베이스에서 검색**해야 한다.
- **가드를 한 곳에서 막아도 다른 경로로 새어 들어온다.** 룩어헤드를 `rcept_no`로 막았지만 비율의 분자인 가격은 열려 있었다. "무엇을 막았는가"가 아니라 **"그 지표를 구성하는 모든 입력이 시점 t 이전 정보인가"**로 점검해야 한다.
- **검증 통과가 정확성을 보장하지 않는다.** verify_indicators는 79종목 8개 지표 완전 일치로 통과했지만, 검증 대상이 "Java 재현도"였기 때문에 백테스트 관점의 결함을 원리적으로 잡을 수 없었다. **검증의 범위 자체를 의심해야 한다.**
- 데이터가 없는 환경에서는 코드 수정까지만 가능하다. 실행 검증이 필요한 작업은 계획 단계에서 제외하는 편이 낫다.
