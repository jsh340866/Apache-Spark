## 5. verify_indicators 검증 (핵심 성과)
## `03_build_indicators`에서 계산한 값과 실제 JAVA 프로젝트의 값의 비교 및 검증

### 검증 방법
기존 ValuePick MySQL이 로컬에 없어, `docker-compose-local.yml`로 ValuePick(`db`, `bn`)을 로컬 기동한 뒤 01번이 받은 Parquet 원본을 그대로 MySQL 스키마에 역주입(`_seed_valuepick_db.py`)하고, `/admin/indicator/calculate/{year}/{reprtCode}` API로 Java가 실제 계산한 값을 우리 03번 결과와 대조.

- 로컬 검증 중 스케줄러의 대량 API 자동 호출(DART/공공데이터 콜 소모, 같은 키를 프로덕션과 공유) 위험을 막기 위해 `DemoApplication.java`의 `@EnableScheduling`을 검증 동안만 주석 처리 → **검증 완료 후 원상복구함**
- 회원가입 후 DB에서 직접 `role='ADMIN'`으로 승격, JWT 로그인 토큰으로 지표 계산 API 호출
- Spark 컨테이너를 ValuePick의 별도 docker network(`valuepick-local_custom-network`)에 연결해 `db` 서비스명으로 JDBC 접속 (검증 종료 후 연결 해제 및 네트워크 삭제)

### 발견 및 수정한 버그
`pivot_financials`가 `account_id`만으로 매칭할 때, DART 응답에서 `ifrs-full_Equity`(자본총계)가 재무상태표(BS)뿐 아니라 자본변동표(SCE)에도 지분 항목별로 수백 건 중복 등장하는 것을 발견. Java는 API 응답 순서 그대로 "처음 만난 값"을 채택(HashMap)해 정상적으로 BS 값을 잡지만, Spark는 분산 처리 특성상 `F.first()`의 순서가 보장되지 않아 SCE의 엉뚱한 하위 항목을 자본총계로 잘못 채택하는 사례 발생(종목 000020: bps 14573.4가 나와야 하는데 자본변동표 오염으로 다른 값 산출 위험).

**해결**: `sj_div`(BS/CIS/IS/CF)를 계정별 허용 범위로 명시 필터링. Java에는 없는 필드(`DartItem.java`에 `sj_div` 자체가 없음)를 활용해 순서 의존성을 원천 제거 — Java보다 오히려 더 안정적인 방식으로 개선.

### 검증 결과
- 대조 대상 79종목 중 **78종목 EPS/BPS/PER/PBR/ROE/부채비율/배당수익률/ROA 8개 지표 완전 일치**
- 1종목만 PER 계산에서 반올림 순서 차이로 0.08 오차 (무시 가능한 수준)
- momentum/F-Score/EPS성장률은 Java 쪽이 NULL로 나왔는데, 이는 계산 로직 문제가 아니라 검증용으로 역주입한 시세가 연속 시계열이 아닌 스냅샷 방식이라 Java의 "기준일 이하 최근값" 탐색이 하루 경계에서 어긋난 것 (검증 환경 한계, 03번 결함 아님)

- 다만 일부 종목(예: 지누스)은 DART API가 원본이 아닌 **최신 정정보고서의 rcept_no**를 반환하는 걸 실제 호출로 확인(2022년 사업보고서인데 rcept_no가 2026년). 이 경우 `rcept_no <= rebalance_date` 조건에서 해당 종목이 부당하게 탈락할 수 있으나, 미래 정보 누출보다는 안전한 방향의 부작용이라 이번 버전에서는 별도 보정하지 않음

## 12. 03번 fan-out 버그 발견 및 수정 (심각도 높음)

03번을 dynamic overwrite로 재실행한 뒤 04번을 돌렸더니 여전히 이상 동작이 발견되어 조사한 결과, `03_build_indicators.py`의 지표 결과가 종목당 1행이 아니라 **최대 50행까지 중복**되어 있었음(2021년 기준 55,182행 vs 실제 종목수 2,368).

- **원인 1(핵심)**: `join_momentum`이 `stock_code`만으로 조인하는데, `01_ingest_raw.py`를 여러 날에 걸쳐 반복 실행하면서 `1m_ago`/`12m_ago` 스냅샷이 종목당 여러 `bas_dt`로 계속 append됨(예: 1m_ago 5개 x 12m_ago 5개 = 25배 중복). 각 중복 행은 momentum 값만 다르고 나머지 지표는 동일했음.
  - **해결**: `_latest_snapshot()` 헬퍼로 종목별 `bas_dt` 최신 1건만 사용하도록 수정.
- **원인 2(부차)**: `join_dividend_yield`가 참조하는 DART 배당 원본 자체에 같은 `(stock_code, year, se, stock_knd)`로 값 있는 행과 공백(`-`) 행이 동시에 존재하는 경우가 실제로 있었음(원본 API 응답 특성, 확정 원인 미상). `parse_amount`가 `-`도 0(non-null)으로 바꿔버려 `F.first(ignorenulls=True)`가 순서에 취약했던 것도 함께 수정.
  - **해결**: 원본 `thstrm`이 실제 값을 가진 행만 non-null로 남기고 `F.first(ignorenulls=True)`로 값이 있으면 그 값을, 전부 없으면 null을 채택하도록 변경.
- 2021/2022/2023 전체 재실행 후 종목당 정확히 1행(2,368건)임을 검증. 79종목 초기 검증(2026-07-29) 당시엔 01번이 한 번만 실행된 상태라 이 문제가 드러나지 않았을 가능성이 높음 — **다년치/반복 재실행 환경에서만 나타나는 버그**였다는 점이 교훈.

## 13. `04_backtest_grid.py`를 실제 monthly/quarterly 리밸런싱으로 재구현

기존 "연 단위로 간소화" 버전을 실제 월간/분기 리밸런싱으로 확장.
- 재무제표(사업보고서)는 연 1회뿐이라 스크리닝 기준 자체를 월별로 갱신할 수는 없음. 대신 **"재무 기준은 그 시점 이전 가장 최근 공시된 사업보고서를 계속 사용하되, 가격은 매월/매분기 재평가해서 포트폴리오를 재구성"**하는 방식으로 monthly/quarterly를 실제로 구분(`latest_valid_indicators`가 시점마다 종목별 최신 유효 rcept_no를 자동 판단).
- `build_rebalance_dates`가 rebalance 값에 따라 다른 시점 목록 생성: monthly는 2021-01~2023-12 전체 월말(36개), quarterly는 3/6/9/12월말(12개)
- **OutOfMemoryError 발생**: for루프로 `unionByName`을 반복 호출하는 구조가 DataFrame 실행계획(lineage)을 시점 수(36+12=48개)만큼 계속 이어붙여 드라이버 메모리 초과. `.cache()` + `.count()`로 각 단계마다 즉시 실체화해 lineage를 끊어 해결. 추가로 `--conf spark.driver.memory`는 클라이언트 모드에서 이미 시작된 SparkContext에 적용 안 됨을 확인 — `spark-submit --driver-memory 3g`(CLI 전용 플래그)로 지정해야 실제 반영됨.
- 검증: monthly(30구간)와 quarterly(10구간)가 실제로 다른 성과(예: 같은 PER8/PBR1.2/n10 조건에서 monthly 누적수익률 -64.6%/MDD -67.4%, quarterly -66.4%/MDD -59.0%)를 내는 것을 확인.

## 운영상 유의사항

- Jupyter 노트북 커널을 탭만 닫고 종료하지 않으면 클러스터 코어를 계속 점유해 다른 작업이 대기 상태에 빠짐 → 작업 끝나면 반드시 `spark.stop()` 호출 또는 Kernel Shut Down
- `spark-submit` 실행 시 `--properties-file /opt/spark-apps/conf/spark-defaults.conf`를 빠뜨리면 클러스터 모드가 아닌 드라이버 로컬 모드로 실행되어 워커 분산이 전혀 안 됨 (반드시 옵션 포함해서 실행)
- Windows Git Bash에서 `docker exec`에 절대경로 인자를 쓸 때는 `MSYS_NO_PATHCONV=1`을 앞에 붙여야 경로 자동변환 오류를 피할 수 있음
- `mode("overwrite")+partitionBy(...)`로 연도별로 나눠 실행할 때는 기본(static) 모드가 출력 디렉토리 전체를 지우므로, `--conf spark.sql.sources.partitionOverwriteMode=dynamic`을 반드시 붙여야 다른 연도 파티션이 보존됨
- DART 공공데이터포털 API가 429가 아닌 502/503(일시적 게이트웨이 장애)을 반환하는 경우가 실제로 있었음. 직후 재요청 시 정상 응답을 받아 횟수 제한이 아님을 확인 → `request_json_with_retry`가 429 외 502/503도 재시도하도록 보강
- 도커 컨테이너가 예기치 않게 재시작된 뒤, 실제 마운트 소스를 확인하지 않고 파일 수정 시각만으로 "안 쓰는 사본"을 판단해 데이터 폴더를 삭제하는 사고가 있었음. 컨테이너 상태를 바꾸기 전에는 `docker inspect <container> --format '{{json .Mounts}}'`로 실제 마운트 경로를 먼저 확인할 것
- for루프로 DataFrame을 반복 `unionByName`하면 lineage가 계속 이어붙어 큰 시점 수(수십 개 이상)에서 드라이버 OutOfMemoryError로 이어질 수 있음 — 중간 결과를 `.cache()` 후 `.count()`로 즉시 실체화해 lineage를 끊을 것
- 드라이버 메모리를 늘리려면 `--conf spark.driver.memory=...`가 아니라 `spark-submit --driver-memory 3g` CLI 플래그를 써야 함(클라이언트 모드에서는 SparkContext 생성 이후 `--conf`로 주입해도 적용 안 됨을 실측 확인)
