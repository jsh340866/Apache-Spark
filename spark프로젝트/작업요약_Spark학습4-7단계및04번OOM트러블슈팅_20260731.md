# Spark 학습 4~7단계 및 04번 파이프라인 트러블슈팅 (2026-07-31)

## 개요

전반부는 `docs/spark-learning/` 학습 로드맵을 4단계(셔플)부터 7단계(성능)까지 완주했다. 후반부는 룩어헤드 바이어스 재실행 검증과 `portfolio_size` 선별 유효성 검증(n=ALL 추가)을 시도하는 과정에서 `04_backtest_grid.py`가 세 번 연속 실패했고, 원인을 층층이 걷어내는 트러블슈팅으로 세션 대부분을 썼다. **최종적으로 04번은 아직 성공 못 했다** — 세 가지 원인을 확정하고 두 가지는 수정했지만, 마지막 재실행도 29분째 좀비 상태로 죽어 사용자 지시로 중단했다.

## 1. Spark 학습 4~7단계 완주

`docs/spark-learning/03_지연_실행.md`까지 되어 있던 상태에서 이어서 진행. 각 단계 문서를 새로 작성했다.

- **4단계 (`04_셔플.md`)**: 셔플의 3단계(디스크 쓰기→네트워크 전송→디스크 읽기), `.explain()`의 `Exchange` 노드. 직접 실습으로 AQE(Adaptive Query Execution)가 `spark.sql.shuffle.partitions` 설정값(200/4)과 무관하게 실제 파티션 수를 1로 줄여버리는 걸 실측 확인(`spark.sql.adaptive.enabled=false`로 껐을 때만 설정값이 그대로 반영됨). 2단계의 "셔플 이후 파티션 수는 shuffle.partitions가 정한다"는 서술에 "AQE가 꺼져 있을 때만"이라는 단서가 필요하다고 정정.
- **5단계 (`05_비결정성.md`)**: 셔플이 같은 키를 같은 파티션에 모으는 건 보장하지만 그 안의 행 순서는 보장 안 한다는 것, `F.first()`/`F.last()`가 이 비결정성에 노출되는 이유. 이 리포에서 반복된 버그 3건(03번 `join_momentum`, 03번 배당, 04번 `summarize_performance`)이 "필요한 지점에 orderBy가 정확히 안 들어갔다"는 하나의 원인으로 수렴한다는 정리. `Window`가 함수가 아니라 "범위 지정자"라는 개념, `groupBy`(행 축소)와의 차이.
- **6단계 (`06_조인_브로드캐스트.md`)**: 기존 ValuePick(Spring Boot/JPA)의 N+1 문제와 `JOIN FETCH` 해결 사례를 브로드캐스트 조인과 같은 발상("필요한 걸 나중에 나눠서 개별 요청하지 말고 미리 합쳐서 곁에 둔다")으로 연결. `F.broadcast(market_codes)`를 재현해 `.explain()`에서 `BroadcastHashJoin`/`BroadcastExchange` 확인. fan-out(조인 상대편 중복 키로 인한 행 증식)을 `join_momentum` 실제 사례와 연결.
- **7단계 (`07_성능.md`)**: 워커 확장이 왜 항상 성능 향상으로 이어지지 않는지(읽기 단계 vs 셔플 단계, 데이터 쏠림, AQE가 튜닝을 무력화하는 지점). 개념 정리만 하고 실측(워커 2대 vs 4대 벤치마크)은 사용자 판단으로 장기 보류.

`00_학습_진행상황.md`를 매 단계 완료 후 갱신. 학습 로드맵(1~7단계) 문서화는 이걸로 일단락.

## 2. 룩어헤드 바이어스 재실행 검증

2. **03번 2020~2023 4개년 재실행**: 순서대로 실행, 각 연도 정상 완료(2020: 2,195건, 2021~2023: 각 2,368건).

## 3. `portfolio_size` 선별 유효성 검증 시도 (n=ALL)

### 배경

기존 `PORTFOLIO_SIZE = [10, 20, 30, 50, 100]`가 전부 "조건 통과 종목 중 상위 N개 선별"이라, "PER/PBR 조건 자체가 시장 평균보다 나은 선택인가"(선별 유효성)를 검증할 대조군이 없었다. 이건 07-30 세션의 "다음 세션에서 이어갈 것" 항목에 이미 있던 논의(`conf/strategies.yaml`에 n=ALL 영구 추가 여부 결정)의 연장.

### 진행 및 실패 3연속

1. `PORTFOLIO_SIZE`에 `9999`(사실상 무제한, `screen_portfolio`의 `rank<=portfolio_size` 필터가 안 걸림) 추가 → **드라이버가 실제 `OutOfMemoryError: Java heap space`로 죽음**(SIGTERM도 처리 못 할 정도로 힙 고갈).
2. `9999`를 `300`으로 낮춰 재실행 → **또 실패**(executor가 드라이버 명령으로 강제 kill됨, "저장 완료" 로그 없음).
3. 원인을 `spark-batch-engineer` 에이전트에 위임해 분석 → `run_for_rebalance_group()`이 monthly/quarterly 두 번 호출되는데 `.cache()`한 4개 DataFrame(`prices_by_date`/`portfolios`/`period_returns`/`summary`)을 해제하는 `unpersist()`가 코드 전체에 없어서, monthly 캐시가 남은 채 quarterly 캐시가 계속 쌓이는 게 원인이라고 판단 → `unpersist()` 추가.
4. `unpersist()` 반영 후 재실행 → **또 같은 방식으로 실패**. 이때 세 방향(04번 코드 재검증, jobs 01~04 전체 로직 검증, Docker/conf 인프라 검증)으로 에이전트 3개를 병렬로 보내 원인을 재조사.

### 확정된 세 가지 원인

1. **`spark.executor.memory` 미지정** — `spark-defaults.conf`에 이 값이 없어 Spark 기본값 1GB로 executor가 뜨고 있었음. 워커 `--memory 2G`는 "워커가 executor에 배분 가능한 총량"이지 executor 하나의 크기가 아니라는 게 실측(`-Xmx1024M`, `docker logs`의 `KILLED exitStatus 143` 패턴)으로 확인됨.
2. **`strategies.yaml` 재생성 누락 (경로 버그)** — `generate_strategies.py`가 `open("strategies.yaml", "w")`로 **상대경로** 저장을 하는데, `docker exec spark-master python3 /opt/spark-apps/conf/generate_strategies.py`로 실행하면 스크립트 위치가 아니라 `docker exec`의 기본 작업 디렉토리(`/opt/spark/work-dir`)에 저장됨. 그 결과 `9999→300` 수정 후 두 번이나 "재생성"했다고 착각했지만 실제 04번이 읽는 `/opt/spark-apps/conf/strategies.yaml`은 옛 값(`portfolio_size: 20`이 200개, `300`은 0개) 그대로였음. `cd /opt/spark-apps/conf && python3 generate_strategies.py`로 명시해서야 정상 반영 확인.
3. **`.cache()` 미해제** — 위 3번 항목의 `unpersist()` 추가.

### 세 가지 수정 후 재실행 (마지막 시도)

`spark-defaults.conf`에 `spark.executor.memory 1536m` 추가 + `strategies.yaml` 실제 재생성(n=300 반영 검증 완료) + `unpersist()` 적용 상태로 KOSPI 재실행.

- 이전 두 번(15~19분)보다 훨씬 오래(29분+) 버텼으나 **결국 좀비 상태로 죽음**(CPU 누적 시간이 40초 이상 전혀 안 늘어나는 것으로 확정 판정).
- 중간에 **Docker Desktop 자체가 일시적으로 응답 불가 상태**(`docker ps`가 500 Internal Server Error)에 빠지는 일도 있었음 — PROGRESS.md에 기록된 이전 워커 4대 사고와 같은 계열(호스트 메모리 압박)로 추정. Docker는 자연 복구됐지만 04번 잡 자체는 이미 좀비였음.
- 사용자가 "executor 메모리 1GB로 되돌리자"고 판단한 시점에 **작업 중단 지시**로 세션 종료. 좀비 드라이버(PID 4492)는 정리하지 않은 채 남아있음.

## 4. 발견했으나 처리 안 한 것 (다음 세션 인수인계)

### [긴급] 좀비 드라이버 정리 필요
`spark-master` 컨테이너 안에 PID 4492(`04_backtest_grid.py --market KOSPI`)가 좀비 상태로 남아있다. 클러스터 코어 4개를 계속 점유하므로, 다음 세션 시작 시 가장 먼저 확인·정리해야 한다(`docker exec spark-master ps aux`로 확인 후 `kill -KILL`).

### [중요] `spark.executor.memory` 재조정 필요
1536m도 실패했다(다만 executor 자체의 OOM인지, 호스트 레벨 메모리 압박인지 완전히 분리 확인은 못 함 — Docker Desktop 응답불가가 끼어들어 판단이 흐려짐). 사용자는 "1GB로 되돌리자"는 방향을 마지막에 제시했으나 실행 전에 중단됨. 재개 시 이 값부터 결정해야 한다.

```
현재 conf/spark-defaults.conf 상태: spark.executor.memory 1536m (되돌리기 전)
호스트 총 메모리: 7.7GB (PROGRESS.md 실측)
워커 2G×2 + 드라이버 3G + executor(워커 메모리 내에서 배분) 조합을 다시 계산해서
Docker Desktop 응답불가를 안 일으키는 안전한 값을 찾아야 함
```

### [확인 필요] `strategies.yaml` 재생성 습관화
`generate_strategies.py`가 상대경로로 저장하는 구조 자체는 고치지 않았다(요청 범위 밖이라 판단해 손대지 않음). 앞으로 이 스크립트를 실행할 때는 반드시 `cd /opt/spark-apps/conf &&`를 붙이거나, 스크립트를 절대경로 저장으로 고치는 걸 고려해야 한다. 잘못 생성됐던 `/opt/spark/work-dir/strategies.yaml`은 삭제 완료.

### [확인 필요] 문서-코드 불일치
- `generate_strategies.py`의 주석(9999→300 관련 서술)과 `README.md`(77행, "10/30/50/100/9999(ALL로 표시)")가 최종 코드값(`[10,30,50,100,300]`, ALL 특수처리 없음)과 어긋난 상태로 남아있을 수 있음 — Docker/conf 검증 에이전트가 발견했으나 이후 세션 중단으로 정리 못 함. 다음 세션에서 재확인 필요.

### [미완료] 04번 KOSPI/ALL 실행 자체
n=300 포함 백테스트가 **한 번도 성공하지 못한 상태**다. `data/backtest_results/KOSPI/`, `data/backtest_results/ALL/` 모두 존재하지 않는다. 이번 세션에서 계획했던 아래 작업은 전부 미착수:
- `04_backtest_grid.py` ALL 시장 실행
- `check_04_backtest.ipynb`에 portfolio_size별(10/30/50/100/300) 누적수익률 비교 그래프 추가
- `PROGRESS.md` 갱신 (룩어헤드 수정 완료 반영, portfolio_size 후보값 갱신, 오늘 OOM 사건 기록)

### [경미] `notebooks/test/01.ipynb`
사용자가 만든 것으로 보이는 실습용 노트북(오늘 11:48 수정, 8.5KB)이 미커밋 상태로 존재. 커밋 대상인지 스크래치인지 미확정.

## 5. 이번 세션의 교훈

- **"재생성했다"는 로그 메시지(`저장 완료`)를 곧이곧대로 믿으면 안 된다.** `generate_strategies.py`가 "conf/strategies.yaml 저장 완료"를 두 번이나 출력했지만, 실제로는 엉뚱한 경로에 저장되고 있었다. 상대경로로 파일을 쓰는 스크립트를 `docker exec`처럼 작업 디렉토리가 불분명한 방식으로 실행할 때는 **결과 파일을 직접 grep해서 값이 실제로 바뀌었는지 검증**해야 한다는 게 이번 사고에서 나온 교훈.
- **"완료(exit code 0)" 알림도 무조건 믿으면 안 된다.** Docker Desktop이 일시적으로 응답 불가였던 여파로 백그라운드 태스크 알림이 실제 상태와 다르게(completed) 보고된 적이 있었다. 항상 8088 마스터 UI/실제 결과 디렉토리로 교차 검증해야 한다.
- **좀비 프로세스 판정은 순간 스냅샷이 아니라 시간차 비교로 해야 한다.** `ps aux`로 한 번 보면 "살아있다"로 보이지만, CPU 누적 시간을 15~40초 간격으로 두 번 이상 비교해야 실제로 일하고 있는지 멈춰있는지 판별된다.
- **원인을 하나 고쳤다고 다음이 성공한다고 단정하지 않는 게 맞았다.** unpersist 추가 → 실패, 원인 3개 확정 → 재실행 → 또 실패. 매번 "이번엔 될 것"이라 예단하지 않고 재실측한 게 결과적으로 두 번째 착각(strategies.yaml 미반영)을 잡아낼 수 있었던 이유.
