## 1. 셔플이 비싼 이유 — 워커는 서로 다른 프로세스다

2단계에서 이 리포의 클러스터 구성을 봤다.

```
spark-master        스케줄링 담당
├─ spark-worker-1   컨테이너 1
└─ spark-worker-2   컨테이너 2
```

워커-1과 워커-2는 물리적으로 **다른 컨테이너**다. 같은 워커 안에서 파티션을 옮기는 것과, 다른 워커로 옮기는 것은 비용이 완전히 다르다. 셔플이 일어나면 "이 값 기준으로는 워커-2로 가야 한다"고 결정된 행은 네트워크를 통해 실제로 전송돼야 한다.

### 셔플이 하는 일 — 3단계

```
1. shuffle write
   각 워커가 자기 파티션의 행들을 "어느 워커로 가야 하는지" 기준으로 분류해
   로컬 디스크에 파일로 씀

2. 네트워크 전송
   다른 워커가 그 디스크 파일에서 "자기 몫"만 네트워크로 가져감

3. shuffle read
   받은 쪽 워커가 다시 디스크에서 읽어 처리
```

메모리가 아니라 디스크에 쓰는 이유: 셔플 대상 데이터가 메모리 용량을 넘을 수도 있고, 여러 워커가 동시에 요청할 때를 대비해 안정적으로 남아있어야 하기 때문 (메모리는 다른 작업에 밀려 날아갈 수 있지만, 디스크 파일은 그 작업이 끝날 때까지 남는다).

**셔플이 비싸다는 말의 실체**: `filter`, `withColumn`은 메모리 안에서 행 하나씩 보고 끝나는데, 셔플은 여기에 디스크 쓰기 + 네트워크 전송 + 디스크 읽기가 추가로 붙는다.

셔플 중간 파일은 잡이 끝나면 정리된다 — 이미 각 워커가 자기 몫을 다 받아서 새 파티션을 구성한 뒤라, 원본 분류 파일은 더 이상 쓸 데가 없기 때문이다 (디스크 공간 낭비 방지).

### 비유 — 트럭

파티션 하나에 실제로 옮길 데이터가 얼마 안 되는데 파티션 개수만 많다면, 물건 12개를 나르는 데 트럭 200대를 부르는 것과 같다. 트럭 한 대를 부르고 출발시키는 절차(스케줄링, 통신) 자체가, 실어 나르는 물건의 양보다 오래 걸리는 상황이 된다. 이 비유는 6장(AQE)에서 실측으로 다시 나온다.

## 2. `.explain()`으로 셔플 확인하기

3단계에서 배운 `.explain()`을 셔플 유무를 비교하는 데 쓸 수 있다.

```python
raw = spark.read.parquet("/opt/spark-apps/data/cleaned/prices")

no_shuffle = raw.filter(F.col("year") == 2021)
no_shuffle.explain()

with_shuffle = raw.groupBy("stock_code").count()
with_shuffle.explain()
```

**셔플 없는 연산(filter)의 실행 계획**:

```
== Physical Plan ==
*(1) ColumnarToRow
+- FileScan parquet [...] PartitionFilters: [isnotnull(year#10), (year#10 = 2021)], ...
```

**셔플 있는 연산(groupBy)의 실행 계획**:

```
== Physical Plan ==
AdaptiveSparkPlan isFinalPlan=false
+- HashAggregate(keys=[stock_code#0], functions=[count(1)])
   +- Exchange hashpartitioning(stock_code#0, 200), ENSURE_REQUIREMENTS, [plan_id=20]
      +- HashAggregate(keys=[stock_code#0], functions=[partial_count(1)])
         +- Project [stock_code#0]
            +- FileScan parquet [...]
```

`groupBy` 쪽에만 등장하는 노드가 있다 — **`Exchange`**. 이게 셔플이 실행 계획에 남기는 흔적이다. 지금까지 말한 "디스크 쓰기 → 네트워크 전송 → 디스크 읽기"가 벌어지는 지점이 바로 이 `Exchange` 노드다.

`HashAggregate`가 두 번(Exchange 앞뒤로) 나오는 것도 눈여겨볼 부분: 셔플 전에 각 워커에서 부분 집계(`partial_count`)를 먼저 해서 옮길 데이터량을 줄이고, 셔플 후에 최종 집계(`count`)를 한다.

---

## 3. `Exchange` 옆의 숫자 — `spark.sql.shuffle.partitions`

`Exchange hashpartitioning(stock_code#0, 200)`에서 `200`은 셔플 후 만들어질 파티션 수다. 이 숫자가 어디서 오는지는 `conf/spark-defaults.conf`에서 확인 가능하다.

```
spark.sql.shuffle.partitions          4
```

이 리포는 4로 맞춰뒀는데(2단계: 워커 2대 × 2코어 = 총 4코어에 맞춘 값), 방금 `.explain()` 결과에는 200이 찍혔다. 원인은 실행 방식의 차이다.

```
spark-submit --properties-file .../spark-defaults.conf
  → conf 파일을 명시적으로 읽음 → shuffle.partitions=4 적용

Jupyter에서 SparkSession.builder.master(...).appName(...).getOrCreate()
  → conf 파일을 전혀 참조하지 않음
  → Spark 자체의 기본값인 200이 그대로 적용됨
```

CLAUDE.md의 "`--properties-file` 누락 시 워커 분산이 전혀 안 된다"는 경고와 같은 종류의 함정이다 — 이번엔 파티션 개수 설정이 안 먹은 경우.

---

## 4. 실측 — 그런데 파티션 수가 200도 4도 아니었다

직접 실험해봤다.

```python
grouped = raw.groupBy("stock_code").count()
print("현재 shuffle.partitions:", spark.conf.get("spark.sql.shuffle.partitions"))
print("실제 결과 파티션 수:", grouped.rdd.getNumPartitions())

spark.conf.set("spark.sql.shuffle.partitions", "4")

grouped2 = raw.groupBy("stock_code").count()
print("변경 후 shuffle.partitions:", spark.conf.get("spark.sql.shuffle.partitions"))
print("실제 결과 파티션 수:", grouped2.rdd.getNumPartitions())
```

**실측 결과**:

```
현재 shuffle.partitions: 200
실제 결과 파티션 수: 1

변경 후 shuffle.partitions: 4
실제 결과 파티션 수: 1
```

`shuffle.partitions`가 200이든 4든 상관없이 실제 결과는 **1개 파티션**이었다. 설정값과 실제 파티션 수가 따로 놀았다.

## 5. 원인 — AQE (Adaptive Query Execution)

`.explain()` 결과 맨 위에 있던 이 줄이 단서였다.

```
AdaptiveSparkPlan isFinalPlan=false
```

Spark 3.x부터 기본으로 켜져 있는 **AQE(적응형 쿼리 실행)** 때문이다.

```
spark.sql.shuffle.partitions  → 이건 "최대 몇 개까지 쓸 수 있는지"의 상한선일 뿐
AQE가 실행 도중 실제 데이터 양을 보고
  → "stock_code 종류가 얼마 안 되고 데이터도 작으니 파티션 1개면 충분하다"
  → 설정값(200이든 4든)과 무관하게 실제로는 더 적은 파티션만 사용
```

이걸 다시 실측으로 검증했다. AQE를 끄면 설정값이 그대로 적용되는지 확인.

```python
spark.conf.set("spark.sql.adaptive.enabled", "false")

grouped3 = raw.groupBy("stock_code").count()
print("AQE 끈 상태, shuffle.partitions:", spark.conf.get("spark.sql.shuffle.partitions"))
print("실제 결과 파티션 수:", grouped3.rdd.getNumPartitions())
```

**실측 결과**:

```
AQE 끈 상태, shuffle.partitions: 4
실제 결과 파티션 수: 4
```

AQE를 끄니 설정값(4)이 그대로 실제 파티션 수로 나왔다. 이걸로 AQE가 원인이라는 게 실측으로 확정됐다.

**2단계 내용에 정정이 필요한 지점**: 2단계에서 "셔플 이후 파티션 수는 shuffle.partitions가 정한다"고 정리했는데, 정확히는 **"AQE가 꺼져 있을 때만 그렇다"**는 단서가 붙어야 한다. AQE가 기본으로 켜진 Spark 3.x에서는, 그 설정값을 상한으로 두고 Spark가 실행 중 데이터를 보며 알아서 줄이는 게 기본 동작이다.

## 6. AQE와 "코어 수에 맞춘 파티션 수"의 상충

AQE가 파티션을 줄이는 것 자체는 1장의 트럭 비유를 실제로 막아주는 좋은 기능이다 — 데이터가 작은데 쓸데없이 많은 파티션으로 쪼개는 낭비(관리 비용이 계산 비용보다 커지는 상황)를 자동으로 방지한다.

문제는 2단계에서 배운 다른 원칙과 부딪힐 수 있다는 점이다.

```
2단계 원칙: 파티션 < 코어 → 코어가 논다
이 리포는 코어가 4개뿐이라 shuffle.partitions=4로 맞춰둠 (코어 수에 딱 맞춘 값)
```

AQE가 "데이터가 작으니 4보다 더 줄여도 된다"고 판단해서 실제로 2개나 1개만 쓰면:

```
파티션 2개, 코어 4개:
  코어A ──▶ 파티션1
  코어B ──▶ 파티션2
  코어C ──▶ (일감 없음)
  코어D ──▶ (일감 없음)
```

의도적으로 "코어 4개 다 활용"하려고 맞춰둔 값을, AQE가 그 밑으로 깎아버리면 오히려 일부 코어가 노는 상황이 될 수 있다.

```
AQE가 파티션을 줄이는 게 좋은 경우:  데이터가 정말 작아서, 4개보다 적어도 코어가 노는 것보다 이득일 때
AQE가 파티션을 줄이는 게 걱정되는 경우: 04번처럼 원래도 코어가 딱 4개뿐인 상황에서
                                     AQE가 4보다 더 줄이면 남은 코어가 놀아서
                                     오히려 병렬성이 떨어질 수 있음
```

**이건 아직 실측 안 된 부분**이다 (CLAUDE.md 원칙: 성능 수치는 추정하지 않고 실측 먼저). 04번 잡을 실제로 `spark-submit --properties-file`로 정상 실행했을 때, 각 셔플 단계의 실제 파티션 수가 몇 개로 나오는지 Spark UI(`localhost:8088`, 잡 실행 중엔 `localhost:4040`)의 SQL 탭에서 확인해야 결론을 낼 수 있다.

## 7. 정리

```
셔플이 비싼 이유: 워커가 서로 다른 프로세스라, 셔플이 일어나면
                디스크 쓰기(shuffle write) + 네트워크 전송 + 디스크 읽기(shuffle read)가 붙는다
                파티션 수가 데이터량에 비해 너무 많으면, 이 관리 비용이 계산 비용보다 커진다 (트럭 비유)

.explain()에서 셔플 확인: Exchange hashpartitioning(...) 노드가 셔플의 흔적
                        HashAggregate가 셔플 앞뒤로 두 번 나오는 건 부분집계 → 셔플 → 최종집계 구조

spark.sql.shuffle.partitions: conf 파일 값은 spark-submit --properties-file로 명시해야 적용됨
                              Jupyter의 SparkSession.builder(...)는 이 conf를 안 읽어서 Spark 기본값(200) 사용

AQE (Adaptive Query Execution): Spark 3.x 기본 활성화
                               shuffle.partitions는 "상한선"일 뿐
                               실행 중 실제 데이터 양을 보고 파티션 수를 자동으로 줄임
                               (실측: 200이든 4든 → 실제 1. AQE 끄면 → 설정값 그대로 4)

주의할 점: 코어 수에 맞춰 일부러 늘려둔 shuffle.partitions를
          AQE가 그 밑으로 깎아버리면 오히려 코어가 놀 수 있다 (04번 실측 필요, 미완)
```

1. 셔플 후 파티션 안 행의 순서가 왜 보장되지 않는가 (네트워크로 각기 다른 시점에 도착하는 조각들)
2. `03_build_indicators.py`, `04_backtest_grid.py`에서 실제로 발생했던 세 건의 버그 코드
3. `F.first(ignorenulls=True)` 같은 임시방편과, `Window.orderBy` + `F.first`/`F.last`로 순서를 명시하는 정공법의 차이
