# 2단계. 파티션 — 조각을 몇 개로 나눌 것인가

> 학습 로드맵
> ```
> 1단계  Spark가 대체 뭘 하는 물건인가        → 01_스파크_개념.md
> 2단계  파티션 — 데이터가 쪼개져 있다는 것    ← 이 문서
> 3단계  지연 실행 — 안 하고 미뤘다가 몰아서 한다
> 4단계  셔플 — 쪼갠 걸 다시 섞는 비싼 작업
> 5단계  그래서 순서가 안 지켜진다 (본 리포 버그 3건의 정체)
> 6단계  조인 전략 / 브로드캐스트
> 7단계  성능 — 왜 워커를 늘려도 빨라지지 않는가
> ```

> **용어 통일**: 1단계에서 "조각", "상자"로 부르던 것이 전부 **파티션(partition)** 이다. 앞으로는 파티션으로 쓴다.

**코어 수(4개)만은 양쪽 환경에서 항상 동일하게 유지한다.** 이 문서 내내 나오는 숫자다.

## 2. 코어 1개 = 한 번에 파티션 1개

Spark에서 가장 기본이 되는 규칙.

```
코어 1개는 한 번에 파티션 1개를 처리한다
파티션은 쪼갤 수 없는 작업 배분의 최소 단위다
```

코어가 파티션을 나눠 가질 수 없다. 파티션 하나를 코어 두 개가 반씩 처리하는 건 불가능하다.

```
파티션이 4개일 때 (4코어):

  코어A ──▶ 파티션1  ████████
  코어B ──▶ 파티션2  ████████
  코어C ──▶ 파티션3  ████████
  코어D ──▶ 파티션4  ████████
                     ↑ 전부 동시에. 딱 맞음
```

### 파티션이 적으면 — 코어가 논다

```
파티션 2개, 코어 4개:

  코어A ──▶ 파티션1  ████████████████
  코어B ──▶ 파티션2  ████████████████
  코어C ──▶ (놀음)
  코어D ──▶ (놀음)
           ↑ 절반이 논다. 시간은 2배
```

**코어를 늘려도 소용없는 상태다.**

### 파티션이 너무 많으면 — 관리비가 붙는다

파티션 하나를 처리하려면 Spark가 이걸 해야 한다:

1. 태스크(작업 단위)를 만들고
2. 워커에 보내고
3. 워커가 받아서 실행하고
4. 결과를 회수하고

이게 파티션당 **수십 밀리초**씩 든다. 계산 시간과 별개로.

```
[파티션 4개]
  파티션당 47만 행
  계산 ████████  관리 ▪
                 ↑ 관리비 무시할 수준

[파티션 2555개]
  파티션당 737행
  계산 ▪         관리 ████████████
                 ↑ 배보다 배꼽
```

188만 행을 2,555파티션으로 나누면 파티션당 737행. 737행 계산은 눈 깜짝할 새인데 태스크 만들고 보내고 받는 데 그보다 오래 걸린다. 게다가 코어는 여전히 4개라 **동시성도 안 늘어난다.**

## 3. spark.sql.shuffle.partitions = 4

`conf/spark-defaults.conf:3`

```
# worker-1, worker-2 각 2코어 = 총 4코어 -> shuffle partition 기본값(200)이 과도하므로 축소
spark.sql.shuffle.partitions          4
```

**코어 4개니까 파티션 4개.**

설정 이름에 `shuffle`이 붙어 있는 점에 주의. **셔플 후에** 파티션을 몇 개로 만들지를 정하는 값이다.

### 기본값이 200인 이유

Spark를 만든 사람들이 상정한 환경이 **수십~수백 코어짜리 클러스터**다. 코어가 100개면 파티션 200개가 적당하다.

이 리포는 4코어라 200으로 두면:

```
파티션 200개 ÷ 코어 4개 = 코어당 50파티션을 순차 처리
파티션당 데이터: 188만 ÷ 200 = 9,400행
→ 계산은 금방인데 태스크 200개 관리비가 다 붙음
```

4로 줄인 것은 환경에 맞는 정확한 판단이다.

### 실무 기준

```
파티션 수 = 총 코어 수 × 2 ~ 4
```

4코어면 8~16 정도. 코어 수보다 크게 잡는 이유는 **파티션마다 크기가 다를 수 있어서**다.

```
[파티션 4개, 크기가 다를 때]
  코어A ──▶ 파티션1  ████                    → 먼저 끝남, 논다
  코어B ──▶ 파티션2  ████                    → 먼저 끝남, 논다
  코어C ──▶ 파티션3  ████                    → 먼저 끝남, 논다
  코어D ──▶ 파티션4  ████████████████████    → 혼자 계속
                                               ↑ 전체가 이거 기다림

[파티션 8개]
  코어A ──▶ 파티션1 ██ → 파티션5 ██
  코어B ──▶ 파티션2 ██ → 파티션6 ██
  코어C ──▶ 파티션3 ██ → 파티션7 ██
  코어D ──▶ 파티션4 ██ → 파티션8 ██
           ↑ 먼저 끝난 코어가 남은 파티션을 가져가므로 놀지 않음
```

**이 리포의 설정 4는 "코어 수 × 1"이라 이론상 살짝 적다.** 8로 올리면 빨라질 수 있고, 데이터가 고르게 나뉘면 4가 최적일 수도 있다. **실측해야 안다** — PROGRESS.md 96줄의 "튜닝 전/후 실행시간 실측"이 정확히 이걸 재는 작업이다.

## 4. 파티션 수는 단계마다 바뀐다

`shuffle.partitions = 4`로 설정했다고 그 잡의 파티션이 항상 4개인 게 아니다.

```
(1) 파일을 읽었을 때 생기는 파티션 수  ← 파일 개수/크기가 정함
(2) 셔플하고 나서 생기는 파티션 수    ← shuffle.partitions가 정함
```

**`shuffle.partitions`는 (2)에만 적용된다.** 파일 읽기는 셔플이 아니므로 해당 없다.

### 파일 읽기는 파일이 정한다

```
data/cleaned/prices/
├── year=2021/
│   ├── part-00000.parquet
│   ├── part-00001.parquet
│   ├── part-00002.parquet
│   └── part-00003.parquet
├── year=2022/
└── year=2023/
```

`.parquet` 파일이 여러 개로 쪼개져 저장돼 있고, Spark가 읽을 때 **대략 파일 하나당 파티션 하나**를 만든다. 파일이 12개면 파티션도 대략 12개다.

(정확히는 큰 파일을 쪼개거나 작은 파일 여러 개를 합치기도 한다. `spark.sql.files.maxPartitionBytes` 등이 관여하지만 "파일이 정한다" 정도로 충분하다.)

### 흐름 예시

```
1. 파일 읽기                    → 파티션 12개 (파일이 정함)
2. filter                       → 파티션 12개 (셔플 없음, 행만 줄어듦)
3. groupBy("stock_code")        → 셔플 → 파티션 4개  ← 여기서 처음 적용
4. 또 다른 셔플                 → 파티션 4개
```

**3번에서 처음으로 4가 나온다.**

### 셔플이 없으면 아예 안 쓰인다

```python
raw = spark.read.parquet(...)      # 파일 3개 → 파티션 3개
raw.filter(...).write.parquet(...) # 끝까지 파티션 3개
```

셔플이 한 번도 없으면 `shuffle.partitions`는 쓰이지 않는다. 코어가 4개인데 3개만 쓰고 하나가 논다. 이럴 땐 직접 늘려야 한다.

```python
raw.repartition(4).filter(...).write.parquet(...)
```

`repartition()`은 강제로 파티션 수를 바꾸는 명령이고, 당연히 셔플이 일어난다.

### 확인 방법

```python
raw = spark.read.parquet("/opt/spark-apps/data/cleaned/prices")
print("읽었을 때:", raw.rdd.getNumPartitions())      # 4가 아닐 것

grouped = raw.groupBy("stock_code").count()
print("셔플 후:", grouped.rdd.getNumPartitions())    # 4
```

## 5. 02번 잡의 실제 파티션 흐름

```
89줄  spark.read.parquet(input_dir)
      → 파티션 N개 (파일이 정함)

93줄  filter(snapshot_type == "current")
      → 파티션 N개 그대로 (셔플 없음)

45줄  stock_codes.crossJoin(calendar)
      → 셔플 → 4개

47줄  join(prices, on=["stock_code", "bas_dt"])
      → 셔플 → 4개

51줄  Window.partitionBy("stock_code")
      → 이미 stock_code 기준으로 모여 있으므로 셔플 생략 가능 → 4개

68줄  Window.partitionBy("stock_code")  (flag_split_suspects)
      → 51줄과 같은 기준 → 셔플 생략 가능 → 4개

123줄 write.partitionBy("year")
      → 저장 (디스크 폴더 분리, 아래 7장 참고)
```

**51줄과 68줄이 같은 기준(`stock_code`)이라 유리하다.** 47줄에서 이미 그 기준으로 모아놨으므로 재배치가 필요 없다. 만약 68줄이 `partitionBy("bas_dt")`였다면 날짜 기준으로 또 셔플해야 했다.

### 셔플 후 보장되는 것 / 아닌 것

```
보장됨:      같은 종목은 같은 파티션에 있다
보장 안 됨:  파티션 하나에 한 종목만 있다 (아님. 약 640종목씩 섞임)
```

파티션 4개에 종목 2,555개가 들어간다. 보장되는 건 "같은 종목이 쪼개지지 않는다"뿐이다.

### 파티션이 줄면 하나가 커진다

```
읽었을 때: 188만 행 ÷ 12 = 파티션당 약 15.7만 행
셔플 후:   188만 행 ÷ 4  = 파티션당 약 47만 행
```

파티션은 메모리에 올라가므로 너무 크면 디스크로 넘치거나(spill) 터진다.

## 6. groupBy vs Window.partitionBy

둘 다 셔플을 일으키고 기준도 같게 잡을 수 있지만 **결과 행 수가 다르다.**

```
groupBy              → 행들의 요약        (행 줄어듦)
Window.partitionBy   → 각 행에 정보 추가  (행 유지)
```

원본:

```
stock_code  bas_dt    close_price
005930      20210104  81000
005930      20210105  82900
005930      20210106  82200
```

### groupBy — 3행이 1행으로

```python
df.groupBy("stock_code").agg(F.avg("close_price").alias("avg_price"))
```

```
stock_code  avg_price
005930      82033
```

개별 날짜 정보가 사라지고 종목별 요약값만 남는다.

### Window — 3행 그대로

```python
w = Window.partitionBy("stock_code")
df.withColumn("avg_price", F.avg("close_price").over(w))
```

```
stock_code  bas_dt    close_price  avg_price
005930      20210104  81000        82033
005930      20210105  82900        82033
005930      20210106  82200        82033
```

원본을 잃지 않고 평균이 컬럼으로 붙는다.

### 02번이 Window를 쓴 이유

`jobs/02_clean_prices.py:51-56`

```python
w = Window.partitionBy("stock_code").orderBy("bas_dt").rowsBetween(Window.unboundedPreceding, 0)
filled = filled.withColumn(col, F.last(col, ignorenulls=True).over(w))
```

하려는 것이 **"결측일을 직전 종가로 채우기"**다. `groupBy`를 쓰면 종목당 1행으로 뭉개져서 날짜별 데이터가 사라진다.

```
원하는 결과:
005930  20210104  81000   (원본)
005930  20210105  81000   (결측 → 직전값으로 채움)
005930  20210106  82200   (원본)
        ↑ 날짜별 행이 살아 있어야 함
```

**행을 유지해야 하니까 Window.**

### 선택 기준

```
"종목별 평균이 얼마야?"           → groupBy  (요약이 목적)
"각 행에 종목 평균을 붙여줘"      → Window   (원본 유지가 목적)

질문에 "각 행마다"가 들어가면 Window
```

셔플 비용은 둘이 비슷하다. 차이는 **모은 다음에 뭘 하냐**다.

## 7. partition이라는 단어가 세 군데 나온다

같은 단어인데 뜻이 다르므로 주의.

| 표현 | 뜻 | 위치 |
|---|---|---|
| `spark.sql.shuffle.partitions` | 데이터 조각 개수 | 메모리 |
| `Window.partitionBy("stock_code")` | 셔플 기준 | 메모리 |
| `write.partitionBy("year")` | 저장 폴더 분리 | **디스크** |

세 번째는 다른 얘기다. `jobs/02_clean_prices.py:123`

```python
result.write.mode("overwrite").partitionBy("year").parquet(args.output_dir)
```

디스크에 폴더를 나눠 저장하라는 뜻이다.

```
data/cleaned/prices/
├── year=2021/
├── year=2022/
└── year=2023/
```

나중에 `--year 2021`로 읽으면 2021 폴더만 읽어서 빠르다. (이것 때문에 `partitionOverwriteMode=dynamic`이 필요하다 — README.md 80줄)

## 8. 불변성(immutable) — DataFrame은 안 바뀐다

```python
raw = spark.read.parquet(...)             # 파티션 12개
df  = raw.groupBy("stock_code").agg(...)  # 파티션 4개
```

**`raw`는 계속 12개다.** 4개로 바뀌는 게 아니라 `df`가 새로 생긴 것이다.

```
        raw (12개)
         │
         ├──────────▶ df (4개)
         │
         └──────────▶ (raw는 여전히 12개, 계속 재사용 가능)
```

```python
df1 = raw.groupBy("stock_code").agg(...)      # raw 그대로
df2 = raw.filter(F.col("close_price") > 1000) # raw 여전히 그대로
# raw=12개, df1=4개, df2=12개
```

### 파이썬 리스트와의 차이

```python
# 파이썬 리스트 — 원본이 바뀜
lst = [3, 1, 2]
lst.sort()
print(lst)      # [1, 2, 3]

# Spark DataFrame — 원본 안 바뀜
raw.groupBy("stock_code").agg(...)
# raw는 그대로. 결과를 안 받았으므로 버려짐
```

그래서 반드시 이름을 붙여야 한다.

```python
raw = raw.filter(F.col("close_price") > 1000)
```

이건 원본 변경이 아니라 **이름표 이동**이다. 새 DataFrame이 만들어지고 `raw`라는 이름표가 그쪽으로 옮겨간 것. 원본은 그대로 있고 이름이 없어졌을 뿐이다.

`jobs/02_clean_prices.py:53-56`이 이 패턴이다.

```python
filled = joined
for col in ["close_price", "open_price", "listed_share_count", "market_cap"]:
    filled = filled.withColumn(col, F.last(col, ignorenulls=True).over(w))
```

루프 4번 = DataFrame 4개 생성. `filled` 이름표가 계속 최신 것으로 옮겨간다.

### 왜 불변으로 만들었나

**데이터가 여러 컴퓨터에 흩어져 있기 때문**이다.

pandas는 데이터가 내 램에 통째로 있어서 "3번 행 값을 5로 바꿔"가 가능하다. Spark는 worker-1, worker-2에 나뉘어 있어서:

- 3번 행이 어느 워커에 있는지 찾아야 하고
- 그 워커에 명령을 보내야 하고
- 다른 워커가 동시에 읽고 있으면 어떡하고
- 그 워커가 죽으면 어떡하고

**분산 환경에서 제자리 수정은 지옥이다.** 그래서 수정 대신 항상 새로 만들기로 했다.

### 그 대가로 얻은 것 — 고장 복구

```
raw (파일) → filter → groupBy → df
                                 ↑ 워커가 죽어서 파티션 하나 날아감
```

불변이라 `raw`가 그대로 있으므로 **날아간 파티션만 다시 계산**하면 된다. 중간에 원본을 고쳤다면 원본이 뭐였는지 몰라 복구가 불가능하다.

```
불변이라서 → 재계산이 가능하고
재계산이 가능해서 → 워커가 죽어도 복구된다
```

수백 대 클러스터에서는 워커가 죽는 게 일상이므로 이게 필수다.

## 9. 중간 결과는 안 들고 있다 — lineage

> 질문: 셔플하면 새 파티션 4개가 생기는데, 기존 파티션은 Spark가 기억하고 있나?

**"기억"하는 게 아니라 "만드는 법"을 알고 있다.**

```
Spark가 갖고 있는 것:
  "raw를 파일에서 읽고 → filter하고 → groupBy하면 df가 나온다"  ← 레시피

Spark가 갖고 있지 않은 것:
  filter 직후의 실제 데이터
```

### 왜 안 들고 있나

```python
raw = spark.read.parquet(...)      # 188만 행
df1 = raw.filter(...)              # 100만 행
df2 = df1.withColumn(...)          # 100만 행
df3 = df2.groupBy(...).agg(...)    # 2,555행
```

중간 결과를 다 들고 있으면 약 390만 행어치 메모리가 필요하다. 단계가 20개면 감당 못 한다. 그래서 **중간 결과를 버리고 만드는 법만 적어둔다.**

이 레시피가 **lineage(계보)** 다.

### lineage가 길어지면 그 자체가 짐이 된다

PROGRESS.md 71줄:

> for루프로 `unionByName`을 반복 호출하는 구조가 **실행계획(lineage)을 시점 수(48개)만큼 이어붙여** OOM 발생

```python
result = None
for date in 48개_시점:
    part = 계산(date)
    result = result.unionByName(part)   # 48번 반복
```

```
result = ((((((...48겹...) union part46) union part47) union part48)
```

**레시피가 48겹으로 쌓인다.** 이 레시피는 드라이버 메모리에 있어야 하므로 드라이버가 터졌다.

**데이터가 커서가 아니라 레시피가 커서 터진 것.** 헷갈리기 쉬운 지점이다.

### 해결책 — cache로 레시피 자르기

같은 71줄:

> `.cache()` + `.count()`로 각 단계마다 즉시 실체화해 lineage를 끊음

```python
result = result.unionByName(part).cache()
result.count()   # 여기서 실제로 계산해버림
```

`.cache()`는 "레시피 말고 실제 데이터를 들고 있어"라는 명령이다.

```
[캐시 전]
  레시피: 파일읽기 → union → union → union → ... (48겹)

[캐시 후]
  실제 데이터 있음 (레시피 필요 없음)
  → 레시피 초기화. 여기서부터 다시 쌓임
```

### 정리

```
기본:      중간 결과를 버린다. lineage만 남긴다
.cache():  실제로 들고 있는다

셔플 중간 파일은 잠깐 디스크에 남지만 임시이며 잡이 끝나면 사라진다
```

## 10. PROGRESS.md 97줄 사건 — 워커 4대 시도가 실패한 이유

> 워커 3/4(각 1G) 추가를 시도했으나 호스트 메모리(7.7GB) 대비 **워커 6GB + 드라이버 3GB 과다 할당**으로 Docker Desktop/WSL2가 응답 불가에 빠짐(2회)

### 원인 1 — 메모리 산수

```
현재:  워커1 2G + 워커2 2G                       = 4GB
시도:  워커1 2G + 워커2 2G + 워커3 1G + 워커4 1G = 6GB
       + 드라이버 3G                              = 9GB

호스트 메모리: 7.7GB
9GB > 7.7GB  ← 여기서 터짐
```

Spark 문제가 아니라 산수 문제였다.

### 원인 2 — 파티션을 안 늘렸다 (아직 드러나지 않은 문제)

워커를 4대로 늘리면 코어가 8개가 되는데 `shuffle.partitions`는 **여전히 4**다.

```
코어 8개, 파티션 4개:

  코어A ──▶ 파티션1
  코어B ──▶ 파티션2
  코어C ──▶ 파티션3
  코어D ──▶ 파티션4
  코어E ──▶ (일감 없음)
  코어F ──▶ (일감 없음)
  코어G ──▶ (일감 없음)
  코어H ──▶ (일감 없음)
```

일감이 4덩어리인데 사람이 8명이면 4명은 논다. **워커를 2배로 늘려도 성능은 그대로다.**

### 재시도 시 체크리스트

```
1. 메모리 총합 사전 계산
   워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리

2. spark.sql.shuffle.partitions도 같이 변경
   워커 2대 (4코어) → 4
   워커 4대 (8코어) → 8

   안 바꾸면 "워커 늘렸는데 왜 안 빨라지지?"가 되고
   벤치마크 자체가 무의미해진다
```

## 11. 정리

```
1. 코어 1개 = 한 번에 파티션 1개
   파티션은 쪼갤 수 없는 작업 배분의 최소 단위

2. 파티션 < 코어  →  코어가 논다
   파티션 >> 코어 →  태스크 관리비가 계산보다 커진다

3. spark.sql.shuffle.partitions = 셔플 후 만들 파티션 수
   기본값 200은 수십~수백 코어 기준. 이 리포는 4코어라 4로 축소
   실무 기준은 코어 수 × 2~4

4. 파티션 수는 단계마다 다르다
   파일 읽기 직후 → 파일 개수/크기가 정함
   셔플 이후      → shuffle.partitions가 정함
   셔플이 없는 잡이면 이 설정은 아예 안 쓰인다

5. groupBy는 행들의 요약, Window.partitionBy는 각 행에 정보 추가
   셔플 비용은 비슷. 차이는 모은 다음에 뭘 하냐

6. DataFrame은 불변이다
   연산해도 원본은 안 바뀌고 새 DataFrame이 생긴다
   raw = raw.filter(...)는 이름표 이동이지 원본 변경이 아니다

7. 중간 결과는 안 들고 있다. lineage(만드는 법)만 남긴다
   lineage가 길어지면 그 자체가 드라이버 메모리를 먹는다 → 04번 OOM
   .cache() + .count()로 잘라낸다

8. 워커를 늘리면 파티션도 같이 늘려야 한다
   안 그러면 늘어난 코어가 논다
```
