## 1. 셔플이 보장하는 것, 보장 안 하는 것

`groupBy("stock_code")`처럼 특정 컬럼 기준으로 셔플이 일어나면 두 가지를 구분해야 한다.

```
보장됨:     같은 stock_code를 가진 행들은 반드시 같은 파티션 하나에 모인다
           (안 모이면 애초에 종목별 집계가 불가능하므로)

보장 안 됨: 그 파티션 안에서 행들이 어떤 순서로 나열되는지
           (원본 파일 순서든, 날짜순이든 전혀 보장이 없다)
```

---

## 2. 왜 순서가 마구잡이가 되는가

같은 `stock_code="005930"`인 행이 원본 데이터에서 워커-1, 워커-3, 워커-4에 흩어져 있었다고 하자. 셔플이 일어나면 이 셋이 동시에 목적지 워커(예: 워커-2)로 네트워크를 통해 전송된다.

```
워커-1 → 워커-2 전송  (도착 시간은 네트워크 상황에 따라 다름)
워커-3 → 워커-2 전송  (도착 시간은 네트워크 상황에 따라 다름)
워커-4 → 워커-2 전송  (도착 시간은 네트워크 상황에 따라 다름)
```

어느 게 먼저 도착할지는 네트워크 지연, 각 워커가 그 순간 얼마나 바쁜지 같은 요인에 달려있고, 이건 실행할 때마다 달라질 수 있다. 워커-2는 **도착한 순서대로** 자기 파티션에 쌓는다. 그러니 같은 코드, 같은 데이터를 넣어도 실행할 때마다 파티션 안 행의 순서가 달라질 수 있다.

---

## 3. 비결정성 (non-determinism)

```
비결정성 = 같은 코드, 같은 데이터를 넣어도 실행할 때마다 결과가 달라질 수 있는 성질
원인      = 셔플 후 파티션 안 행의 도착 순서가 매 실행마다 다르기 때문
```

이게 이 리포에서 세 번 반복된 버그의 공통 원인이다. `PROGRESS.md`에 기록된 사례:

```
03_build_indicators.py의 join_momentum
  stock_code만으로 조인 → 종목별 여러 bas_dt 스냅샷 중 어느 게 F.first()로 뽑힐지
  실행마다 달라짐 (자본총계 등이 잘못 채택된 사례)

03_build_indicators.py의 배당 데이터
  같은 키로 값 있는 행과 공백(-) 행이 동시 존재 →
  F.first()가 어느 쪽을 뽑을지 순서 의존적

04_backtest_grid.py의 summarize_performance
  groupBy().agg(F.last("cum_return"))이 "정말 마지막 구간"이라는 보장이 없었음
```

## 4. `F.first()` / `F.last()`가 위험한 이유

```python
result = df.groupBy("stock_code").agg(F.first("dividend_yield"))
```

여기서 "첫 번째"는 날짜순 첫 번째도, 원본 파일 순서상 첫 번째도 아니다. 그냥 **셔플 후 그 파티션에 어쩌다 먼저 도착한 행**이다.

```
실행 1회차: 워커-3 데이터가 먼저 도착 → F.first() = 2021년 값
실행 2회차: 워커-1 데이터가 먼저 도착 → F.first() = 2023년 값

같은 코드, 같은 데이터인데 실행할 때마다 다른 값이 나올 수 있다
```

`groupBy().agg(...)`는 정렬 개념이 없는 순수 집계라서, `F.first`/`F.last`에 "어떤 기준으로 첫/마지막을 정할지" 알려줄 방법이 애초에 없다. 이게 근본 원인이다.

### 세 사례를 하나로 묶으면 — 결국 "orderBy가 정확히 안 들어갔다"

앞서 나온 세 버그를 다시 놓고 보면, 원인이 두 갈래로 갈리는 것처럼 보이지만 결국 하나로 수렴한다.

```
(a) 애초에 orderBy를 안 넣은 경우
    03번 join_momentum, 03번 배당 데이터
    → groupBy().agg(F.first())만 씀. 정렬 기준 자체가 레시피에 없음

(b) orderBy를 넣었지만, 그 정렬이 무효화되는 연산으로 이어붙인 경우
    04번 summarize_performance
    → Window.orderBy("period_start")까지는 정렬을 명시했지만
      그 뒤에 groupBy().agg(F.last(...))로 넘어가면서 정렬이 씻겨나감
    → PROGRESS.md: "앞에서 윈도우로 정렬했더라도 마지막 구간 값이 나온다는 보장이 없다"
```

(b)가 더 위험한 이유는, 코드만 보면 이미 `orderBy`가 있어서 "정렬 처리했네" 하고 안심하게 되지만, `F.first()`/`F.last()`가 실제로 실행되는 시점에는 그 정렬이 이미 무효화된 뒤라는 것이다. 그래서 이 버그가 앞의 두 건보다 더 늦게 발견됐다.

**세 사례를 관통하는 하나의 원인**: `F.first()`/`F.last()`가 실제로 실행되는 그 순간에, 정렬이 보장된 상태가 아니었다. "안 넣은 것"과 "넣었는데 중간에 무효화된 것"은 겉보기엔 다르지만, 레시피 전체를 놓고 보면 둘 다 **"필요한 지점에 orderBy가 정확히 들어가지 않았다"**는 같은 결함이다.

## 5. Window란 무엇인가 — 함수가 아니라 범위 지정자

`Window`는 함수 호출이 아니라, **각 행마다 계산에 사용할 주변 행의 범위를 정의하는 설정값**이다.

```python
w = Window.partitionBy("stock_code").orderBy("bas_dt")
```

이 줄 자체는 아무 계산도 하지 않는다. `w`에는 "stock_code별로 나누고, 그 안에서 bas_dt 순으로 정렬한 범위"라는 **정의**만 담긴다. 실제 계산은 이 `w`를 다른 함수에 `.over(w)`로 붙일 때 일어난다.

```python
F.first("dividend_yield").over(w)
```

```
F.first("dividend_yield")  ← 무엇을 계산할지 (집계 함수)
.over(w)                   ← 어느 범위/순서를 대상으로 계산할지 (Window가 정한 규칙)
```

`groupBy`는 "묶어라"까지만 알려주고 순서는 안 알려주는 반면, `Window.partitionBy(...).orderBy(...)`는 묶는 기준과 정렬 기준을 **둘 다** 명시한다. 그래서 `F.first()`가 뽑는 값이 도착 순서가 아니라 정렬 기준상 진짜 첫 번째로 고정된다 — 즉 **결정적**이 된다.

---

## 6. groupBy vs Window — 행이 줄어드는가, 유지되는가

2단계에서 다룬 내용과 바로 연결된다.

```
groupBy = 요약. 행 개수가 줄어든다 (예: 종목당 여러 행 → 종목당 1행)
Window  = 정보 추가. 행 개수는 그대로 유지되고, 각 행에 계산된 값이 컬럼으로 붙는다
```

```
원본 df: 100만 행 (종목별 여러 날짜의 데이터)

df.groupBy("stock_code").agg(F.first(...))
  → 결과: 2,555행 (종목 수만큼으로 축소)

df.withColumn("first_yield", F.first(...).over(w))
  → 결과: 여전히 100만 행
  → 각 행에 "이 종목의 (윈도우 기준) 첫 번째 값"이라는 컬럼이 추가로 붙음
```

비유: `groupBy`는 학생들을 반별로 묶어서 "반 평균 점수"만 뽑아내는 것(학생 수 → 반 수로 축소). `Window`는 반 평균은 계산하되 그 값을 각 학생 옆에 다시 적어주는 것(학생 수 그대로, 정보만 추가).

04번이 `summarize_performance`에서 `groupBy` 대신 `Window`를 쓴 이유가 이 특성 때문이다 — 시계열(리밸런싱 시점별 행)을 유지한 채로 "전략별 마지막 구간 값"이라는 정보만 각 행에 채워야 했다. `groupBy`로 바로 요약하면 시계열 자체가 사라진다.

## 7. 실제 코드 — `04_backtest_grid.py`의 수정

`summarize_performance` 함수(214-240행)의 실제 코드와 주석:

```python
def summarize_performance(period_returns: DataFrame) -> DataFrame:
    w = Window.partitionBy("name").orderBy("period_start")
    with_cum = period_returns.withColumn(
        "cum_return",
        F.exp(F.sum(F.log(F.col("period_return") + 1.0)).over(w)) - 1.0,
    )
    ...
    # 전략별 "마지막 구간"의 누적수익률을 결정적으로 뽑는다.
    # groupBy().agg(F.last(...))는 셔플 이후의 행 순서에 의존하는 비결정적 함수라, 앞에서 윈도우로
    # 정렬했더라도 마지막 구간 값이 나온다는 보장이 없다(03_build_indicators.py에서 F.first()의 같은
    # 순서 의존성 때문에 자본총계가 잘못 채택된 사례를 이미 겪었다). orderBy와 프레임을 명시한 윈도우
    # 위에서의 F.last()는 순서가 정의되어 있어 안전하므로, 마지막 행 값을 그룹 전체 행에 채운 뒤
    # 집계한다. 그룹 내에서 상수이므로 F.max()로 꺼내도 값이 달라지지 않는다.
    w_full = w.rowsBetween(Window.unboundedPreceding, Window.unboundedFollowing)
    with_final = with_drawdown.withColumn("final_cum_return", F.last("cum_return").over(w_full))
```

```
w = Window.partitionBy("name").orderBy("period_start")
  → 전략(name)별로 나누고, 리밸런싱 시점(period_start) 순으로 정렬
  → 이 순서 위에서 누적수익률(cum_return)을 계산하므로 결과가 항상 동일

w_full = w.rowsBetween(unboundedPreceding, unboundedFollowing)
  → "그룹 전체 범위"를 보라는 뜻 (앞뒤 끝까지 다 포함)
  → 이 범위 위에서 F.last("cum_return")을 쓰면
    "period_start 정렬 기준 진짜 마지막 행의 값"이 항상 뽑힘
```

주석에 적힌 대로, `orderBy`로 이미 정렬을 해뒀어도 `groupBy().agg(F.last(...))`처럼 다시 집계 단계로 넘어가면 그 정렬이 사라진다 — `agg`는 셔플 이후의 순서를 그대로 신뢰하는 별개의 연산이기 때문이다. 그래서 정렬된 채로 `.over(w_full)`을 써서 각 행에 최종값을 채워 넣은 뒤, 그룹 내에서 상수가 된 이 값을 `F.max()` 같은 걸로 꺼내는 방식을 쓴다.

## 8. SQL과의 대응

`Window.partitionBy().orderBy().rowsBetween()`은 SQL 윈도우 함수 문법을 그대로 옮긴 것이다.

```sql
SELECT
  name,
  period_start,
  LAST_VALUE(cum_return) OVER (
    PARTITION BY name
    ORDER BY period_start
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
  ) AS final_cum_return
FROM period_returns
```

```
PARTITION BY name          ↔ Window.partitionBy("name")
ORDER BY period_start      ↔ .orderBy("period_start")
ROWS BETWEEN ... AND ...   ↔ .rowsBetween(...)
LAST_VALUE(...) OVER(...)  ↔ F.last(...).over(w)
```

`GROUP BY`만 쓰고 `ORDER BY` 없이 `FIRST_VALUE`/`LAST_VALUE`를 쓰면 SQL에서도 똑같이 비결정적이다 — Spark만의 특이한 문제가 아니라, 분산·병렬 처리 환경에서 정렬을 명시하지 않으면 공통으로 발생하는 문제다.

## 9. 정리

```
셔플이 보장하는 것:     같은 그룹 키의 행은 같은 파티션에 모인다
셔플이 보장 안 하는 것:  그 파티션 안 행의 순서 (네트워크 도착 순서라 매 실행마다 다름)

비결정성:              같은 코드·데이터인데 실행마다 결과가 달라지는 성질
                       원인은 셔플 후 행 순서가 정해져 있지 않다는 것

groupBy().agg(F.first()/F.last()):
                       정렬 기준을 줄 방법이 없어 비결정적 → 이 리포 버그 3건의 공통 원인

Window:                함수가 아니라 "계산 범위(그룹+정렬)를 정의하는 설정값"
                       .over(w)로 다른 함수와 결합해야 실제 계산이 일어남
                       groupBy와 달리 행을 축소하지 않고 각 행에 정보를 추가

해결법:                Window.partitionBy(...).orderBy(...) 로 그룹 안 정렬 기준을 명시
                       rowsBetween(unboundedPreceding, unboundedFollowing)으로
                       전체 범위를 보게 하면 F.first()/F.last()가 결정적으로 동작

주의:                  orderBy로 정렬해도, 그 뒤에 groupBy().agg()로 다시 넘어가면
                       정렬 정보가 사라진다. 반드시 .over(w)로 정렬된 채로 값을 뽑아야 함

SQL 대응:              PARTITION BY / ORDER BY / ROWS BETWEEN 이 SQL 윈도우 함수 문법과 1:1 대응
```

## 6단계에서 다룰 것

**주제: 조인 전략 / 브로드캐스트**

4단계에서 셔플이 네트워크 전송을 필요로 한다는 걸 봤다. `join`도 셔플이 일어나는 대표적인 연산인데, 양쪽 DataFrame 크기가 크게 차이 나면 굳이 둘 다 셔플할 필요 없이 작은 쪽을 통째로 각 워커에 복사해버리는 방법이 있다 — 브로드캐스트 조인.

1. 일반 조인(셔플 조인)과 브로드캐스트 조인의 차이
2. `spark.sql.autoBroadcastJoinThreshold` — 이 리포 conf에 이미 설정된 값 확인
3. `.explain()`에서 `BroadcastHashJoin` vs `SortMergeJoin` 구분
4. 이 리포에서 fan-out(행 증식) 버그가 났던 조인 지점과 연결
