## 1. 실무 비유 — JPA의 N+1 문제와 JOIN FETCH

Spark 얘기를 시작하기 전에, 같은 발상이 다른 기술 스택에도 있다는 걸 먼저 짚었다. Spring Boot/JPA 프로젝트(ValuePick)의 실제 트러블슈팅 사례:

```java
// N+1 문제 (고치기 전): StockIndicator를 N개 순회하며 매번 Company를 개별 쿼리로 가져옴
List<StockIndicator> indicators = repository.findAll();       // 쿼리 1번
for (StockIndicator i : indicators) {
    i.getCompany().getCorpCls();                               // 순회할 때마다 쿼리 추가 (N번)
}
// 총 쿼리 수 = 1 + N

// JOIN FETCH로 해결: 지표와 회사를 SQL JOIN으로 한 번에 가져옴
@Query("SELECT i FROM StockIndicator i JOIN FETCH i.company WHERE ...")
// 총 쿼리 수 = 1
```

핵심 아이디어: **필요한 데이터를 나중에 여러 번 나눠서 개별 요청하지 말고, 한 번에 미리 합쳐서 가져오면 반복적인 개별 요청 비용을 없앨 수 있다.**

이게 정확히 이번 장의 브로드캐스트 조인과 같은 결이다.

```
JPA N+1 문제:    N번의 개별 쿼리 (네트워크 왕복 N번, DB 왕복 N번)
Spark 셔플 조인:  네트워크로 데이터가 흩어졌다 모이는 재배치 과정 (비쌈)

JPA 해결(JOIN FETCH):    SQL 레벨에서 한 번에 합쳐서 가져옴
Spark 해결(브로드캐스트): 작은 쪽을 통째로 미리 복사해 곁에 둬서, 셔플(재배치) 자체를 생략
```

## 2. 브로드캐스트 조인이란

**브로드캐스트 조인** = 작은 쪽 DataFrame 전체를 워커(정확히는 각 워커의 executor) 단위로 통째로 복제해서, 조인 시 큰 쪽 데이터의 셔플(재배치)을 생략하는 방법.

```
일반 조인(셔플 조인): "내 파티션에 있는 종목이 상대 파티션 어딘가에 있을 수도 있다"
                     → 양쪽 다 stock_code 기준으로 재배치해서 짝을 맞춰야 함 (셔플)

브로드캐스트 조인:    "작은 쪽은 이미 내 옆에 통째로 다 있다"
                     → 상대를 찾아 돌아다닐 필요 없이, 로컬에서 바로 짝지음
```

**복사 단위는 파티션이 아니라 워커다.**

```
워커-1 (파티션 1, 2 담당) → companies 전체 복사본 1벌 (파티션 1, 2 처리할 때 계속 재사용)
워커-2 (파티션 3, 4 담당) → companies 전체 복사본 1벌 (워커-1과 별개의 복사본)
```

파티션마다 매번 새로 복사하는 게 아니라, 워커 하나당 딱 1벌만 받아서 그 워커가 처리하는 모든 파티션에 재사용한다. 그래서 복사본 개수는 파티션 수가 아니라 **워커 수**에 비례한다.

## 3. 브로드캐스트가 항상 좋지는 않은 이유

```
1. 워커 수만큼 복사본이 생김
   워커가 많아질수록(예: 2대 → 100대) 전체적으로 낭비되는 메모리 총량이 커진다

2. "작은 쪽"이 실제로 작지 않으면 워커 OOM
   각 워커 메모리(이 리포 2GB)보다 큰 데이터를 통째로 복사하려 하면
   → 그 워커의 계산용 메모리 공간을 잡아먹거나, 메모리 한도를 넘어 OOM 발생
   (3단계 드라이버 OOM과는 원인이 다른 "워커 OOM")
```

그래서 Spark는 "이 정도로 작을 때만" 자동으로 브로드캐스트하도록 상한선을 둔다.

```
# conf/spark-defaults.conf
spark.sql.autoBroadcastJoinThreshold  10485760   # 10MB
```

```
작은 쪽 데이터가 10MB 이하 → Spark가 자동으로 브로드캐스트 조인을 선택
작은 쪽 데이터가 10MB 초과 → 일반 조인(셔플 조인)으로 처리
```

주석: "04_backtest_grid.py의 종목 마스터(2,500행) broadcast join 힌트가 자동 적용되도록 임계값 설정".

## 4. 브로드캐스트 기준 조정하는 법

```python
# 1. 전역 conf 값 변경 (클러스터의 모든 잡에 적용)
spark.sql.autoBroadcastJoinThreshold  20971520   # 20MB로 상향

# 2. 세션 중간에 동적으로 변경
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", 20 * 1024 * 1024)

# 3. 자동 판단 끄기 (항상 셔플 조인만 쓰게 강제)
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", -1)

# 4. 특정 조인 하나에만 강제 지정 (임계값과 무관하게)
from pyspark.sql.functions import broadcast
result = big_df.join(broadcast(small_df), "stock_code")
```

```
전역 조정(1, 2, 3): "이 크기까지는 자동으로 브로드캐스트해라"는 기준선 자체를 조정
개별 강제(4):       "이 조인 하나는 무조건 브로드캐스트로 해라"는 예외 지정
```

## 5. 실측 — `.explain()`으로 확인

`04_backtest_grid.py:311`에서 실제로 쓰인 코드:

```python
companies = spark.read.parquet(args.companies_dir).filter(F.col("corp_cls") == corp_cls)
market_codes = companies.select("stock_code").distinct()
indicators = indicators.join(F.broadcast(market_codes), on="stock_code", how="inner")
```

Jupyter에서 재현하고 `.explain()`을 실행한 결과:

```
== Physical Plan ==
*(3) Project [stock_code#91, ...]
+- *(3) BroadcastHashJoin [stock_code#91], [stock_code#126], Inner, BuildRight, false
   :- *(3) Filter isnotnull(stock_code#91)
   :  +- ... FileScan parquet (indicators, 큰 쪽) ...
   +- BroadcastExchange HashedRelationBroadcastMode(...), [plan_id=220]
      +- *(2) HashAggregate(keys=[stock_code#126], functions=[])
         +- Exchange hashpartitioning(stock_code#126, 4), ENSURE_REQUIREMENTS, [plan_id=216]
            +- *(1) HashAggregate(keys=[stock_code#126], functions=[])
               +- ... FileScan parquet (companies, 작은 쪽) ...
```

이 실행 계획 하나에 서로 다른 두 동작이 순서대로 들어있다.

```
1. companies 읽기 → corp_cls 필터
2. distinct() 때문에 셔플 발생 (Exchange hashpartitioning) → 중복 제거
   ← distinct()도 "남의 행을 봐야 하는 연산"이라 셔플이 필요 (4단계 원리 그대로)
3. 이렇게 만들어진 작은 쪽(market_codes)을 BroadcastExchange로 모든 워커에 복제
4. indicators(큰 쪽)와 BroadcastHashJoin — 여기서는 셔플 없음, 이미 복제된 걸 로컬에서 훑어봄
```

**핵심 구분**: `Exchange`(셔플, 재배치)와 `BroadcastExchange`(복제, 뿌리기)는 이름은 닮았지만 동작이 다르다. 브로드캐스트 조인을 썼다고 이 실행 계획에 셔플이 "전혀" 없는 게 아니라, **조인 자체에서는 (훨씬 크고 비싼) 큰 쪽의 셔플이 생략된다**는 뜻이다. `distinct()`처럼 작은 쪽을 준비하는 별개의 과정에는 여전히 (작은 규모의) 셔플이 있을 수 있다.

```
join()이라는 코드 한 줄은 "무엇을 할지"만 정하고,
실제 실행 방식(셔플 조인 vs 브로드캐스트 조인)은 Spark나 힌트가 고른다:

  힌트 없음 + 데이터 큼             → SortMergeJoin (셔플 조인)
  힌트 없음 + 데이터 작음(임계값 이하) → BroadcastHashJoin (자동 선택)
  F.broadcast() 힌트 있음           → BroadcastHashJoin (크기 무관 강제)
```

## 6. fan-out — 조인의 근본적인 위험

**fan-out**(팬아웃): 조인할 때 한쪽에 같은 키를 가진 행이 여러 개 있으면, 조인되는 순간 결과 행이 그 개수만큼 곱해져서 불어나는 현상.

```
df (지표, stock_code=005930) 1행

p1m (1개월전 가격, stock_code=005930이 실수로 3행 중복)
  005930, bas_dt=2023-01-15
  005930, bas_dt=2023-02-15
  005930, bas_dt=2023-03-15

df.join(p1m, on="stock_code")
  → stock_code가 같은 모든 조합을 다 만듦 → 결과 3행 (1행이 3행으로 불어남)
```

이건 조인 방식(브로드캐스트냐 셔플이냐)과 **무관하게** 발생한다 — "같은 키가 왼쪽에 A개, 오른쪽에 B개 있으면 결과는 A×B개"라는 건 조인의 정의 자체이기 때문이다. 브로드캐스트는 "어떻게 실행할지"만 바꾸지, "무엇이 결과로 나올지"는 안 바꾼다.

> 참고로 "카티전 곱"이라는 표현은 두 맥락에서 쓰인다: (a) 위처럼 중복 키로 인해 결과가 곱해지는 일반적 성질, (b) `crossJoin`처럼 조인 조건 없이 아예 모든 조합을 의도적으로 만드는 특수 연산(`check_04_02_backtest.ipynb`에서 전략×시점 조합을 만들 때 실제로 씀). 브로드캐스트 조인은 (a)의 성질을 그대로 가지되, (b)의 `crossJoin`과는 다른 연산이다.

## 7. 이 리포 실제 사례 — `join_momentum` fan-out 버그

**왜 중복이 생겼나**: `prices_1m`(1개월전 가격 스냅샷)은 01번 잡을 실행할 때마다 "그 시점 기준 1개월 전 가격"을 `mode("append")`로 계속 쌓는 구조다. 01번을 여러 번 재실행하면, 같은 `stock_code`에 대해 서로 다른 `bas_dt`(01번 실행 시점)를 가진 행이 계속 누적된다.

```
005930, bas_dt=2023-01-15  (1월 실행분)
005930, bas_dt=2023-02-10  (2월 실행분)
005930, bas_dt=2023-03-05  (3월 실행분)
```

**왜 더 심하게 불어났나** — 카티전 곱: `join_momentum`은 조인을 두 번 연쇄한다.

```python
df = df.join(p1m, on="stock_code", how="left").join(p12m, on="stock_code", how="left")
```

```
1단계: df(1행) join p1m(3행 중복) → 3행으로 불어남
2단계: 그 3행 각각이 p12m(예: 5행 중복)과 또 조인
       → 3행 × 5행 = 15행으로 곱해짐
```

실측 결과: 2021년 기준 55,182행 (실제 종목수 2,368) — 종목당 최대 50행까지 중복.

**해결법 — `_latest_snapshot()`**:

```python
def _latest_snapshot(prices: DataFrame) -> DataFrame:
    w = Window.partitionBy("stock_code").orderBy(F.desc("bas_dt"))
    return prices.withColumn("_rank", F.row_number().over(w)).filter(F.col("_rank") == 1).drop("_rank")
```

5단계에서 배운 `Window` 그대로다 — `partitionBy("stock_code")`로 종목별로 나누고, `orderBy(F.desc("bas_dt"))`로 최신순 정렬한 뒤, `row_number() == 1`로 종목당 가장 최근 것 1건만 남긴다. 양쪽(`p1m`, `p12m`) 모두에 이걸 적용해 조인 상대편의 중복을 원천 제거하면, fan-out이 안 생긴다.

```
_latest_snapshot() 적용 후:
  df(1행) join p1m(1행, 중복 제거됨) → 1행
  1행 join p12m(1행, 중복 제거됨) → 1행 (곱해지지 않음)
```

## 8. 정리

```
브로드캐스트 조인: 작은 쪽 데이터를 워커 단위로 통째로 복제해서
                  조인 시 큰 쪽의 셔플(재배치)을 생략하는 방법
                  판단 기준: spark.sql.autoBroadcastJoinThreshold (이 리포 10MB)
                  개별 강제: F.broadcast() 힌트

.explain() 확인:  BroadcastHashJoin = 조인이 브로드캐스트로 실행됨
                  BroadcastExchange = 복제해서 뿌리는 지점 (셔플의 Exchange와 이름만 닮음, 동작은 "재배치"가
                  아니라 "복제")
                  브로드캐스트를 써도, 작은 쪽을 "만드는 과정"의 별개 셔플(예: distinct())은 그대로 남을 수 있다

브로드캐스트가 항상 좋지 않은 이유:
                  워커 수만큼 복사본이 생겨 메모리 낭비가 커짐
                  "작은 쪽"이 실제로 작지 않으면 워커 OOM

fan-out:          조인 상대편에 같은 키의 중복 행이 있으면 그만큼 결과가 곱해지는 현상
                  조인 방식(셔플/브로드캐스트)과 무관하게 발생 (조인의 기본 성질)
                  이 리포 사례: 01번 append 재실행으로 쌓인 가격 스냅샷 중복 → join_momentum에서
                  조인 두 번 연쇄되며 곱셈으로 폭증 (55,182행 vs 실제 2,368종목)
                  해결: Window(partitionBy+orderBy+row_number)로 조인 전에 중복을 미리 제거
```

## 7단계에서 다룰 것

**주제: 성능 — 왜 워커를 늘려도 빨라지지 않는가**

4단계에서 이미 "코어 8개인데 파티션이 4개면 절반이 논다"는 걸 다뤘다. 이번 장은 이걸 포함해 워커 확장이 실제로 성능에 미치는 영향을 정리하고, 미완으로 남아있는 워커 2대 vs 4대 벤치마크(PROGRESS.md)를 실측으로 완성하는 게 목표다.

1. 워커를 늘렸는데 왜 그대로인 경우 — 파티션 수, 셔플, 브로드캐스트 임계값이 여전히 예전 설정인 경우
2. AQE가 파티션을 자동으로 줄이는 것과 "워커를 늘렸다"는 게 충돌하는 지점 (4단계에서 실측한 내용과 연결)
3. 메모리 산정 — 워커 메모리 합 + 드라이버 메모리가 호스트 총 메모리를 넘지 않는지 사전 계산
4. 04번 실제 실행 시간 실측 (튜닝 전/후, 워커 2대/4대)
