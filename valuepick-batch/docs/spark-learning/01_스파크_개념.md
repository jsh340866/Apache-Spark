# 1단계. Spark 개념 — 쪼갠다, 그리고 대가를 치른다

> 학습 로드맵
> ```
> 1단계  Spark가 대체 뭘 하는 물건인가        ← 이 문서
> 2단계  파티션 — 데이터가 쪼개져 있다는 것
> 3단계  지연 실행 — 안 하고 미뤘다가 몰아서 한다
> 4단계  셔플 — 쪼갠 걸 다시 섞는 비싼 작업
> 5단계  그래서 순서가 안 지켜진다 (본 리포 버그 3건의 정체)
> 6단계  조인 전략 / 브로드캐스트
> 7단계  성능 — 왜 워커를 늘려도 빨라지지 않는가
> ```

## 1. Spark 없이 하면 뭐가 문제인가

이 프로젝트의 시세 데이터 규모:

- 종목 2,555개
- 3년치 거래일 737일
- **약 188만 행**

pandas로 하면 이렇게 된다.

```python
df = pd.read_parquet("prices")   # 188만 행을 램에 통째로
df = df.sort_values(["stock_code", "bas_dt"])
df["prev_close"] = df.groupby("stock_code")["close_price"].shift(1)
```

돌아간다. 188만 행이면 pandas도 충분하다. 문제는 두 가지다.

**문제 1 — 램에 다 올려야 한다.** 데이터가 10배, 100배가 되면 램이 터진다. 터지면 죽는다. 우회로가 없다.

**문제 2 — 코어 1개만 쓴다.** CPU에 코어가 4개, 8개 있어도 pandas는 기본적으로 1개만 쓴다. 나머지는 논다.

## 2. Spark의 답 — 쪼개서 나눠준다

```
[pandas]
  188만 행 ────────→ 코어 1개가 전부
                     (램에 다 올려야 함)

[Spark]
  188만 행
    ├─ 조각1 (47만) ──→ 코어 A
    ├─ 조각2 (47만) ──→ 코어 B
    ├─ 조각3 (47만) ──→ 코어 C
    └─ 조각4 (47만) ──→ 코어 D
                     (조각 하나씩만 램에 올리면 됨)
```

이 **조각 하나**가 **파티션(partition)** 이다.

### 여기서 모든 게 갈라져 나온다

Spark의 거의 모든 특성이 "쪼개져 있다"는 사실 하나에서 나온다.

- 쪼개져 있으니 → 여러 코어가 동시에 처리 (빠름)
- 쪼개져 있으니 → 조각 하나만 램에 올리면 됨 (큰 데이터 가능)
- 쪼개져 있으니 → **조각끼리 데이터를 주고받아야 할 때가 생김** (셔플, 4단계)
- 쪼개져 있으니 → **전체 순서라는 게 없음** (버그의 원인, 5단계)

**장점만 오는 게 아니라 대가가 같이 붙어온다.** Spark를 어렵게 만드는 건 전부 대가 쪽이다.

## 3. 독립적 작업 vs 비독립적 작업

Spark를 쓸지 말지, 그리고 빠를지 느릴지를 가르는 기준.

### 독립적 — 한 행 안에서 끝난다

`jobs/03_build_indicators.py:258`

```python
df = df.withColumn("per", F.when(F.col("eps") > 0, F.round(F.col("close_price") / F.col("eps"), 2)))
```

**한 행 안에서** `close_price`와 `eps`를 나눈다. 다른 행을 안 본다.

```
PER = 주가 ÷ EPS
EPS = 당기순이익 ÷ 발행주식수
```

삼성전자 PER을 구하는 데 필요한 건 전부 삼성전자 것뿐이다. SK하이닉스 주가를 몰라도 삼성전자 PER은 나온다. ROE(순이익÷자기자본), PBR(주가÷BPS)도 같다.

### 비독립적 — 여러 행을 모아야 한다

비교나 순위가 들어가는 순간 독립성이 깨진다.

- "PER 낮은 순 상위 10종목" → 전 종목을 다 봐야 순위가 나옴
- "업종 평균 PER 대비 저평가" → 같은 업종 전부 필요
- "시장 전체 PER 중앙값" → 전 종목 필요

`jobs/04_backtest_grid.py`의 종목 선정이 여기 해당한다 (PROGRESS.md 70줄):

> 종목 선정: 조건 만족 종목 중 **PER 낮은 순 상위 N종목**, 동일비중

```
[독립적] 03번 PER 계산
  조각1: 삼성전자 → 주가÷EPS     ┐
  조각2: 하이닉스 → 주가÷EPS     ├ 서로 대화 없음. 각자 끝.
  조각3: 현대차   → 주가÷EPS     ┘
                                 → 빠름

[비독립적] 04번 PER 낮은 순 상위 10
  조각1: 삼성전자 PER=12  ┐
  조각2: 하이닉스 PER=8   ├ 전부 한자리에 모아야 줄을 세움
  조각3: 현대차 PER=5     ┘
                          → 데이터가 네트워크를 타고 이동 (셔플)
                          → 느림
```

## 4. 셔플 — 공이 상자를 갈아탄다

### 조각 안에는 칸막이가 없다

흔한 오해: "조각 안에 종목별로 칸막이가 쳐져 있다" — **아니다.**

조각 안은 그냥 행이 쭉 있는 상태다.

```
조각1의 실제 모습:

  005930  20210104  81000
  000660  20210104  126000
  005930  20210105  82900     ← 삼성 행이 하이닉스 행 사이에 끼어 있음
  000660  20210105  128000
  005930  20210106  82200
```

종목별로 모여 있지도 않고, 날짜순도 아니다. 그냥 섞여 있다.

### 재배치가 일어나는 시점

`jobs/02_clean_prices.py:51`

```python
w = Window.partitionBy("stock_code").orderBy("bas_dt")
```

이 줄이 Spark에게 시키는 것:

> "지금부터 계산할 건데, **종목코드가 같은 것끼리 묶고**, 그 안에서 **날짜순으로 정렬**해서 봐."

Spark가 이 시점에 데이터를 재배치한다.

```
[Window 적용 전]        [Window 적용 후]
005930  20210104        005930  20210104  ┐
000660  20210104        005930  20210105  ├ 삼성 묶음, 날짜순
005930  20210105   →    005930  20210106  ┘
000660  20210105        000660  20210104  ┐
005930  20210106        000660  20210105  ├ 하이닉스 묶음, 날짜순
                                          ┘
```

**이 재배치가 셔플(shuffle)이다.**

### 정렬이 아니라 이사다

셔플을 "각 조각 안에서 줄을 다시 세우는 것"으로 이해하면 틀린다. **데이터가 조각을 옮겨 다닌다.**

```
[셔플 전] 원래 조각              [셔플 후] 새 조각
  상자1: 🔴🔵🟡  ─┐          ┌→ 새상자1: 🔴🔴🔴🔴
  상자2: 🔵🟡🔴  ─┼─ 전부 ─┼→ 새상자2: 🔵🔵🔵🔵
  상자3: 🟡🟢🔴  ─┼─ 다시 ─┼→ 새상자3: 🟡🟡🟡🟡
  상자4: 🟢🔴🔵  ─┘  배분  └→ 새상자4: 🟢🟢🟢🟢
```

원래 상자를 정리하는 게 아니라 **상자를 새로 만들어서 전부 옮겨 담는다.**

### 왜 비싼가

조각이 서로 다른 프로세스(worker-1, worker-2)에 있어서 데이터 이동이 네트워크를 탄다.

```
worker-1 ─── 상자1, 상자2
                ↕  데이터가 여기를 건너감 (네트워크)
worker-2 ─── 상자3, 상자4
```

옮기는 과정:

1. 각 행이 어느 조각으로 갈지 계산
2. 디스크에 임시로 쓰기
3. 네트워크로 전송
4. 받아서 다시 읽기

**계산보다 옮기는 데 시간이 더 든다.** Spark에서 제일 비싼 작업이 셔플인 이유.

### 왜 굳이 하는가

안 하면 계산이 **틀리기 때문**이다.

빨간 공이 상자1, 2, 3에 흩어져 있을 때 "빨간 공이 몇 개냐"를 세면:

- 상자1이 세면 → 2개
- 상자2가 세면 → 1개
- 상자3이 세면 → 1개

각자 다른 답이 나온다. 아무도 4개라는 걸 모른다.

같은 얘기로, 삼성전자 737일치가 세 조각에 흩어져 있으면 **"직전 종가"를 못 구한다.** 조각1이 1월 5일 종가를 갖고 있는데 1월 4일 종가가 조각3에 있으면 끌어올 수가 없다.

**같은 종목은 반드시 같은 조각에 모여야 하고, 그러려면 이사가 필수다.**

### partitionBy와 orderBy는 다른 단계

```python
Window.partitionBy("stock_code").orderBy("bas_dt")
         ↑ 기준별로 이사        ↑ 조각 안에서 정렬
```

1. `partitionBy("stock_code")` — 같은 종목끼리 같은 조각으로 **이사** (비쌈)
2. `orderBy("bas_dt")` — 조각 안에서 날짜순 **정렬** (쌈)

정렬은 조각 안에서만 일어나고 조각을 넘나들지 않는다.

### 용어 주의

`shuffle`이라는 단어 때문에 "무작위로 뒤섞는다"로 읽히기 쉬운데 **정반대다.** 기준에 따라 정확하게 모으는 작업이다. 빨간 건 반드시 상자1로, 파란 건 반드시 상자2로. 규칙이 있다. "재배치"로 기억하는 게 낫다.

## 5. 셔플은 코드에 안 보인다

셔플은 직접 호출하는 게 아니다. **Spark가 판단해서 자동으로 끼워 넣는다.**

```python
w = Window.partitionBy("stock_code").orderBy("bas_dt")
```

여기서 요청한 건 "종목별로 날짜순 보고 계산해줘"다. "셔플해라"라고 쓰지 않았다.

Spark가 이걸 받고 *"이거 하려면 같은 종목이 한 조각에 모여 있어야 하는데 지금 흩어져 있네. 셔플해야겠다"* 라고 판단한다.

**그래서 `df.shuffle()` 같은 건 코드에 없고, 어디서 셔플이 일어나는지 모른 채 느린 잡을 만들기 쉽다.** 실행 계획을 봐야 보인다 (3단계 이후).

### 셔플이 일어나는 조건

> **"다른 조각에 있는 데이터를 봐야 하는 순간" 셔플이 일어난다.**

| 코드 | 셔플? | 이유 |
|---|---|---|
| `df.filter(price > 1000)` | 안 남 | 자기 행만 보면 됨 |
| `df.withColumn("per", price/eps)` | 안 남 | 자기 행 안에서 나눗셈 |
| `Window.partitionBy("stock_code")` | **남** | 같은 종목을 한 조각에 모아야 함 |
| `df.groupBy("stock_code").agg(...)` | **남** | 같은 종목을 한 조각에 모아야 함 |
| `df1.join(df2, on="stock_code")` | **남** | 양쪽의 같은 종목을 한 조각에 모아야 함 |
| `df.orderBy("per")` | **남** | 전체 순위는 다 모아야 나옴 |

위 두 개와 아래 네 개의 차이는 **자기 행만 보면 되는가, 남의 행을 봐야 하는가**다. 3장의 독립적/비독립적과 정확히 같은 구분이다.

### 판단 단위는 "조각"이 아니라 "행"이다

흔한 오해: "filter는 조각 하나를 본다" — **아니다. 행 하나를 본다.**

```python
df.filter(F.col("close_price") > 1000)
```

```
조각1을 처리할 때:

  005930  20210104  81000   → 81000 > 1000?  O  통과
  000660  20210104  126000  → 126000 > 1000? O  통과
  005930  20210105  700     → 700 > 1000?    X  버림
  000660  20210105  128000  → 128000 > 1000? O  통과
        ↑
  한 행씩, 그 행의 값만 보고 판단. 다른 행 값은 전혀 안 봄
```

세 번째 행을 버릴 때 첫 번째 행 값을 참고하지 않는다. **행끼리도 서로 안 본다.**

이 구분이 중요한 이유 — "조각 하나를 본다"고 이해하면 이런 게 가능할 것처럼 들린다.

```python
# 조각 안의 평균보다 높은 행만 남기기?
df.filter(F.col("close_price") > 조각_평균)   ← filter로는 안 됨
```

평균을 구하려면 그 조각의 **모든 행**을 봐야 하는데 `filter`는 행 하나만 본다. 이걸 하려면 `groupBy`나 `Window`를 써야 하고, 그 순간 셔플이 붙는다.

```
1. 행 하나만 본다          → filter, withColumn, when
                             셔플 없음. 제일 쌈

2. 여러 행을 모아야 한다   → groupBy, join, Window, orderBy
                             2-a. 이미 그 기준으로 모여 있음 → 셔플 생략
                             2-b. 흩어져 있음               → 셔플 발생 (보통의 경우)
```

### 조각은 몇 개 생기나

셔플이 실제로 일어날 때마다 새 조각 세트가 만들어진다.

```python
df1 = df.groupBy("stock_code").agg(...)      # 셔플 1 → 새 조각
df2 = df1.join(other, on="corp_cls")         # 셔플 2 → 또 새 조각
df3 = df2.orderBy("per")                     # 셔플 3 → 또 새 조각
```

반면 `filter`는 행만 줄어들 뿐 조각 수도, 조각의 위치도 그대로다.

```
[filter — 셔플 없음]
  조각1: 5행 → 걸러서 3행    (제자리)
  조각2: 5행 → 걸러서 2행    (제자리)
  조각3: 5행 → 걸러서 4행    (제자리)
  조각4: 5행 → 걸러서 1행    (제자리)
              ↑ 데이터가 이동하지 않음. 조각 수도 그대로 4개
```

주의할 점은 **조건식이 있냐 없냐가 기준이 아니라는 것**이다.

- `03:258`의 `F.when(F.col("eps") > 0, ...)` — 조건식이 있지만 셔플 **없음** (자기 행만 봄)
- `02:47`의 `full_grid.join(prices, on=["stock_code", "bas_dt"])` — 조건식이 없지만 셔플 **있음** (양쪽의 같은 키를 모아야 함)

### 기준이 무엇인지는 코드가 정한다

`stock_code`가 특별한 게 아니라, 02번 잡이 그렇게 쓴 것뿐이다.

```python
Window.partitionBy("stock_code")   → stock_code 기준으로 담음
Window.partitionBy("bas_dt")       → 날짜 기준으로 담음
groupBy("corp_cls")                → 시장구분 기준으로 담음
df.filter(price > 1000)            → 셔플 자체가 안 일어남
```

기준이 같으면 재배치를 재사용할 수 있고, 다르면 또 셔플해야 한다. `02_clean_prices.py`는 51번 줄과 68번 줄 모두 `stock_code` 기준이라 이 점에서 유리하다.

## 6. 파티션 수는 데이터가 아니라 하드웨어에 맞춘다

종목이 2,555개라고 조각이 2,555개가 되는 게 아니다. 이 프로젝트는 **4개**다.

`conf/spark-defaults.conf`

```
# worker-1, worker-2 각 2코어 = 총 4코어 -> shuffle partition 기본값(200)이 과도하므로 축소
spark.sql.shuffle.partitions          4
```

**코어가 4개니까 조각도 4개.**

조각 하나에 여러 종목이 같이 들어간다.

```
[상상] 종목별로 1조각씩          [실제] 4조각
  조각1: 삼성전자 (737행)          조각1: 약 640종목, 47만 행
  조각2: 하이닉스 (737행)          조각2: 약 640종목, 47만 행
  ...                              조각3: 약 640종목, 47만 행
  조각2555: (737행)                조각4: 약 640종목, 47만 행
```

### 왜 2,555개로 안 하는가

조각을 2,555개로 나눠도 코어는 4개뿐이라 동시성은 여전히 4다. 그런데 조각마다 **관리 비용**(태스크 생성, 워커 전송, 결과 수집)이 붙는다.

```
[4조각]     계산 47만행 ████████  관리 ▪
[2555조각]  계산 737행  ▪         관리 ████████████
                                  ↑ 배보다 배꼽이 큼
```

> 자세한 내용은 2단계에서.

## 7. 정리

```
1. Spark는 데이터를 지정한 개수(이 리포: 4)로 쪼갠다
2. 각 조각에는 데이터가 무작위로 섞여 담긴다. 종목별 칸막이 같은 건 없다
3. 남의 행을 봐야 하는 연산을 만나면
   → 그 연산이 지정한 기준(02번은 stock_code)으로
4. 기존 조각이 아닌 새 조각에 기준별로 전량 옮겨 담는다  ← 셔플, 네트워크를 타므로 비쌈
5. 옮기고 나면 기준별 독립 계산이 가능하다
6. 셔플은 코드에 안 보인다. Spark가 알아서 끼워 넣는다
```

### 한 줄 요약

> **Spark 성능 튜닝 = 셔플을 줄이거나 싸게 만드는 것**

앞으로 나올 브로드캐스트 조인(6단계), 파티션 수 조정(2단계), 캐싱 — 전부 이 한 줄의 변주다.

### 다음 단계로 넘어가는 실마리

셔플로 데이터를 모을 때, 조각1·조각2·조각3의 데이터가 새 조각으로 모인다. **그런데 어느 조각 것이 먼저 도착하는지는 아무도 모른다.** 네트워크 상황에 따라 매번 달라진다.

그래서 도착한 뒤 "첫 번째 값 가져와"(`F.first()`)를 하면 **매번 다른 값이 나올 수 있다.**

이것이 이 리포에서 3회 발생한 버그의 정체다 (PROGRESS.md 51, 58, 73줄). → **5단계**
