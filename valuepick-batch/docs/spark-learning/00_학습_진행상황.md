3. 결론보다 과정
4. 항상 이 프로젝트의 실제 코드로 연결
5. 가능하면 직접 확인할 실험을 제안

**진행 방식**: Claude가 설명 → 내가 내 말로 다시 정리 → 틀린 부분 교정 → 문서화

## 지금까지 이해한 것 (핵심만)

### 1단계

```
Spark는 데이터를 지정한 개수(이 리포: 4)로 쪼갠다
각 파티션에는 데이터가 무작위로 섞여 담긴다. 종목별 칸막이 같은 건 없다
남의 행을 봐야 하는 연산을 만나면
  → 그 연산이 지정한 기준(02번은 stock_code)으로
  → 기존 파티션이 아닌 새 파티션에 전량 옮겨 담는다  ← 셔플, 비쌈
셔플은 코드에 안 보인다. Spark가 알아서 끼워 넣는다
```

판단 단위는 **파티션이 아니라 행**이다.

```
filter, withColumn, when   → 행 하나만 봄. 셔플 없음
groupBy, join, Window      → 여러 행을 모아야 함. 셔플 발생
```

조건식이 있냐 없냐가 기준이 아니다. `F.when`은 조건식이지만 셔플 없고, `join`은 조건식 없이도 셔플이 난다.

> **Spark 성능 튜닝 = 셔플을 줄이거나 싸게 만드는 것**

### 2단계

```
코어 1개 = 한 번에 파티션 1개 (쪼갤 수 없는 최소 단위)
이 리포는 워커 2대 × 2코어 = 총 4코어 → shuffle.partitions = 4

파티션 < 코어  → 코어가 논다
파티션 >> 코어 → 태스크 관리비가 계산보다 커진다
실무 기준은 코어 수 × 2~4
```

파티션 수는 단계마다 다르다.

```
파일 읽기 직후 → 파일 개수/크기가 정함 (shuffle.partitions와 무관)
셔플 이후      → shuffle.partitions가 정함
```

`groupBy`는 행들의 요약(행 줄어듦), `Window.partitionBy`는 각 행에 정보 추가(행 유지).

DataFrame은 **불변**이다. `raw = raw.filter(...)`는 원본 변경이 아니라 이름표 이동.
Spark는 중간 결과를 안 들고 있고 **lineage(만드는 법)** 만 기억한다. → 04번 OOM의 원인.

## 3단계에서 다룰 것 (다음 세션 시작점)

**주제: 지연 실행 (lazy evaluation)**

2단계 9장에서 절반쯤 들어갔다. 이어서 볼 질문들:

1. Spark는 왜 연산을 즉시 실행하지 않고 미루는가
2. **transformation vs action** — `filter`는 아무 일도 안 일어나고 `count()`는 실행된다. 이 구분이 핵심
3. `.count()`가 왜 lineage를 끊는가 (04번 OOM 해결책의 원리)
4. 미뤄둔 덕분에 Spark가 할 수 있는 최적화 (predicate pushdown 등)
5. 실행 계획을 눈으로 보는 법 — `df.explain()`, Spark UI(`localhost:4040`)

**연결되는 실제 이슈**: PROGRESS.md 71줄 04번 드라이버 OOM. 데이터가 커서가 아니라 lineage 48겹이 드라이버 메모리를 먹어서 터진 사건.

## 미뤄둔 실습 (Docker 필요)

집 컴퓨터에서 Docker를 못 띄워 넘어간 것들. 클러스터 뜨면 해볼 것.

```python
# 1. 파티션 수가 단계마다 다른 것 확인
raw = spark.read.parquet("/opt/spark-apps/data/cleaned/prices")
print("읽었을 때:", raw.rdd.getNumPartitions())      # 4가 아닐 것

grouped = raw.groupBy("stock_code").count()
print("셔플 후:", grouped.rdd.getNumPartitions())    # 4

# 2. 3단계에서 쓸 것 — 실행 계획 보기
raw.filter(...).explain()
```

클러스터 기동:

```bash
cd valuepick-batch/docker
docker compose up -d
# Spark 마스터 UI: http://localhost:8088
# Jupyter:        http://localhost:8888
```

### 워커 벤치마크 재시도 시 체크리스트 (2단계에서 도출)

PROGRESS.md 97줄 사건이 두 번 실패한 이유:

```
1. 메모리 산수
   워커 2G×2 + 워커 1G×2 + 드라이버 3G = 9GB > 호스트 7.7GB  ← 터진 원인
   → 워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리로 사전 계산

2. shuffle.partitions도 같이 변경  ← PROGRESS.md에 없는 항목
   워커 2대(4코어) → 4
   워커 4대(8코어) → 8
   안 바꾸면 늘어난 코어 4개가 놀아서 벤치마크가 무의미해진다
```
