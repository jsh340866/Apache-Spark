## 지금까지 이해한 것 (핵심만)

### 1단계

```
Spark는 데이터를 지정한 개수(이 리포: 4)로 쪼갠다
각 파티션에는 데이터가 무작위로 섞여 담긴다. 종목별 칸막이 같은 건 없다
남의 행을 봐야 하는 연산을 만나면
  → 그 연산이 지정한 기준(02번은 stock_code)으로
  → 기존 파티션이 아닌 새 파티션에 전량 옮겨 담는다  ← 셔플, 비쌈
셔플은 코드에 안 보인다. Spark가 알아서 끼워 넣는다
```

판단 단위는 **파티션이 아니라 행**이다.

```
filter, withColumn, when   → 행 하나만 봄. 셔플 없음
groupBy, join, Window      → 여러 행을 모아야 함. 셔플 발생
```

조건식이 있냐 없냐가 기준이 아니다. `F.when`은 조건식이지만 셔플 없고, `join`은 조건식 없이도 셔플이 난다.

> **Spark 성능 튜닝 = 셔플을 줄이거나 싸게 만드는 것**

### 2단계

```
코어 1개 = 한 번에 파티션 1개 (쪼갤 수 없는 최소 단위)
이 리포는 워커 2대 × 2코어 = 총 4코어 → shuffle.partitions = 4

파티션 < 코어  → 코어가 논다
파티션 >> 코어 → 태스크 관리비가 계산보다 커진다
실무 기준은 코어 수 × 2~4
```

파티션 수는 단계마다 다르다.

```
파일 읽기 직후 → 파일 개수/크기가 정함 (shuffle.partitions와 무관)
셔플 이후      → shuffle.partitions가 정함
```

`groupBy`는 행들의 요약(행 줄어듦), `Window.partitionBy`는 각 행에 정보 추가(행 유지).

DataFrame은 **불변**이다. `raw = raw.filter(...)`는 원본 변경이 아니라 이름표 이동.
Spark는 중간 결과를 안 들고 있고 **lineage(만드는 법)** 만 기억한다. → 04번 OOM의 원인.

### 3단계

```
transformation: DataFrame → DataFrame. 레시피만 늘어남. 실행 안 됨
                (filter, withColumn, select, groupBy, join, cache 포함)
action:         DataFrame → 그 외의 것. 지금까지의 레시피 전체가 실행됨
                (count, collect, show, write)
```

미루는 이유는 게을러서가 아니라, action 전까지 레시피 전체를 미리 보고 최적화하기 위해서다 (predicate pushdown, 컬럼 pruning). `.explain()`으로 실제 실행 계획(FileScan의 PartitionFilters 등)을 눈으로 확인 가능.

`.cache()`도 transformation이라 그 자체로는 저장이 안 된다. "여기서부터 저장해두라"는 포스트잇만 붙을 뿐, 뒤따르는 action이 있어야 실제로 메모리에 올라간다. action 없이 다음 transformation으로 계속 넘어가면, 캐시가 안 붙은 채로 그 위에 새 레시피가 계속 얹혀 무한정 길어질 수 있다 — 이게 04번 OOM(Out Of Memory, 메모리 부족으로 프로세스가 죽는 에러)의 정체였다. `.cache()` 직후 `.count()`를 붙이는 이유는 그 시점 레시피를 즉시 실행·고정해 끊기 위함. 단, 이건 계산량 자체를 줄이는 게 아니라 "안 죽고 끝까지 돌게" 만드는 안전장치라 04번이 오래 걸리는 이유와는 별개다.

### 4단계

```
셔플이 비싼 이유: 워커는 서로 다른 프로세스라, 셔플이 일어나면
                디스크 쓰기(shuffle write) → 네트워크 전송 → 디스크 읽기(shuffle read)가 붙는다
                (filter/withColumn은 메모리 안에서 끝나는 것과 대비)
                파티션이 데이터량에 비해 너무 많으면 이 관리 비용이 계산 비용보다 커진다 (트럭 비유)
```

`.explain()`에서 `Exchange hashpartitioning(...)` 노드가 셔플의 흔적. `HashAggregate`가 셔플 앞뒤로 두 번 나오는 건 부분집계 → 셔플 → 최종집계 구조.

**실측으로 확인한 것 — AQE(Adaptive Query Execution)**: `spark.sql.shuffle.partitions`(conf 파일 값 4)는 Jupyter에서 `SparkSession.builder(...)`로 직접 세션을 만들면 안 읽혀서 Spark 기본값 200이 적용된다. 그런데 실제 `groupBy` 결과 파티션 수는 200일 때도 4로 바꿨을 때도 **1**이었다 — Spark 3.x부터 기본 켜진 AQE가 `shuffle.partitions`를 "상한선"으로만 쓰고 실행 중 데이터 양을 보고 자동으로 줄이기 때문. `spark.sql.adaptive.enabled=false`로 끄면 설정값(4)이 그대로 적용됨을 실측 확인.

**정정**: 2단계에서 "셔플 이후 파티션 수는 shuffle.partitions가 정한다"고 했는데, 정확히는 "AQE가 꺼져 있을 때만"이라는 단서가 필요하다.

**미해결**: 이 리포는 코어 4개에 맞춰 `shuffle.partitions=4`를 일부러 지정해뒀는데, AQE가 이걸 4보다 더 줄이면 오히려 일부 코어가 놀 수 있다 (파티션 < 코어 문제, 2단계). 04번을 `spark-submit`으로 정상 실행했을 때 AQE가 실제로 얼마나 줄이는지는 아직 미실측.

### 5단계

```
셔플이 보장하는 것:    같은 그룹 키(stock_code 등)의 행은 반드시 같은 파티션에 모인다
셔플이 보장 안 하는 것: 그 파티션 안 행의 순서 — 네트워크 도착 순서라 매 실행마다 다를 수 있음

비결정성 = 같은 코드·데이터인데 실행마다 결과가 달라질 수 있는 성질
         groupBy().agg(F.first()/F.last())는 정렬 기준을 줄 방법이 없어 비결정적
         → 이 리포에서 세 번 반복된 버그(03번 join_momentum, 03번 배당, 04번 summarize_performance)의 공통 원인
```

`Window`는 함수가 아니라 "계산 범위(그룹+정렬)를 정의하는 설정값" — `.over(w)`로 다른 함수와 결합해야 실제 계산이 일어난다. `groupBy`(행 축소, 요약)와 달리 `Window`는 행 개수를 유지한 채 각 행에 정보를 추가한다(2단계 내용과 연결).

```
해결법: Window.partitionBy(...).orderBy(...) 로 그룹 안 정렬 기준을 명시
       rowsBetween(unboundedPreceding, unboundedFollowing)으로 전체 범위를 보게 하면
       F.first()/F.last()가 정렬 기준상 진짜 첫/마지막 값을 결정적으로 뽑음
```

실제 코드: `04_backtest_grid.py:217-240` `summarize_performance` — `Window.partitionBy("name").orderBy("period_start")` 위에서 `F.last("cum_return").over(w_full)`로 마지막 구간 값을 결정적으로 채움. `PARTITION BY`/`ORDER BY`/`ROWS BETWEEN`은 SQL 윈도우 함수 문법과 1:1 대응.

### 6단계

```
브로드캐스트 조인 = 작은 쪽 데이터를 워커 단위로 통째로 복제해서
                   조인 시 큰 쪽의 셔플(재배치)을 생략하는 방법
                   판단 기준: spark.sql.autoBroadcastJoinThreshold (이 리포 10MB), 개별 강제는 F.broadcast() 힌트
```

JPA의 N+1 문제(순회하며 개별 쿼리 N번) → `JOIN FETCH`(한 번에 합쳐서 가져옴)와 같은 발상. "필요한 걸 나중에 나눠서 개별 요청하지 말고 미리 합쳐서 곁에 둔다"는 점에서 동일.

`.explain()` 실측(04_backtest_grid.py:311의 `F.broadcast(market_codes)` 재현): `BroadcastHashJoin`이 조인 자체가 브로드캐스트로 실행됐다는 증거, `BroadcastExchange`는 복제(셔플의 `Exchange`와 이름은 닮았지만 "재배치"가 아닌 "복제"). 단, 작은 쪽을 만드는 과정(`distinct()`)에는 별개의 작은 셔플이 여전히 남아있을 수 있다 — 조인 자체의 셔플 생략과 데이터 준비 과정의 셔플은 별개.

**fan-out**: 조인 상대편에 같은 키의 중복 행이 있으면 그만큼 결과가 곱해지는 현상. 조인 방식(셔플/브로드캐스트)과 무관하게 발생하는 조인의 기본 성질. 이 리포 실제 사례 — 01번을 `append`로 여러 번 재실행하며 같은 stock_code의 가격 스냅샷이 중복 축적 → `join_momentum`에서 조인 두 번이 연쇄되며 곱셈으로 폭증(2021년 55,182행 vs 실제 2,368종목). `_latest_snapshot()`(Window: partitionBy+orderBy+row_number)로 조인 전 중복을 미리 제거해 해결.

### 7단계 (개념 정리만, 실측은 아직)

```
워커만 늘리고 shuffle.partitions를 안 바꾸면:
  읽기 단계 → 원본 파일 조각 수가 충분하면 워커 확장 효과 그대로 반영 (2단계, shuffle.partitions와 무관)
  셔플 단계 → 여전히 예전 파티션 수에 묶여 늘린 코어가 놈
```

`shuffle.partitions`도 코어 수에 맞춰 늘려야 함 (기준: 코어 수 × 2~4). 왜 1:1이 아니라 여유를 두는지 — 데이터 쏠림(skew): 파티션 하나에 데이터가 몰리면 나머지 코어가 다 끝내고도 그 파티션 하나 때문에 대기하게 됨. 파티션을 코어 수보다 잘게 나눠두면 빨리 끝난 코어가 남은 파티션을 이어받아 처리해 완충됨.

**그런데 이 튜닝도 무조건 통하지 않음** — 4단계에서 실측한 AQE 동작이 다시 걸림돌이 됨. shuffle.partitions를 늘려도 AQE가 실제 데이터량을 보고 그보다 적게 줄여버릴 수 있어서, **데이터가 작은 단계는 파티션을 늘려봤자 효과 없음**. 데이터가 큰 단계(예: portfolios, 48시점×전략 조합)에서만 워커 확장이 체감됨.

메모리 산정 체크리스트(PROGRESS.md 97줄 실패 사례에서 도출): 워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리를 반드시 사전 계산 (6GB+3GB=9GB > 호스트 7.7GB로 Docker Desktop이 응답 불가에 빠졌던 사례).

**미완료 — 다음에 실측할 것**: `04_backtest_grid.py`를 `spark-submit`으로 정상 실행했을 때 각 셔플 단계의 실제 파티션 수(Spark UI SQL 탭), 튜닝 전/후 실행 시간, 워커 2대 vs 4대 스케일링 비교. 재시도 전 메모리 산정 체크리스트부터 확인.

### 워커 벤치마크 재시도 시 체크리스트 (2단계에서 도출)

PROGRESS.md 97줄 사건이 두 번 실패한 이유:

```
1. 메모리 산수
   워커 2G×2 + 워커 1G×2 + 드라이버 3G = 9GB > 호스트 7.7GB  ← 터진 원인
   → 워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리로 사전 계산

2. shuffle.partitions도 같이 변경  ← PROGRESS.md에 없는 항목
   워커 2대(4코어) → 4
   워커 4대(8코어) → 8
   안 바꾸면 늘어난 코어 4개가 놀아서 벤치마크가 무의미해진다

3. AQE 개입 여부 확인 (4단계에서 실측 확인) ← 2번보다 먼저 볼 것
   shuffle.partitions를 8로 바꿔도 AQE가 실행 중 데이터량을 보고
   그보다 적은 파티션만 쓸 수 있다 (실측: 설정값 200/4 모두 실제론 1로 줄어든 사례 있음)
   벤치마크 시 Spark UI SQL 탭에서 "설정값"이 아니라 "실제 사용된 파티션 수"를 확인해야
   2번 항목이 제대로 적용됐는지 알 수 있다
```

2번(shuffle.partitions 변경 필요성)은 코드에서 추론한 것이었으나, 4단계에서 AQE가 이 설정값을 "상한선"으로만 쓰고 실제로는 자동 조정한다는 걸 실측으로 확인했다. 2번을 적용해도 AQE가 다시 줄여버릴 수 있어 3번(AQE 개입 확인)이 선행돼야 벤치마크가 의미를 가진다.
