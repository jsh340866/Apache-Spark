## 1. 워커만 늘리고 다른 걸 안 바꾸면 — 파티션 병목

이 리포는 워커 2대(각 2코어) = 총 4코어, `shuffle.partitions=4`로 맞춰져 있다. 워커를 4대로 늘리면 코어는 8개가 되지만, `shuffle.partitions`를 그대로 두면:

```
파티션 4개, 코어 8개:
  코어A ──▶ 파티션1
  코어B ──▶ 파티션2
  코어C ──▶ 파티션3
  코어D ──▶ 파티션4
  코어E~H ──▶ (일감 없음, 놈)
```

새로 늘린 코어 4개가 통째로 논다. 워커를 2배로 늘렸는데 **셔플이 일어나는 단계의 속도는 그대로**다.

---

## 2. 그런데 모든 단계가 똑같이 느린 건 아니다 — 읽기 단계 vs 셔플 단계

2단계에서 이미 배운 원리가 있다.

```
파일 읽기 직후 → 파티션 수 = 원본 Parquet 파일 조각 개수 (shuffle.partitions와 무관)
셔플 이후      → 파티션 수 = shuffle.partitions가 정함
```

원본 Parquet 파일이 8개 이상 조각으로 나뉘어 있다면, **파일 읽기 단계**에서는 워커 4대(코어 8개)를 그대로 다 활용할 수 있다. 반면 `groupBy`, `distinct`, `join` 같은 **셔플 단계**에서는 `shuffle.partitions`(그대로 4)에 발이 묶인다.

```
하나의 잡 안에서도 단계별로 병목 지점이 다르다:
  읽기 단계  → 워커 4대 늘린 효과가 그대로 반영됨 (파일 조각 수가 충분하면)
  셔플 단계  → shuffle.partitions를 안 늘렸으면 여전히 4파티션, 코어 4개만 씀
```

전체 실행 시간만 보면 "워커를 늘렸는데 별로 안 빨라졌다"로 보이지만, 실제로는 "일부 단계만 빨라지고 나머지는 그대로"인 경우가 많다.

---

## 3. `shuffle.partitions`도 코어 수에 맞춰 늘려야 한다

2단계 원칙을 다시 가져오면:

```
실무 기준: 파티션 수 = 코어 수 × 2~4
```

워커 4대(코어 8개)로 늘렸다면, `shuffle.partitions`도 8(최소)~32(코어수×4) 사이로 같이 올려야 한다. 이걸 놓치면 PROGRESS.md 2단계 체크리스트에 적힌 대로 "워커 늘렸는데 왜 안 빨라지지?"가 되고 벤치마크 자체가 무의미해진다.

### 왜 코어 수보다 더 많이 잡는가 — 데이터 쏠림(data skew)

파티션 수를 코어 수와 정확히 1:1로 맞추면 위험한 지점이 있다.

```
파티션 8개, 코어 8개 (1:1):
  코어1~7: 각자 파티션 처리, 빨리 끝남
  코어8:   유독 큰 파티션 처리, 오래 걸림 (셔플 기준 컬럼 값 분포가 고르지 않을 때 발생)
  → 코어1~7은 다 끝내고도 코어8이 끝날 때까지 놀면서 대기
  → 전체 작업 시간 = 가장 느린 파티션(코어8) 시간에 좌우됨
```

이런 데이터 쏠림 현상을 **skew**라 부른다. 파티션을 코어 수보다 더 잘게(예: 코어 8개에 파티션 16~32개) 나눠두면, 빨리 끝낸 코어가 계속 다음 남은 파티션을 이어받아 처리하므로 쏠림이 있어도 완충된다. "코어 수 × 2~4"라는 기준의 실제 근거가 이것이다.

## 4. 튜닝해도 소용없는 경우 — AQE가 이미 줄여버린 단계

4단계에서 실측한 사실을 다시 가져온다.

```
4단계 실측: shuffle.partitions를 200으로 두든 4로 두든
           AQE가 실행 중 데이터량을 보고 실제로는 1개로 줄여버렸다 (데이터가 작았으므로)
```

이걸 워커 확장 상황에 대입하면 중요한 결론이 나온다.

```
shuffle.partitions를 코어 수에 맞춰 늘리는 튜닝은
  "셔플 대상 데이터가 충분히 클 때"만 의미가 있다
  데이터가 작으면 AQE가 설정값과 무관하게 알아서 줄여버리므로, 파티션 수를 아무리 늘려도 소용없다
```

그래서 04번처럼 여러 단계로 이루어진 잡 안에서도, 단계마다 워커 확장의 효과가 다르게 나타난다.

```
market_codes.distinct() (몇천 행)
  → 작은 데이터, AQE가 파티션을 확 줄임 → 워커를 늘려도 이 지점은 거의 안 빨라짐

portfolios (48개 리밸런싱 시점 × 종목 × 1,000개 전략 조합, 훨씬 큰 데이터)
  → AQE가 파티션을 덜 줄이거나 안 줄임 → 이 지점은 워커를 늘리면 실제로 빨라질 여지가 있음
```

**결론**: "워커를 늘리면 빨라진다"는 잡 전체가 아니라 **셔플 대상 데이터가 충분히 큰 특정 단계**에만 적용되는 얘기다. 이걸 확인하려면 `.explain()`과 Spark UI의 SQL 탭에서 각 단계가 실제로 실행 시간을 얼마나 잡아먹는지, 파티션이 몇 개로 실행됐는지를 봐야 한다 (아직 실측 전).

## 5. 메모리 산정 — PROGRESS.md 실패 사례

PROGRESS.md 97줄에 기록된 실제 사고: 워커 3/4(각 1G) 추가를 시도했으나 두 번 실패했다.

```
현재:  워커1 2G + 워커2 2G                       = 4GB
시도:  워커1 2G + 워커2 2G + 워커3 1G + 워커4 1G = 6GB
       + 드라이버 3G                              = 9GB

호스트 메모리: 7.7GB
9GB > 7.7GB  ← Docker Desktop/WSL2가 응답 불가에 빠짐
```

Spark 문제가 아니라 산수 문제였다. 재시도 시 체크리스트:

```
1. 메모리 총합 사전 계산
   워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리

2. spark.sql.shuffle.partitions도 같이 변경 (3장 내용)
   워커 2대(4코어) → 8~16
   워커 4대(8코어) → 16~32

3. AQE 개입 여부 확인 (4장 내용) ← 2번보다 먼저 확인
   shuffle.partitions를 늘려도 AQE가 데이터량을 보고 그보다 적은 파티션만 쓸 수 있다
   벤치마크 시 Spark UI SQL 탭에서 "설정값"이 아니라 "실제 사용된 파티션 수"를 확인해야
   2번이 제대로 적용됐는지 알 수 있다
```

## 6. 정리

```
워커만 늘리고 shuffle.partitions를 안 바꾸면:
  읽기 단계  → 원본 파일 조각 수가 충분하면 워커 확장 효과 그대로 반영
  셔플 단계  → 여전히 예전 파티션 수에 묶여 늘린 코어가 놈

shuffle.partitions도 코어 수에 맞춰 늘려야 함:
  기준: 코어 수 × 2~4 (딱 1:1로 맞추면 데이터 쏠림 시 가장 느린 파티션이 전체를 좌우함)

그런데 이 튜닝도 무조건 통하지 않음:
  AQE가 데이터량을 보고 shuffle.partitions 설정값을 무시하고 더 줄여버릴 수 있음(4단계 실측)
  → 데이터가 작은 단계는 파티션을 늘려봤자 효과 없음
  → 데이터가 큰 단계에서만 워커 확장이 실제로 체감됨

메모리 산정 필수:
  워커 메모리 합 + 드라이버 메모리 < 호스트 총 메모리
  (2026-07-30 실패 사례: 6GB + 3GB = 9GB > 호스트 7.7GB로 Docker Desktop 응답 불가)

벤치마크 시 확인 순서:
  1) 메모리 산수부터 안전한지 확인
  2) shuffle.partitions를 늘어난 코어 수에 맞게 조정
  3) AQE가 그 설정을 실제로 얼마나 따르는지 Spark UI SQL 탭에서 실측 확인
  4) 그 다음에야 워커 2대 vs 4대의 실행 시간 비교가 의미를 가짐
```
