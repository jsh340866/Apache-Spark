## 1. DataFrame이란 무엇인가

**DataFrame**은 Spark에서 표 형태 데이터(행과 열이 있는 데이터)를 다루는 자료구조다. 엑셀 시트나 SQL 테이블처럼, 컬럼 이름과 타입이 정해져 있고 그 아래 여러 행이 있는 구조.

```
Parquet   = 디스크에 저장된 파일 포맷 (컬럼 단위로 저장하는 방식)
DataFrame = 그 파일을 Spark 안에서 다루기 위한 표 형태 자료구조
```

`spark.read.parquet(".../prices")`를 호출하면 디스크의 Parquet 파일을 Spark가 다룰 수 있는 DataFrame으로 감싸준다. 원본이 CSV든 JSON든 MySQL 테이블이든, Spark 안에서는 전부 같은 DataFrame 형태로 다뤄진다.

```
비유:
  Parquet   = 창고에 쌓여있는 실제 상자들
  DataFrame = "저 창고에서 이런 규격으로 상자를 꺼내 써라"는 지시서
```

여기서 중요한 포인트 — `raw = spark.read.parquet(...)`를 실행해도 `raw`라는 변수 안에 실제 행 데이터가 들어있는 게 아니다. "이 경로를 이 스키마로 읽어라"는 **레시피의 시작점**만 들어있다 (2단계 lineage 개념 그대로).

---

## 2. transformation — 레시피에 한 줄 추가

```python
raw = spark.read.parquet(".../prices")   # 레시피: "파일 읽기"
df1 = raw.filter(...)                    # 레시피: "파일 읽기 → filter"
df2 = df1.withColumn(...)                # 레시피: "...→ withColumn"
```

`raw`, `df1`, `df2` 전부 DataFrame이다. 다만 각자 담고 있는 레시피 길이가 다를 뿐이다. transformation을 호출할 때마다 레시피가 한 줄 늘어난 **새 DataFrame**이 만들어진다 (2단계 불변성과 같은 원리 — 원본은 안 바뀌고 새 이름표가 붙는다).

```
transformation의 정의: DataFrame을 받아서 새 DataFrame을 돌려주는 메서드
                      예: filter, withColumn, select, groupBy, join, cache
                      → 실제로 실행 안 됨. 레시피만 한 줄 늘어남
```

---

## 3. action — 레시피를 실제로 실행

레시피는 **DataFrame이 아닌 다른 것을 돌려주는 메서드**를 만날 때 실행된다.

```
count()             → 레시피 실행 후 정수 하나
collect()           → 레시피 실행 후 파이썬 리스트
show()              → 레시피 실행 후 화면 출력
write.parquet(...)  → 레시피 실행 후 파일 저장
```

이걸 **action**이라 부른다.

```
구분 기준:
  반환값이 DataFrame이다      → transformation (실행 안 됨)
  반환값이 DataFrame이 아니다  → action (지금까지 쌓인 레시피 전체가 실행됨)
```

`04_backtest_grid.py:391`:

```python
print(f"전략 조합 로드 완료: {strategies.count()}개")
```

`strategies`가 만들어지기까지 여러 transformation을 거치지만 다 안 실행되고 있다가, `.count()`를 만나는 순간 한꺼번에 실행된다.

## 4. 왜 미루나 — 미뤄야 최적화가 가능하다

```python
raw = spark.read.parquet(".../prices")           # 컬럼 10개, 수백만 행
filtered = raw.filter(F.col("year") == 2021)     # year=2021만
result = filtered.select("stock_code", "close")  # 2개 컬럼만
result.show()
```

즉시 실행 방식이라면 1번째 줄에서 이미 전체 컬럼·전체 연도를 다 읽어버린다. 그 다음에 걸러내는 건 늦은 일이다.

`filter`, `select`는 행 하나만 보면 되는 연산이라 셔플이 없다 — 그런데도 미루는 이유는 셔플과는 무관하다. `result.show()`를 만나기 전까지 실행을 미루면, Spark는 그 순간 레시피 전체("결국 2개 컬럼의 2021년치만 있으면 된다")를 미리 보고 있는 상태가 된다. 그래서 필요 없는 `year=2022`, `year=2023` 디렉토리는 **아예 열어보지도 않고**, 필요 없는 컬럼도 디스크에서 안 읽는다.

```
컬럼 10개 중 2개만 읽기   → 컬럼 pruning (가지치기)
year=2021 파티션만 읽기  → predicate pushdown (조건을 읽기 단계로 밀어넣음)
```

**"가져온 다음 거른다"가 아니라 "거를 걸 알고 있으니 처음부터 안 가져온다"**는 차이다. 즉시 실행이었다면 이미 다 읽어버린 뒤라 이런 최적화가 불가능했다.

```
지연 실행을 하는 이유:
  action 전까지 레시피 전체를 미리 볼 수 있어서
  → Spark가 실행 순서를 바꾸거나(predicate pushdown), 안 쓰는 컬럼을 아예 안 읽는 식으로
    실행 계획을 최적화할 수 있다
```

## 5. 실행 계획을 눈으로 보기 — `.explain()`

```python
result.explain()
```

이 리포 데이터로 실행하면 대략 이런 모양이 나온다 (표현은 버전에 따라 다를 수 있음, 직접 실행해서 확인 필요).

```
== Physical Plan ==
*(1) Project [stock_code#12, close#15]
+- *(1) Filter (isnotnull(year#8) AND (year#8 = 2021))
   +- *(1) ColumnarToRow
      +- FileScan parquet [...] PartitionFilters: [isnotnull(year#8), (year#8 = 2021)]
                                  PushedFilters: [...]
```

**읽는 법**: 트리는 아래(안쪽)에서 위(바깥쪽)로 실행된다. 리프 노드가 먼저 계산돼야 그 결과를 바깥 노드가 받아 쓸 수 있기 때문이다.

```
1번째 실행: FileScan   (읽기, PartitionFilters로 year=2021만)
2번째 실행: Filter     (파티션 필터로 못 거른 나머지, 예: null 체크)
3번째 실행: Project    (select)
```

코드에 적은 순서(읽기 → filter → select)와 실행 순서 자체는 같다. 달라진 건 **"filter 조건이 어디서 적용되느냐"**다. `FileScan` 노드 안에 이미 `PartitionFilters: [year#8 = 2021]`이 들어가 있다 — `year=2022`, `year=2023` 디렉토리는 파일 시스템 레벨에서 아예 안 열어본다는 뜻. 4장에서 말한 predicate pushdown이 실제로 적용됐다는 증거다.

`.explain()`은 action이 아니다 — 실행하지 않고 레시피(실행 계획)를 텍스트로 보여주기만 한다.

## 6. `.cache()`는 "예약"일 뿐, 그 자체로는 저장이 안 된다

`.cache()`도 DataFrame을 돌려주는 메서드이므로 **transformation**이다. 그렇다면 transformation의 정의("실행 안 됨, 레시피만 늘어남")가 그대로 적용된다.

```python
df3 = df2.groupBy(...).agg(...).cache()
```

이 줄이 실행돼도 아무 데이터도 안 읽히고 메모리에 아무것도 저장되지 않는다. 레시피에 **"여기서부터는 결과를 저장해두라"는 포스트잇 하나**가 붙을 뿐이다.

```
이 시점 상태:
  레시피: raw읽기 → filter → withColumn → groupBy → agg → [캐시 포스트잇]
  메모리: 아직 비어있음
```

포스트잇이 실제로 실행되려면(=메모리에 진짜 데이터가 올라가려면) 뒤따르는 **action**이 있어야 한다.

```python
df3.count()   # action. 레시피 전체(raw~agg)가 실행되고,
              # 실행 도중 [캐시 포스트잇] 지점을 지나가면서 그 순간의 결과를 메모리에 저장
```

**캐시가 저장하는 단위**: `.cache()`가 붙은 지점 하나의 결과(위 예시라면 `groupBy.agg()` 직후)만 저장된다. `df1`, `df2` 같은 캐시가 안 붙은 중간 단계는 저장 대상이 아니다. 그 뒤에 이어지는 `df3.filter(...)` 같은 것도 캐시 대상이 아니므로, 다시 쓸 때마다 재계산된다.

**캐시가 있을 때와 없을 때의 차이** (같은 `df3`를 여러 번 재사용하는 경우):

```
캐시 없음: df3.count()를 3번 부르면
          매번 raw부터 filter → withColumn → groupBy → agg 전부 재계산 (3번 반복)

캐시 있음: 첫 count()에서 딱 한 번 전체 계산 + 결과를 메모리에 저장
          이후 count()는 raw부터 재계산하지 않고 저장된 결과를 바로 사용
```

## 7. 액션 없이 캐시 지점 위에 레시피가 계속 쌓이면

`.cache()` 뒤에 action 없이 바로 다음 transformation으로 넘어가면 무슨 일이 벌어지는지가 이번 장에서 가장 헷갈렸던 지점이었다.

```python
portfolios = portfolios.cache()          # 캐시 포스트잇. 아직 실행 안 됨 (48번 union 레시피 그대로)
period_returns = calculate_period_returns(portfolios, ...)  # 이 함수 내부도 union을 반복하는 transformation
```

`portfolios`가 아직 "저장된 결과"가 아니라 "48겹 레시피 그 자체"인 상태이므로, `calculate_period_returns`가 만드는 새 레시피는 그 48겹 **위에 그대로 이어붙는다.** 캐시가 뭔가를 "기억"하고 있는 게 아니라, 아직 실행조차 안 된 채로 그 위에 새 레시피가 계속 얹히기만 하는 것이다.

```
액션을 계속 안 만나고 진행 →
  캐시는 여전히 "실행 대기 중"
  캐시를 재료로 삼는 다음 레시피가 그 위에 또 쌓임
  → 다음 레시피가 또 그 위에 쌓임
  → 결국 첫 action을 만나는 시점, 실행해야 할 전체 레시피가 점점 더 길어져 있다
```

`PROGRESS.md` 71줄의 04번 OOM(Out Of Memory, 메모리 부족으로 프로세스가 강제 종료되는 에러) 사건이 정확히 이 패턴이다.

```python
result = None
for date in 48개_시점:
    part = 계산(date)
    result = result.unionByName(part)   # 48번 반복, 전부 transformation
```

48번 union이 다 transformation이라 하나도 실행이 안 된 채 레시피만 48겹으로 쌓이고, 이게 드라이버(우리가 짠 파이썬 코드가 실행되는 프로세스, 워커에게 작업을 지시하고 결과를 모으는 역할)의 메모리 한도를 넘어서 죽어버렸다. **데이터가 커서가 아니라 레시피(계산 계획)가 커서 터진 것.**

## 8. 해결책 — `.cache()` 직후 `.count()`로 즉시 끊기

`04_backtest_grid.py`의 실제 코드:

```python
prices_by_date = prices_at_dates(prices, rebalance_dates).cache()

portfolio_results = []
for rebalance_date in rebalance_dates[:-1]:
    date_prices = prices_by_date.filter(F.col("rebalance_date") == rebalance_date)
    portfolio = screen_portfolio(indicators, date_prices, group_strategies, rebalance_date)
    portfolio_results.append(portfolio)
portfolios = portfolio_results[0]
for p in portfolio_results[1:]:
    portfolios = portfolios.unionByName(p)
portfolios = portfolios.cache()
portfolios.count()  # 캐시를 즉시 실체화해 이후 단계에서 lineage 재계산이 일어나지 않게 함

period_returns = calculate_period_returns(portfolios, prices_by_date, rebalance_dates).cache()
period_returns.count()  # calculate_period_returns 내부도 구간 수만큼 반복 union하므로 여기서 실체화

summary = summarize_performance(period_returns).cache()
summary.count()
```

`.cache()` 바로 뒤에 매번 `.count()`를 붙인 이유는, 그 시점 레시피를 **즉시 실행시켜서 끊어버리기 위해서**다.

```
.cache()만 걸고 넘어감:
  레시피가 다음 단계 위에 계속 얹혀서 무한정 길어짐 → OOM

.cache() 직후 .count():
  그 시점 레시피가 즉시 실행되고 결과가 메모리에 고정됨
  레시피는 여기서 초기화, 다음 단계는 짧은 레시피에서 다시 시작
```

주의할 구분: 이 패턴은 04번을 **느리게 만드는 원인이 아니다.** 04번이 오래 걸리는 주된 이유는 1,000개 전략 × 48개 리밸런싱 시점이라는 계산량 자체다. `.cache()` + `.count()`는 그 계산이 "중간에 안 죽고 끝까지 도는" 것을 보장하는 안전장치이지, 계산량 자체를 줄여주지는 않는다 (캐싱에 드는 저장 비용만큼 오히려 약간 더 걸릴 수 있다).

## 10. 정리

```
DataFrame:       표 형태 자료구조. Parquet 등 원본 파일을 감싸는 지시서
transformation:  DataFrame → DataFrame. 레시피만 늘어남. 실행 안 됨
                 (filter, withColumn, select, groupBy, join, cache 포함)
action:          DataFrame → 그 외의 것. 지금까지의 레시피 전체가 실행됨
                 (count, collect, show, write)

미루는 이유:      action을 만나기 전까지 레시피 전체를 볼 수 있어서
                 Spark가 순서를 바꾸거나(predicate pushdown) 불필요한 컬럼을
                 안 읽는 식(컬럼 pruning)으로 최적화할 수 있다

.explain():      레시피(실행 계획)를 실행 없이 텍스트로 보여줌. action 아님

.cache()의 함정:  그 자체는 "포스트잇 예약"일 뿐 실행이 아니다
                 뒤에 action이 없으면 저장도 안 되고, 그 위로 다음 레시피가 계속 얹혀
                 레시피가 무한정 길어질 수 있다 (04번 OOM의 정체)

해결책:          .cache() 직후 .count()로 그 시점 레시피를 즉시 실행·고정
                 → 계산량 자체를 줄이진 않지만, 레시피가 안 죽고 끝까지 돌게 만든다

OOM:             Out Of Memory. 필요한 메모리가 할당된 한도를 넘어 프로세스가 죽는 에러
