# 04번을 ValuePick 가치주 점수 기반으로 전환하는 계획 (2026-07-31 수립)

## 왜 필요한가

지금 `04_backtest_grid.py`는 PER상한×PBR상한×배당수익률하한을 **문턱값(threshold)** 으로 필터링하는
전략 그리드를 백테스트한다. 이건 valuepick-batch가 원래 "학습 대상"으로 삼은 **기존 ValuePick
서비스(Spring Boot)의 실제 추천 로직과 다른 방식**이다.

기존 서비스(`Top100Service.scoreAll()`)는 PER/PBR/ROE/ROA/부채비율/EPS성장률/모멘텀 7개 팩터를
**백분위 정규화 후 가중합산**해 점수를 매기고, F-Score(재무 건전성) 필터를 통과한 종목 중 점수
상위 100개를 고정으로 뽑는다. 문턱값 방식이 아니라 **상대평가 점수 방식**이다.

지금까지 04번으로 찾은 "최선의 PER/PBR/배당 조합"은 **ValuePick이 실제로 추천하는 종목군과 무관한
별개의 실험**이다. ValuePick 서비스가 실제로 잘 작동하는지 검증하려면, 04번이 이 점수 로직을
그대로 재현해서 백테스트해야 한다.

따라 절대 수정하지 않는다. Spark 리포(`valuepick-batch/`)에만 새로 구현한다.

## ValuePick 점수 로직 요약 (재현 대상)

```java
// 팩터별 가중치 (합계 1.0)
PER          25%  (낮을수록 고점수)
PBR          15%  (낮을수록 고점수)
ROE          20%  (높을수록 고점수)
ROA          10%  (높을수록 고점수)
부채비율      15%  (낮을수록 고점수)
EPS성장률     5%  (높을수록 고점수)
모멘텀        10%  (높을수록 고점수)
```

각 지표를 종목 집합 내 순위로 바꾼 뒤 `(n-1-rank)/(n-1)`로 0~1 백분위 값을 만들고, 가중치를 곱해
합산한다(총점 0~1). null 값은 불리한 쪽 극값(`MAX_VALUE`/`-MAX_VALUE`)으로 채워 순위 최하위 취급.

**사전 필터**: F-Score(Piotroski, 9점 만점) ≥ 6점만 후보. 단 금융업(`induty_code` 앞 2자리가
64/65/66)은 F-Score 계산 자체가 무의미해 이 필터를 면제받는다. `induty_code`가 없는(업종 미분류)
종목은 이 예외를 공정하게 적용 못 하므로 후보에서 아예 제외.

## Spark 데이터에서 확인된 사실 (2026-07-31 실측)

- `indicators`(03번 출력)에 `roe, roa, debt_ratio, eps_growth_rate, momentum, f_score`가
  **이미 전부 존재한다.** PER/PBR과 별도 계산 불필요.
- **ROE/ROA/부채비율은 재무제표 원본값끼리의 비율**(`net_income_krw/equity_krw` 등)이라
  **가격에 의존하지 않는다.** PER/PBR처럼 시점별 가격 재계산이 필요 없고, `rcept_no <=
  rebalance_date`로 시점에 맞는 재무제표 버전만 고르면 된다 (`latest_valid_indicators`가
  이미 하는 일 그대로 재사용 가능).
- **`raw/companies`에 `induty_code`가 없다.** 01번이 DART `corpCode.xml`(고유번호 목록)만
  호출하고 `company.json`(기업개황, induty_code 포함)은 호출한 적이 없다. 즉 금융업 판정에
  필요한 데이터가 Spark 쪽에 아예 없는 상태 — 새로 수집해야 한다.

## 확정된 결정 사항 (사용자 승인 완료)

1. **F-Score 금융업 예외**: DART API로 `induty_code`를 새로 수집해서 ValuePick과 동일하게
   구현한다. (검토했던 대안 — 예외 없이 전체 적용, 필터 자체 생략 — 은 채택 안 함)

## 작업 순서

### 1단계 — `01_ingest_raw.py`에 `induty_code` 수집 추가

- DART `company.json` API 호출 추가: `https://opendart.fss.or.kr/api/company.json?crtfc_key={DART_API_KEY}&corp_code={corp_code}`
- 응답 필드 `induty_code`(문자열, 3~5자리)를 `companies` 저장 시 컬럼으로 추가
- 이미 수집된 `corp_code` 목록(`fetch_dart_corp_code_map`)을 재사용해 종목당 1회 호출
- `already_ingested()` 방지 로직 그대로 적용 (CLAUDE.md 실행 규칙 확인 필요 — 재수집 방지가
  `snapshot_type_exists()` 기준으로 07-31 세션에 이미 한 번 고쳐졌으므로 그 로직과 충돌 없는지 확인)
- **실행 전 필수 확인**: DART API 일일 호출 한도(보통 20,000회/일). 종목 수(2,555개) 기준
  1회씩만 호출하면 여유 있으나, 실행 중 실패로 재시도가 반복되면 한도 소진 위험 — sleep 간격을
  기존 API 호출 패턴(`fetch_financial_statement` 등)과 동일하게 맞출 것.

### 2단계 — 업종코드 매핑을 어디서 적용할지 결정

`induty_code` 원본은 `companies`에 저장하고, "금융업 여부" 판정(`prefix in ('64','65','66')`)은
04번에서 `screen_portfolio` 진입 전에 종목 목록에 조인하는 방식을 검토. 03번에 넣을지 04번에
넣을지는 이 리포의 "잡 간 데이터는 Parquet, 각 잡은 순수 함수"라는 기존 구조(CLAUDE.md 6항)에
맞춰 다음 세션에서 결정.

### 3단계 — `04_backtest_grid.py` 재작성

**유지하는 것** (2026-07-31 세션에 벡터화·검증 완료된 인프라, 재작업 불필요):
- `prices_at_dates`, `latest_valid_indicators`의 crossJoin+Window 벡터화 구조
- `split_flags` 기반 이상치(액면분할 의심 종목) 제외 로직 (`calculate_period_returns`)
- `calculate_period_returns`, `summarize_performance` — 구간 수익률·성과 계산 자체는
  종목 선정 방식과 무관하므로 그대로 재사용
- 룩어헤드 방지(`rcept_no <= rebalance_date`), History Server, 이벤트 로그

**바뀌는 것**:
- `screen_portfolio`의 `condition`(PER≤x & PBR≤y & dy≥z 문턱값 필터) →
  ValuePick `scoreAll()`과 동일한 7팩터 백분위 가중합산 점수 계산 함수로 교체
  - PySpark 구현 시 순위는 `Window.orderBy` + `F.percent_rank()` 또는 `F.row_number()`로
    ValuePick의 `ascRank`/`descRank`와 동일한 정의(0-based, 낮은 값이 rank 0)를 재현할 것
  - null 처리: ValuePick은 낮을수록 좋은 지표는 `MAX_VALUE`, 높을수록 좋은 지표는 `-MAX_VALUE`로
    채워 최하위 순위를 준다. Spark에서는 `F.coalesce`로 동일하게 재현
- F-Score≥6 필터 추가 (금융업 예외 포함)
- 랭킹 기준이 `per_t asc` → `value_score desc`로 변경
- **시점별 재계산 여부**: PER/PBR/배당수익률만 `compute_point_in_time_ratios`로 시점별 재계산
  유지(룩어헤드 방지 목적 그대로). ROE/ROA/부채비율/모멘텀/EPS성장률/F-Score는 가격 무관이므로
  재계산 없이 `latest_valid_indicators`가 고른 시점의 재무제표 값을 그대로 사용
- `conf/generate_strategies.py`: PER×PBR×배당 그리드(5×5×4=100가지) 제거.
  **리밸런싱주기(2) × portfolio_size(10/30/50/100/300, 5) = 10개 전략**으로 대폭 축소.
  그리드가 작아지므로 계획 트리 문제(2026-07-31 벡터화로 해결한 것)가 재발할 가능성은 낮지만,
  crossJoin 규모가 줄어드는 것뿐 구조 자체는 동일하게 유지.

### 4단계 — 검증

- `held_count`, F-Score 필터 통과 종목 수가 ValuePick 운영 로그(있다면)와 비슷한 규모인지 확인
- 04번 KOSPI 재실행 → `check_04_backtest.ipynb` 갱신 (이번엔 조건 그리드가 없으므로 섹션 9의

## 리스크 / 확인 안 된 것

- DART `company.json`의 `induty_code`가 모든 종목에 존재하는지 미확인 (ValuePick도 "업종
  미분류 종목은 후보 제외"로 대응하는 걸 보면 결측이 실제로 있는 것으로 추정)
- ValuePick의 F-Score 계산(`resolveFScore`, Java)과 Spark `calculate_f_score`(03번)가
  같은 로직인지 미확인 — 이미 같은 리포에 03번이 구현돼 있으므로 대조만 하면 되지만
  아직 안 함
- 점수 기반으로 바꾸면 전략이 10개로 줄어 백테스트 자체는 훨씬 빨라지지만, "그리드 탐색"이라는
  현재 04번의 성격(1,000개 전략 동시 비교)이 사라진다 — 이게 이번 프로젝트의 학습 목표
  ("전략 조합을 곱하는 순간 연산량이 폭증한다"는 것을 Spark로 실측하는 것)와 상충하는지
  다음 세션에서 사용자와 재확인 필요. 필요하면 리밸런싱×n 그리드에 "점수 가중치 조합"이라는
  새 축을 추가해 그리드 규모를 다시 키우는 방향도 검토 가능(예: 가중치를 몇 가지 프리셋으로
  변주).
